# AGENTS.md — алгоритм работы для агентов и новых сессий

**Ямастер Чек** (`Rimlin-UNC/1c_chek`): система сканирования кассовых чеков и
интеграции с 1С:Предприятие (FastAPI). Это главный вход для любой сессии:
пройдите алгоритм ниже по шагам. Отчёты, комментарии в коде, описания коммитов
и документация — **только на русском языке** (правило владельца).

## Задание агента (владелец, 03.11.2026)

Агент — программист с бригадой тестировщиков. Цель — сделать «Ямастер Чек»
приложением № 1 в своей нише: учёт кассовых чеков компании от скана до 1С.

1. **Порядок ценностей:** сохранность и правильность данных → установка без страха
   (обновление из программы, резервная копия, откат) → скорость и удобство
   сотрудника, бухгалтера, руководителя → новые возможности.
2. **Только вперёд:** каждое изменение — улучшение с тестом. Ошибку сначала
   воспроизвести тестом, потом чинить. Ворота CI не ослаблять. Дефект, найденный по
   пути, — исправить или завести задачу, не проходить мимо.
3. **Учиться и брать лучшее:** перед новой функцией посмотреть, как сделали лучшие —
   GitHub, Хабр, документация ФНС и 1С, конкуренты (1С:Сканер чеков, Saby, Expensify
   и другие). Выводы с источниками — в [`docs/kb/10_research.md`](docs/kb/10_research.md).
4. **Предлагать:** на каждой вехе — 1–3 нововведения владельцу с ценностью,
   трудоёмкостью и риском. Решает владелец, если меняется поведение для компаний,
   данные или стоп-лист.
5. **Помнить и уметь откатиться:** история — git (коммиты на русском), CHANGELOG,
   [реестр выпусков](docs/kb/09_releases.md), [журнал сессий](docs/kb/08_session_journal.csv),
   PR #3; порядок отката — раздел [«История и откат»](#история-и-откат).
6. **Беречь время и память:** только нужные коннекторы ([политика](#политика-только-нужные-коннекторы));
   длинные прогоны — фоном и по одному; повторяющееся — скриптами
   (`qa/session_check.py`, `qa/release_gate.py`).

## Алгоритм сессии

### 0. Старт: окружение и сверка с фактом

**Одной командой:** `python3 qa/session_check.py` — git против GitHub, окружение,
Chromium для Playwright, опоры репетиции, вход в GitHub, последний CI ветки и сводка
«что дальше» из `docs/kb`; печатает, что и как исправить. Если рабочие файлы равны
коммиту из истории ветки на GitHub (песочница восстановилась на старом указателе,
или параллельная сессия отправила коммиты в ту же ветку), он напечатает безопасную
команду: `git reset --mixed <коммит> && git merge --ff-only <голова GitHub>`.
Подробности каждого пункта — ниже.

1. **Проверить git.** Восстановленное рабочее пространство может показывать
   ветку на старом коммите, а все файлы — изменёнными (02.11.2026 так и было):
   ```bash
   git status --short | wc -l
   git rev-parse HEAD; git ls-remote origin refs/heads/<ветка сессии>
   # если HEAD ≠ удалённой голове — сравнить дерево через временный индекс:
   GIT_INDEX_FILE=/tmp/v.idx git read-tree <удалённая голова>
   GIT_INDEX_FILE=/tmp/v.idx git add -A
   GIT_INDEX_FILE=/tmp/v.idx git diff --cached --stat <удалённая голова>   # пусто → безопасно
   git reset --mixed <удалённая голова>    # указатель и индекс; файлы не трогает
   ```
   Разница не пустая — **не коммитить**: разобраться и сообщить владельцу.
   История: `git fetch --deepen=300 origin <ветка>`.
2. **Окружение:** `qa/setup_dev.sh --full` — всё для прогона как в CI
   (зависимости, psycopg, pgserver, stylelint и html-validate в `/tmp`).
   `.venv`, `node_modules` и `/tmp` между сессиями не сохраняются; проверка без
   установки — `qa/setup_dev.sh --check --full`.
3. **Сверка с фактом** (только чтение): последний прогон CI ветки
   ([RUNBOOK → CI](docs/RUNBOOK.md#ci)); Supabase — `list_migrations` и
   `supabase/checks/rls_fk_audit.sql`; Vercel — последние деплои `1c-chek`.
   Идентификаторы ресурсов и ограничения — в разделе
   [«Коннекторы и доступы»](#коннекторы-и-доступы).
   Расхождение с документами — сначала поправить документы и записать в журнал.

### 1. Прочитать задачи

1. [`docs/kb/02_roadmap.csv`](docs/kb/02_roadmap.csv) — `in-progress`, `blocked`, P0–P1.
2. Issues — через REST (метки не прикреплены, GraphQL капризен):
   `gh api "repos/Rimlin-UNC/1c_chek/issues?state=all&per_page=100" --jq '.[] | select(.pull_request | not) | [.number, .state, .title] | @tsv'`.
3. [`docs/kb/06_open_questions.csv`](docs/kb/06_open_questions.csv) — `open`;
   две последние записи [журнала](docs/kb/08_session_journal.csv).
4. Выбор: задача владельца → иначе `todo` с наивысшим приоритетом без блокера,
   где «Нужно подтверждение владельца» ≠ «да». Задача с подтверждением —
   показать план и ждать явного «да».
5. Поставить `in-progress` в CSV. Канбан в Google Sheets подтянет статус сам.

### 2. Ветка

- **Сессия Arena:** работать только в ветке сессии (`arena/<id>-1c-chek`), не
  создавать и не пушить другие ветки и `main`. Один PR из ветки в `main`; если
  он открыт — обновлять описание.
- **Человек-разработчик:** ветка от `main`, имя по задаче, PR в `main`.

### 3. Код

- Сначала тест нового поведения, потом код. Стандарт выпуска —
  [`docs/update_playbook.md`](docs/update_playbook.md) (ADR-02, 03, 05, 12, 15).
- Схема БД — только добавляющие изменения; старая версия должна работать с
  новой базой; внешних ключей из новых таблиц на старые не делать (ADR-03, 09).
- Блок «Проверка чеков (ФНС и источники)», паузу антибана и квоту не трогать.
- Новый экран — в обе матрицы ролей: `app/services/rbac.py` и `app/static/js/app.js`.
- Комментарии в коде и сообщения тестов — на русском.

### 4. Тесты

1. `./test.sh full -j2` — **0 failed**; прогон не прерывать.
2. `.venv/bin/ruff check app tests qa` — «All checks passed»; `npm run lint` — 0 ошибок.
3. SQL и БД — тесты PostgreSQL на одноразовой базе: `python qa/pg_local.py`
   (временный сервер; полный прогон как в CI — `python qa/pg_local.py full`).
4. Схема или пути данных — `python -m qa.upgrade_rehearsal --from-ref <коммит на сервере>`;
   путь миграции целиком (1.70.80 → перенос архива → откат) — сквозной тест
   `tests/test_migration_e2e.py` (#20), на PostgreSQL — через `qa/pg_local.py`.
5. Тест API шлёт то тело, что настоящий клиент (форма шлёт все поля, пустые —
   пустой строкой), а не минимальное: на минимальном теле 1.70.89 не увидел потерю
   данных Чек-Пула при сохранении формы (исправлено в 1.70.90).
6. Выпуск — «бригада тестировщиков» `qa/release_gate.py`: `rehearsal` до коммита
   (от всех опор из [реестра выпусков](docs/kb/09_releases.csv) подряд), `stage-b`
   после push, `ci` — ждёт CI и печатает итог ворот.
7. После push — **зелёный CI** на Python 3.11 и 3.12: 0 упавших и 0 пропущенных.
   Падения читать через API аннотаций ([RUNBOOK → CI](docs/RUNBOOK.md#ci)).
   Падение в CI, которого нет локально, — тест зависит от машины: чинить тест.

### 5. Pull request

- Коммиты — на русском: `область: суть; проверки` (выпуск: `vX.Y.Z: суть; NNN passed`).
- `git push origin <ветка>`; описание PR по шаблону: суть, проверки с числами,
  риски, `Refs #N`; `Closes #N` — только для полностью сделанного.
- Правка описания PR: прочитать текущий текст → изменить → проверить, что не
  пусто → `gh api -X PATCH repos/Rimlin-UNC/1c_chek/pulls/<N> --input <json>` →
  прочитать обратно (`gh pr edit` не работает).
- **Не сливать** без подтверждения владельца.

### 6. Обновить статус (в том же PR)

- Задача — `done` в `docs/kb/02_roadmap.csv`; новые задачи — сначала issue, затем
  строка `T-NN`. Вопросы — `06_open_questions.csv`; решения — новый раздел ADR в
  `docs/ARCHITECTURE.md`; БД — `docs/DATABASE.md`; журнал — `08_session_journal.csv`.
- Выпуск — строка в [реестре выпусков](docs/kb/09_releases.csv): в коммите выпуска,
  прогон CI и этап Б — в коммите базы знаний.
- Представления в Google (QA-панель — `qa/test_matrix.py`, лист «Тесты»; отчёт;
  презентация) — **на вехах**: конец фазы или просьба владельца, по фактам из
  репозитория ([RUNBOOK → QA-панель](docs/RUNBOOK.md#qa-панель-в-google-sheets)).
  Между вехами они отстают — это нормально: источник истины — GitHub.

### 7. Деплой и отчёт владельцу

- **Рабочий сервер:** владелец ставит обновление из программы. В отчёте —
  ветка, «Проверить», «Обновить», откат.
- **Vercel:** превью каждого push должно быть `READY` (сигнал сборки, не прод).
- **Отчёт:** что сделано; ссылки на PR, коммиты, issues, таблицу и документ;
  проверки с числами; что ждёт решения владельца.

| Notion | подключён, но выключен | — | Не используется ([ADR-16](docs/ARCHITECTURE.md#adr-16)): база знаний — `docs/kb`, для владельца — Google Slides. |

Права токена GitHub проверять заведомо неверным запросом: 422 — право есть,
403 — нет; данные не меняются. Исключение — PR: неверный `state` в PATCH
молча игнорируется (ответ 200), поэтому права на PR так не проверять.

## Стоп-лист: только после явного «да» владельца

- Слияние в `main`, закрытие или слияние PR, push в чужие ветки.
- Любые DDL, DML и изменения прав в Supabase: история миграций, настройки Auth и
  интеграции с GitHub (#21), ключи API. Схема `qa_lock_…` удалена 07.11.2026 по
  «да» владельца (#7) — правило про DDL остаётся: без явного «да» ничего не менять.
- Новые или изменённые файлы `supabase/migrations`, `supabase/functions`,
  `supabase/config.toml`: ветка сессии — production-ветка интеграции Supabase,
  и push применяет их к рабочему проекту (#21).
- Настройки, переменные, домены и production-деплой Vercel; promote или rollback.
- Перенос архива (backfill) и любые действия на рабочем сервере.
- Изменения блока ФНС, паузы антибана, квоты.
- Ослабление ворот CI: пропуск упавших или пропущенных тестов.
- Удаление или массовая перезапись записей документации без чтения и причины.

## Можно без подтверждения

- Чтение GitHub, Supabase, Vercel, Google.
- Коммиты и push в ветку своей сессии, обновление своего PR.
- Issues, документы, CSV-базы: создание и обновление (не удаление).
- QA-панель, отчёт и презентация в Google — как представления репозитория.
- Локальные тесты, одноразовые базы, превью-деплой Vercel (не production).

## Никогда

- Секреты в репозитории, документах, issues, PR и Google: только имена
  переменных и назначение.
- Строки рабочих данных и персональные данные: только схема и агрегаты.
- Перенос рабочей базы, её копий и выгрузок в Supabase, среду разработки или CI:
  рабочая база остаётся на рабочем сервере, здесь — только синтетические тесты
  (решение владельца 03.11.2026, ADR-14).
- Выдумывать: нет данных или они противоречат друг другу — «требует уточнения».

## Подводные камни (проверено на практике)

Особенности коннекторов — в разделе [«Коннекторы и доступы»](#коннекторы-и-доступы).

- **`wc -c` считает байты:** кириллица в UTF-8 — 2 байта. Длину текста мерить
  символами (`len` в Python).
- **Временная копия репозитория в `/tmp`** ломает тесты: `INSTALL_TMP` строится
  от каталога приложения, а без `.venv` внутри копии падает обёртка Newman.
  Копию для аудита — вне `/tmp`, с доступом к `.venv`.
- **psycopg 3 и знак %:** `exec_driver_sql` передаёт пустые параметры, и `%` в
  PL/pgSQL или LIKE читается как заполнитель — выполнять такой SQL курсором
  драйвера без параметров.
- **Реестр долга линтера** (`tests/test_v17038.py`): потолки по правилам расти
  не должны. Новый файл со строкой `# -*- coding: utf-8 -*-` (UP009) или
  `subprocess.run` без явного `check=` (PLW1510) роняет CI — так упал прогон на
  `7138d5e`. Либо не добавлять замечание, либо поднять потолок в том же коммите
  с обоснованием в комментарии.
- **Роли PostgreSQL общие для кластера:** `CREATE ROLE` после проверки «нет ли
  такой» гоняется при параллельном прогоне (xdist) — перехватывать
  `duplicate_object` и `unique_violation` (`_ensure_roles` в
  `tests/test_supabase_migrations.py`).
- **Модуль `csv` в Python** по умолчанию пишет концы строк CRLF, а базы
  `docs/kb` — с LF: писать с `lineterminator="\n"`.
- **Новый импорт в `app.js`:** `tests/js/telegram_login.test.js` и
  `tests/js/splash.test.js` выполняют `app.js` без строк `import` и подставляют
  заглушки — добавить заглушку нового имени в оба файла. Итог Vitest проверять
  по коду выхода и строке `Errors`: при необработанной ошибке все тесты зелёные,
  а прогон падает (02.11.2026 так поймали `viewUnifiedReview is not defined`).
- **Тесты одного процесса делят состояние** (`--dist loadfile`, фикстура
  `client` — на сессию): cookie гостя пула и фоновые потоки `pool-web-ingest`
  соседних файлов пишут в ту же SQLite. Тест, чья запись идёт в SAVEPOINT
  (слияние гостя), ждёт фон (`_wait_ingest_threads` в `tests/test_v17041.py`)
  и выводит журнал в сообщение — так нестабильно упал прогон на `1adbffa`.
- **Сквозной тест миграции (#20)** запускает фазы старой и новой версии
  отдельными процессами; в неглубоком клоне (CI) коммит 1.70.80 догружает
  сам (`git fetch --depth=1`). 1.70.80 не ставится на чистый PostgreSQL
  (`is_active = 1` в булев столбец) — тест обходит это её же моделями.

- **Параллельная сессия в той же ветке (03.11.2026):** пока сессия ждала ответа,
  в ветку пришли пять коммитов (выпуск 1.70.89). Сверяться с GitHub в начале и перед
  каждым push (`qa/session_check.py`); отставание — `git merge --ff-only`, не перезапись.
- **Восстановленная песочница:** указатель на базовом коммите ветки, новые файлы —
  неотслеживаемые. `git diff <коммит>` их не видит и показывает «удаления» — сравнивать
  дерево с неотслеживаемыми (временный индекс, `qa/session_check.py`).
- **Страж литералов версии** (`tests/test_v17020.py`): литерал текущей версии в строке
  теста с `not in` падает (он подстрока `?v=<версия>`) — выносить в отдельный `assert`
  или писать через `VERSION`.
- **Импорт фикстуры по имени** и её параметр дают F811 и ARG001 в храповике долга —
  связывать присваиванием и `usefixtures`; заранее: `ruff check --select ARG001,I001,F811`.
- **Отчёты репетиции и этапа Б — JSON:** считать проверки разбором (`qa/release_gate.py`),
  а не поиском значков в тексте; прогоны — строго по одному.
