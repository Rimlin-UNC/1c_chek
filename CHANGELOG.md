# Журнал изменений — Ямастер Чек

> Разработчик и владелец идеи: ООО «Ямастер» · [ymaster.ru](https://ymaster.ru) · info@ymaster.ru
> Формат: Semantic Versioning (MAJOR.MINOR.PATCH)

## [1.43.0] — 2026-10-06
### Added
- **Вход по отпечатку пальца / лицу / PIN устройства (WebAuthn, passkey)** — альтернатива паролю. После первого входа по паролю приложение предлагает привязать устройство (если есть сканер: Windows Hello / Touch ID / Android Biometric); дальше вход одним касанием — с экрана входа кнопкой «🔑 Войти по отпечатку пальца / Face ID» или без неё (браузер сам предложит сохранённый ключ).
- **Мультиустройственность:** каждый ключ привязан к своему устройству; у пользователя может быть до 10 ключей, список и отвязка — Настройки → «🔑 Быстрый вход» (доступно всем ролям). Ключи-«пасскеи» синхронизируются экосистемами (iCloud Keychain / Google Password Manager) и работают между устройствами одной экосистемы; между чужими устройствами — привязка заново одним касанием.
- **Приватность (152-ФЗ):** биометрия не хранится на сервере и не покидает устройство — проверяет защищённый чип; передаётся и хранится только публичный ключ (в БД `webauthn_credentials`), одноразовые challenge — в `webauthn_challenges` (3 минуты, однократно). Модели только добавляющие.
- Эндпоинты: `POST /api/v1/auth/passkey/register/options|verify` (привязка, нужен вход), `POST /api/v1/auth/passkey/login/options|verify` (вход без пароля, публично), `GET/DELETE /api/v1/auth/passkeys` (управление). Доменная привязка ключа берётся из Host/X-Forwarded-Proto — работает одинаково на localhost, IP и chek.ymaster.ru. Аудит: `passkey_added`, `passkey_removed`, `login_passkey`, `login_passkey_failed`.
- Зависимость: `webauthn` (py_webauthn, BSD-3-Clause) в requirements.txt.

## [1.42.0] — 2026-10-06
### Changed
- **Меню переключения ролей — только у администратора.** Карточка профиля в шапке у бухгалтера и сотрудника больше не открывает меню переключения (раньше не-админ видел раздел «Посмотреть глазами» с ошибкой доступа). Участники Чек-Пула, как и прежде, работают только в своём кабинете и не видят админских переключателей. В режиме просмотра меню предлагает только возврат.
### Added
- **Права в режиме просмотра = права роли (подтверждено тестами).** Администратор в режиме роли может делать всё, что доступно этой роли, и ничего сверх: сотрудник — правит только уведомление/комментарий своего чека (400 при попытке править суммы), бухгалтер — любые поля чеков компании, админ-эндпоинты недоступны (403). Иерархия: Администратор → Бухгалтер → Сотрудник; отдельный контур — участник Чек-Пула; гость и партнёр API — без интерфейса.
- Памятка об иерархии ролей в разделе «Пользователи».

## [1.41.0] — 2026-10-06
### Added
- **Раздел «Чек-Пул: участники»** (`#/poolpeople`, только администратор): полный список участников пула — e-mail, статус, чеки, баллы, риск-скор, дата входа в пул — с поиском по e-mail/нику. Ранее списка участников в панели не было вовсе.
- **Просмотр кабинета участника (режим просмотра, третья роль).** `POST /api/v1/pool-admin/impersonate-pool/{id}` выдаёт pool-токен участника: ядро-логин администратора сохраняется, кабинет «Мой Чек-Пул» открывается ровно так, как его видит участник (чеки, баллы, ачивки, вывод). Полоса «↩ Вернуться в администратора» восстанавливает прежний токен кабинета; выход фиксируется (`impersonate_pool_stop`). Кабинеты заблокированных участников не открываются (422). Участники также добавлены в меню профиля в шапке (топ-6 + переход в раздел).
- Список участников: `GET /api/v1/pool-admin/participants` (поиск q по e-mail/нику — кириллица без регистра, лимит ≤ 200).
### Roles
- Инвентаризация ролей: **администратор / бухгалтер / сотрудник** (ядро, просмотр — v1.18.0), **участник Чек-Пула** (отдельный контур, самостоятельная регистрация — просмотр добавлен в v1.41.0), **гость сайта** (вид, чеки без аккаунта — аккаунта нет, просмотр не применим), **партнёр API** (apk-ключ, интерфейса не имеет). Просмотр любой роли — только у администратора (require_admin; цепочки исключены: pool-токен не проходит ядро).

## [1.39.0] — 2026-10-06
### Added
- **«Чек-Пул», этап 9.1: платное API для внешних клиентов** (план, Этап 9.1; принцип plan.md «продаём доступ к фильтрам, а не чеки»). **Ключи партнёров**: формат `apk_…`, в БД только sha256 (полный ключ показывается один раз при выдаче), лимиты на ключ (по умолчанию 60 запросов/час, 5 000/мес, настраиваются при выдаче), префикс и статистика в админ-панели; выдача/отзыв — в журнале действий; API включается администратором (по умолчанию выключен).
- **Анонимные агрегаты** (`/api/v1/pool-api/v1/*`): сводка пула (чеки, участники, гео-покрытие, средний чек), регионы, отрасли, топ продавцов (публичные реквизиты магазинов), счётчик и суммы-агрегаты под фильтрами (период/регион/город/отрасль/ИНН/суммы). Сырые чеки, позиции, участники и персональные данные наружу не отдаются.
- **Учёт вызовов**: `pool_api_calls` (path без query), превышение лимита — 429 с текстом тарифа, чистка старше **90 дней** (152-ФЗ) — в общей чистке техданных антифрода.
- Модели только добавляющие: `pool_api_keys` (UNIQUE хэш), `pool_api_calls` (FK на ключ, индекс ключ+время).

## [1.38.0] — 2026-10-06
### Added
- **«Чек-Пул», этап 9 «Рост»: граф-аналитика антифрода.** `GET /api/v1/pool-fraud/graph` — кластеры участников, объединённые общим устройством (`visitor_hash`), подсетью /24 за окно и реферальными парами (union-find, лимит узлов); в панели `#/fraud` — SVG-граф с легендой: цвет точки — карантин/риск ≥ 40/норма, цвет ребра — тип связи, клик по участнику открывает карточку. «Фермы аккаунтов» видны одним взглядом.
- **Партнёрская программа (кэшбэк-канал из plan.md).** Справочник партнёров офлайн (`partners.json`: ИНН, % кэшбэка, город); за верифицированный чек партнёра участник получает кэшбэк баллами — процент от суммы чека, кап 100 баллов, дедуп по чеку, в карантине антифрода не платится (`partner_cashback` в журнале). Публичный список `GET /public/pool/partners` и QR «на кассе»: `GET /public/pool/partners/qr.svg?code=…` — SVG через вендоренный генератор qrcode (BSD, копия в `app/vendor/`), печатается со страницы **«Партнёры и кэшбэк»** (`#/partners`).
### Отложено (по плану)
- ML-классификатор позиций — после накопления корпуса 5–10 тыс. позиций; платное API для внешних клиентов — следующий выпуск (v1.39.0).

### Added
- **«Чек-Пул», этап 8: подбор из пула для компаний** (план разд. 2/8). ## [1.35.0] — 2026-10-06
### Added
- **«Чек-Пул», этап 6: реферальная программа с порогами** (концепция plan.md, разд. 2). Код приглашения `YM-XXXXXX` (без похожих символов) и ссылка `#/r/КОД` (30 дней); вкладка «🎁 Приглашайте» в кабинете: ссылка с копированием, приглашённые, сколько баллов принёс каждый.

Lifetime-хвост **5%**: каждый 20-й чек реферала → +1 балл, **потолок 200 баллов/мес**. **Один уровень**, лимит **50 приглашённых**.
- **Антифрод-связка**: «сам себя пригласил» не приносит ни балла — пары с общим устройством, одной подсетью (`SAME_SUBNET_REFERRAL` +45), мгновенным чеком (`FAST_REFERRAL` +40), петлёй (`REFERRAL_CYCLE` +50) или в карантине **не получают выплаты**, пока сигналы не разобраны в панели антифрода; разбор как ложного возвращает начисления.
- Публичный лендинг `/r/КОД` показывает «вас пригласил …» без персональных данных; все выплаты — в журнале баллов (`R_*`), модели только добавляющие (`pool_referrals`, UNIQUE по приглашённому).

## [1.34.0] — 2026-10-06
### Added
- **«Чек-Пул», этап 5: антифрод из 5 слоёв** (по концепции plan.md), принцип «не запрет, а ограничение скорости выгоды»:
  **Device** — обезличенный отпечаток браузера (`X-Visitor-Id`, на сервере только хэш): один visitor на 2+ аккаунтах → `MULTI_ACCOUNT_DEVICE` +60; **Network** — журнал IP//24: `SUBNET_CLUSTER` (5+ регистраций из одной /24 за сутки) +45, `DATACENTER_IP` (офлайн-список CIDR облаков) +25; **Behavior** — `BOT_PATTERN` (отправка формы быстрее 0,8 с) +40, `EVEN_INTERVALS` (ровные интервалы чеков) +40, `RECEIPT_FLOOD` (20+ чеков/час) +30; **Graph** — связи по устройствам/подсетям в карточке участника, `REFERRAL_FRAUD` зарезервирован до этапа 6; **Rules** — `REPEAT_SUMS` (5 одинаковых сумм подряд) +20.
- **Риск и карантин**: `pool_users.risk_score` (0–100 = сумма весов сигналов без ложных), **risk ≥ 71 → карантин**: чеки сохраняются в пул, баллы приостанавливаются; риск упал — карантин снимается автоматически. Одноимённый сигнал не чаще раза в сутки (честных не спамим); `false_positive` убирает вес.
- **Панель `#/fraud` (админ)**: сводка, лента сигналов с фильтрами (статус/важность), **карточка участника** (устройства, IP, связанные аккаунты, сигналы), разбор в один клик и **массово** (ложное/подтверждено), снятие карантина, аннулирование баллов (с записью в журнале), уровень доверия, чистка техданных старше года (**152-ФЗ: IP/устройства ≤ 12 мес**).
- Модель (только добавляющее): `pool_users.risk_score/quarantined_at`, `pool_consents.visitor_hash`, таблицы `pool_fingerprints`, `pool_ip_log`, `pool_signals`; API `/api/v1/pool-fraud/*`; все модерации — в аудите; оферта дополнена строкой о технических признаках.

## [1.17.0] — 2026-10-04

### Исправлено: обновление из приложения без пароля (главное)
- **Причина отказа пароля найдена**: приложение работает под служебным
  пользователем, а `sudo` проверяет пароль именно его — пароль администратора
  из терминала в приложении работать не мог в принципе.
- **Самоперезапуск re-exec** (`_self_reexec`): после обновления файлов процесс
  заменяет собственный образ (`os.execv`) — новый код загружается тем же PID,
  порт переоткрывается (close-on-exec), права root не нужны. Порядок: sudoers
  → re-exec → systemctl → sudo -S. Конфиг `SELF_REEXEC` (по умолчанию вкл),
  в тестах запрещено (YM_NO_REEXEC / PYTEST_CURRENT_TEST).
- preflight: `reexec_ok`, `can_restart` = systemctl-право ИЛИ re-exec;
  чип «Перезапуск» с режимом; диалог обновления объясняет, почему пароль
  больше не нужен.
- `/admin/system`: python, аптайм, размер БД, счётчик компаний, служебный
  пользователь, имя юнита и **готовая sudoers-команда** (копируется кнопкой).

### Сброс кэша клиентов после обновления

## [1.11.0] — 2026-10-04 — «Платформа: ведите бухгалтерию нескольких компаний»

Приложение выросло из инструмента одной компании в **сервис аутсорсинга бухгалтерии**:
один сервер — неограниченное число компаний-клиентов (ООО, ИП), у каждой своё
изолированное пространство со своими сотрудниками и чеками.

### 🏢 Компании (мультикомпанийность)
- Администратор создаёт компании (название, ИНН, памятка), архивирует их, видит
  сводку: сотрудники (бухгалтеры/пользователи), чеки, суммы, последняя активность.
- **Изоляция**: бухгалтер видит чеки только своей компании; пользователь — только
  свои чеки в своей компании; чужая компания для него «не существует» (в том числе
  в живой ленте WebSocket и журнале действий). Администратор видит всё.
- Механизм — стандартная SaaS-модель «общая БД + company_id в каждой строке»,
  единая точка правил доступа `app/services/scoping.py`; миграция сама создаёт
  компанию по умолчанию и переносит в неё все существующие данные — ничего не теряется.

### 🔓 Фильтр «Все компании / одна компания»
- Селектор в шапке (только у админа): дашборд и база чеков показывают выбранную компанию;
  выбор запоминается. На дашборде без фильтра — карточка **«По компаниям»** со сводкой
  (чеки, суммы, кнопка «открыть пространство»).

### 🔁 Перемещение чеков между компаниями
- База чеков → отметить галочками → **«🏢 Переместить в компанию»**: чек переезжает
  целиком (реквизиты, позиции, статус ФНС), опционально с новым подотчётным лицом.
  Флаг «выгружен в 1С» сбрасывается — выгрузку новой компании контролирует её бухгалтер.
  Чек уникален глобально (ФН+ФД+ФП): дубликат между компаниями невозможен, при скане
  «чужого» чека система честно сообщает об этом без раскрытия данных.

### ✉️ Приглашения и сотрудники в компаниях
- Приглашение создаётся **с привязкой к компании** — новый сотрудник сразу попадает
  в её пространство; в списках пользователей и приглашений видна компания.
- Сотрудника можно перевести в другую компанию (диалог пользователя).
- Сканирование админом: селектор пространства в шапке определяет, куда попадут новые чеки;
  подсказка на экране сканирования.

### 🛡 Безопасность
- WebSocket-подписчики аутентифицируются (token/cookie): события чеков доставляются
  только в свою компанию; аноним получает лишь платформенные события.
- Все чековые API (список, карточка, QR, правка, удаление, проверка, выгрузка, CSV,
  назначение, данные сервисов) проходят через единую изоляцию; перемещения — только админ.
- Выгрузка 1С `pull?company_id=…` — можно забирать чеки одной компании.

  (одноразовую/многоразовую, со сроком); регистратор сразу получает роль. Роль
  «администратор» через приглашение недоступна.

  передача прав `POST /users/{id}/promote-admin` (целевой — админ, прежний — бухгалтер).
- **Обязательная смена временного пароля** (`must_change_password`): первый вход
  администратора и сброс пароля требуют задать новый (несбрасываемое окно).
- **Безопасность:** rate limiting (скользящее окно: login 10/мин, регистрация 20/час,
  API 240/мин → 429 + Retry-After); LoginGuard (5 неудачных входов → блок 15 мин);
  security headers (CSP, X-Frame-Options, nosniff, Referrer/Permissions-Policy).
- **Анти-DoS на периметре:** Nginx limit_req/limit_conn, UFW (только 22/80/443 наружу),
  fail2ban (бан IP за перебор по access-логу) — конфиги в deploy/, ставит deploy.sh.
- **deploy.sh:** развёртывание на Ubuntu 24.04 прямо из GitHub-ветки одной командой,
  режим `--update`, поддержка приватного репозитория через GITHUB_TOKEN, Nginx+UFW+fail2ban.
- **Автоматизация рутины бухгалтера (по анализу рынка Entera/1С:Распознавание):**
  - поле «Сотрудник (подотчётник)» на чеке: массовое назначение, подсказки, попадание
    в EnterpriseData (Контрагент) и Push-payload;
  - авто-проверка чека в ФНС сразу после сканирования (настройка, по умолчанию вкл.);
  - CSV-экспорт для Excel (разделитель «;», BOM, суммы с запятой).
- Комментарий к чеку; поиск по сотруднику; фильтр по сотруднику.

- список чеков: пользователь видит только свои (серверный фильтр);
