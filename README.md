# 1c_chek
# Техническое задание для ИИ-агента: Система сканирования кассовых чеков и интеграции с 1С
## 1. Общее описание и цели проекта
### 1.1. Назначение системы
Разработка кроссплатформенного программного комплекса для автоматизированного сбора, верификации и загрузки данных кассовых чеков в учетные системы на платформе 1С:Предприятие. Система должна обеспечивать сканирование QR-кодов чеков с мобильных устройств, сканеров и веб-камер, централизованное хранение на сервере под управлением Ubuntu 24.04, проверку подлинности через API ФНС и гибкую настройку маппинга реквизитов при загрузке в 1С.
### 1.2. Ключевые цели
- Создать продукт, превосходящий существующие решения (1С:Сканер чеков, СБИС, Entera) по гибкости, скорости и функциональности.
- Обеспечить сквозной процесс: сканирование → верификация → хранение → загрузка в 1С без ручного ввода.
- Реализовать механизмы дедупликации и настраиваемой фильтрации данных на всех этапах.
- Заложить основу для масштабирования и добавления новых источников чеков (ОФД, email, API банков).
### 1.3. Целевая аудитория
- Бухгалтеры и финансовые службы, работающие с авансовыми отчетами.
- Сотрудники, приобретающие товары/услуги для бизнеса.
- ИТ-специалисты, интегрирующие внешние данные в 1С.

## 2. Обзор рынка и анализ лучших практик
### 2.1. Существующие решения
| Решение | Сильные стороны | Ограничения |
|---------|----------------|-------------|
| **1С:Сканер чеков** | Встроен в 1С, проверка в ФНС, мобильное приложение | Только авансовые отчеты, ограниченный маппинг, зависимость от официальной поддержки |
| **СБИС (Saby)** | Автораспознавание документов, широкая экосистема | Высокая стоимость, привязка к экосистеме СБИС |
| **Entera** | Интеграция с 1С, извлечение данных через ОФД | Ограниченная настройка, зависимость от ОФД |
| **Платформа ОФД** | Прямой доступ к фискальным данным | Требует договора с ОФД, нет сканирования |
### 2.2. Технические стандарты и нормативы
**Структура QR-кода кассового чека (54-ФЗ)**:
- `t=` — дата и время расчета (ГГГГММДДТЧЧММ)
- `s=` — сумма расчета
- `fn=` — заводской номер фискального накопителя
- `i=` — порядковый номер фискального документа
- `fp=` — фискальный признак документа
- `n=` — признак расчета
**API ФНС «Открытое API проверки чека ККТ»**:
- Требуется Мастер-токен (получение через заявку)
- Временный токен обновляется периодически
- Доступны методы проверки по ФН, ФД, ФПД
**Формат EnterpriseData для 1С**:
- XML-формат, бизнес-ориентированные структуры
- Поддержка в 1С:ERP, КА2, УТ11, БП 3.0
- Односторонняя/двусторонняя синхронизация
### 2.3. Лучшие практики сканирования
- **Множественное чтение QR**: не полагаться на первый найденный код, собирать все и фильтровать по формату.
- **OCR как fallback**: если QR поврежден, использовать OCR (EasyOCR/Tesseract) для извлечения текстовых реквизитов.
- **Предобработка изображений**: адаптивная бинаризация, увеличение разрешения, устранение перекосов.

### 4.3. Серверная часть (Ubuntu 24.04)

| Метод | Эндпоинт | Описание |
|-------|----------|----------|
| POST | `/api/v1/receipts/scan` | Прием данных сканирования (QR + изображение) |
| POST | `/api/v1/receipts/verify` | Проверка чека через API ФНС |
| GET | `/api/v1/receipts` | Список чеков с фильтрацией |
| POST | `/api/v1/receipts/upload` | Загрузка чеков в 1С |
| GET | `/api/v1/settings/mapping` | Получение настроек маппинга |
| PUT | `/api/v1/settings/mapping` | Обновление настроек маппинга |
| WS | `/ws/status` | WebSocket для实时 статуса обработки |
**Модуль обработки изображений:**
```python
# Псевдокод пайплайна обработки
def process_receipt_image(image: np.ndarray) -> ReceiptData:
    # 1. Предобработка
    gray = cv2.cvtColor(image, cv2.COLOR_BGR2GRAY)
    thresh = cv2.adaptiveThreshold(gray, 255, ...)
    # 2. Множественное чтение QR
    qr_codes = pyzbar.decode(thresh, symbols=[ZBarSymbol.QRCODE])
    valid_codes = [c for c in qr_codes if is_valid_receipt_qr(c.data)]
    if len(valid_codes) == 1:
        return parse_qr(valid_codes[0].data)
    elif len(valid_codes) > 1:
        raise MultipleReceiptsError("Найдено несколько чеков")
    # 3. Fallback на OCR
    text = easyocr.Reader(['ru']).readtext(thresh)
    return extract_receipt_from_ocr(text)
```
**Модуль проверки в ФНС:**
- Асинхронная отправка запросов через Celery.
- Кэширование результатов проверки (TTL 30 дней).
- Обработка ошибок: таймауты, недоступность API, неверные токены.
- Логирование всех запросов для аудита.
**Модуль интеграции с 1С:**
- Поддержка двух режимов:
  - **Push (1С → сервер)**: 1С запрашивает новые чеки через HTTP-сервис.
  - **Pull (сервер → 1С)**: сервер формирует EnterpriseData и отправляет в 1С.
- Настройка маппинга: сопоставление полей чека с реквизитами документов 1С (Поступление товаров, Авансовый отчет).
- Дедупликация на стороне 1С по ключу (ФН + ФД + ФПД).
### 4.4. База данных (PostgreSQL)
**Схема:**
```sql
-- Чеки
CREATE TABLE receipts (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    qr_data TEXT NOT NULL,
    fn VARCHAR(20) NOT NULL,
    fd VARCHAR(20) NOT NULL,
    fp VARCHAR(20) NOT NULL,
    receipt_date TIMESTAMP NOT NULL,
    total_sum DECIMAL(15,2),
    status VARCHAR(20) DEFAULT 'pending',
    fns_status VARCHAR(20),
    raw_data JSONB,
    created_at TIMESTAMP DEFAULT NOW(),
    UNIQUE(fn, fd, fp)
);
-- Позиции чека
CREATE TABLE receipt_items (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    receipt_id UUID REFERENCES receipts(id),
    name TEXT NOT NULL,
    quantity DECIMAL(10,3),
    price DECIMAL(15,2),
    sum DECIMAL(15,2),
    vat_rate VARCHAR(10),
    vat_sum DECIMAL(15,2)
);
-- Настройки маппинга
CREATE TABLE mapping_settings (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    organization_id UUID,
    source_field VARCHAR(100) NOT NULL,
    target_object VARCHAR(100) NOT NULL,
    target_field VARCHAR(100) NOT NULL,
    transform_rule JSONB,
    is_active BOOLEAN DEFAULT TRUE
);
-- Пользователи
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    username VARCHAR(100) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    organization_id UUID,
    role VARCHAR(20) DEFAULT 'user',
    created_at TIMESTAMP DEFAULT NOW()
);
-- Аудит
CREATE TABLE audit_log (
    id BIGSERIAL PRIMARY KEY,
    user_id UUID REFERENCES users(id),
    action VARCHAR(50) NOT NULL,
    entity_type VARCHAR(50),
    entity_id UUID,
    details JSONB,
    created_at TIMESTAMP DEFAULT NOW()
);
```
**Индексы:**
- `CREATE INDEX idx_receipts_fn_fd_fp ON receipts(fn, fd, fp);`
- `CREATE INDEX idx_receipts_date ON receipts(receipt_date);`
- `CREATE INDEX idx_receipts_status ON receipts(status);`

## 7. Требования к качеству и тестированию
### 7.1. Функциональные требования
- Точность распознавания QR-кода: ≥ 99%.

- **Масштабируемость**: горизонтальное масштабирование API (несколько инстансов за Nginx).
- **Отказоустойчивость**: репликация PostgreSQL, автоматическое восстановление Celery-воркеров.
- **Локализация**: поддержка русского языка, форматы дат и сумм.
### 7.3. Метрики успеха
- Снижение времени ручного ввода чеков на 90%.
- Снижение ошибок ввода на 95%.
- Удовлетворенность пользователей ≥ 4.5/5.

## 8. Рекомендации по использованию существующих решений
### 8.1. Что взять готовым
- **API ФНС**: использовать официальное «Открытое API проверки чека ККТ».
- **EnterpriseData**: применять стандартный формат для интеграции с 1С.
- **Библиотеки**: Pyzbar, OpenCV, EasyOCR — зрелые и проверенные решения.
- **Docker-образы**: использовать официальные образы PostgreSQL, Redis, Nginx.
### 8.2. Что разработать самостоятельно (конкурентные преимущества)
1. **Гибкий маппинг реквизитов**: пользователь может настроить, какие поля чека и в какие реквизиты 1С загружать.
2. **Множественное чтение QR**: защита от ложных срабатываний.
3. **Гибридный OCR**: комбинация QR + OCR для максимальной точности.
4. **Офлайн-режим**: работа без интернета с последующей синхронизацией.
5. **Аналитика в реальном времени**: дашборд с метриками по чекам.
6. **API-first**: возможность интеграции с любыми системами, не только 1С.
### 8.3. Что улучшить по сравнению с конкурентами
- **1С:Сканер чеков**: добавить поддержку не только авансовых отчетов, но и поступлений товаров, расширить маппинг.
- **СБИС**: снизить стоимость, убрать привязку к экосистеме.
- **Entera**: добавить офлайн-режим, улучшить UI/UX.

## 10. Заключение
Данное ТЗ описывает комплексный подход к созданию системы сканирования чеков с интеграцией в 1С. Ключевые принципы:
- **Использование проверенных стандартов**: API ФНС, EnterpriseData, 54-ФЗ.
- **Гибкость и настраиваемость**: маппинг реквизитов, выбор источников.
- **Отказоустойчивость**: офлайн-режим, очереди, репликация.
- **Конкурентные преимущества**: множественное чтение, гибридный OCR, API-first.
ИИ-агент должен следовать этапам, вести документацию и конспектировать все изменения для обеспечения преемственности разработки.
