Отличная идея — это превращает ваше приложение из закрытого B2B-инструмента в **платформу с сетевой моделью**: чем больше людей присылают чеки, тем ценнее база для компаний. Такой механикой пользуются Wildberries (отзывы), Яндекс (пробки) и 2ГИС (актуальность данных). Ниже — полноценный дизайн-документ.
Я назову эту фичу **«Чек-Пул»** — открытая краудсорсинговая база фискальных чеков, которую формируют «залётные» пользователи и потребляют ваши корпоративные клиенты.
---
## 1. Концепция в одном абзаце
Любой человек — не клиент, не сотрудник компании — может **отправить чек** (фото QR, ссылку из приложения ФНС, файл) через публичную веб-форму, Telegram-бота или PWA. За это он получает **баллы / кэшбэк / скидку на подписку**. Ваша система парсит чек, обогащает его гео-данными (регион, город) и категорией отрасли, и складывает в **общий пул**. Компании-клиенты подключаются к пулу и подбирают чеки под свои авансовые отчёты — либо вручную, либо через авто-подбор. Администратор платформы видит всю статистику: какие регионы активны, какие отрасли популярны, как растёт база.
---
## 2. Как привлекать «залётных» пользователей
Ключевая проблема: у обычного человека **нет мотивации** возиться с чужим приложением. Значит, нужно **снизить трение** и **дать понятную выгоду**.
### Каналы привлечения
| Канал | Трение | Мотивация | Ожидаемый поток |
|---|---|---|---|
| **Telegram-бот** `@ymaster_chek_bot` | Минимальное — переслал QR из приложения ФНС | Баллы за каждый чек | Высокий |
| **PWA на `chek.ymaster.ru/public`** | Низкое — открыл, сфоткал QR | Баллы + реферальная ссылка | Средний |
| **Партнёрская программа с бизнесами** | Нулевое — QR-код на кассе АЗС / стройбазы / кафе | Кэшбэк от партнёра | Очень высокий |
| **Реферальная программа** | Низкое — пригласи друга | +50% баллов от его чеков (до N месяцев) | Средний, вирусный |
| **Интеграция в существующие приложения** | Нулевое — таксисты, курьеры уже сдают чеки бухгалтеру | Экономия времени на отчётах | Высокий, но узкий |
| **Геймификация** | — | Рейтинг «Топ-100 охотников за чеками», ачивки по регионам | Средний |
### Мотивация: что реально работает
1. **Баллы за чек.** 1 чек = 1 балл. 100 баллов = 100 ₽ на телефон / на подписку Pro.
2. **Реферальные бонусы.** Пригласил друга — получаешь 30% от его баллов пожизненно.
3. **Партнёрский кэшбэк.** Если чек из партнёрской сети (например, сеть АЗС), пользователь получает 5–10% от суммы чека баллами. Партнёр платит вам за трафик — вы делитесь с пользователем.
4. **Соревнование по регионам.** «Ваш город на 3-м месте по количеству чеков — помогите выйти в лидеры». Публичный лидерборд.
5. **Прямая выгода для тех, кому это нужно.** Таксисты, курьеры, командировочные — им самим нужно сдавать авансовые отчёты. Они сдают чек в бот, а потом **их бухгалтер забирает его из пула** — это уже готовая интеграция с вашим ядром.
### Ключевая фишка: «сдал чек — забрал чек»
Любой, кто сдал чек, получает **бесплатный доступ к своей личной выгрузке** (например, PDF со всеми сданными чеками за месяц). Это уже само по себе полезно — люди ведут учёт личных расходов.

## 3. Модель данных
Добавляем в вашу существующую схему несколько новых таблиц.
### Основные сущности
```sql
-- Публичная база чеков
CREATE TABLE receipt_pool (
    id                  BIGSERIAL PRIMARY KEY,
    -- Фискальные данные
    fiscal_drive        VARCHAR(16) NOT NULL,   -- ФН
    fiscal_doc          VARCHAR(10) NOT NULL,   -- ФД
    fiscal_sign         VARCHAR(20) NOT NULL,   -- ФПД
    purchase_dt         TIMESTAMPTZ NOT NULL,   -- дата покупки
    total_sum           NUMERIC(12,2) NOT NULL,
    -- Продавец
    seller_inn          VARCHAR(12) NOT NULL,
    seller_name         VARCHAR(512),
    seller_okved        VARCHAR(10),
    seller_address      TEXT,
    -- Гео
    region_id           INT REFERENCES regions(id),
    city_id             INT REFERENCES cities(id),
    -- Классификация
    industry_id         INT REFERENCES industries(id),
    -- Источник
    source              VARCHAR(32) NOT NULL,  -- 'telegram_bot','web','pwa','partner','api'
    submitted_by        BIGINT REFERENCES public_users(id),
    raw_payload         JSONB,                 -- сырой ответ API ФНС
    -- Модерация
    status              VARCHAR(16) DEFAULT 'pending', -- pending/verified/rejected/used
    verified_at         TIMESTAMPTZ,
    verification_log    JSONB,
    -- Привязка к компании
    assigned_company_id BIGINT REFERENCES companies(id),
    assigned_at         TIMESTAMPTZ,
    -- Метаданные
    created_at          TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE (fiscal_drive, fiscal_doc, fiscal_sign)
);
CREATE INDEX idx_pool_region      ON receipt_pool (region_id);
CREATE INDEX idx_pool_city        ON receipt_pool (city_id);
CREATE INDEX idx_pool_industry    ON receipt_pool (industry_id);
CREATE INDEX idx_pool_status      ON receipt_pool (status);
CREATE INDEX idx_pool_dt          ON receipt_pool (purchase_dt DESC);
CREATE INDEX idx_pool_assigned    ON receipt_pool (assigned_company_id);
```
### Справочники
```sql
CREATE TABLE regions (
    id      SERIAL PRIMARY KEY,
    code    VARCHAR(8) UNIQUE,      -- код субъекта РФ

CREATE TABLE cities (
    id         SERIAL PRIMARY KEY,
    region_id  INT REFERENCES regions(id),
    name       VARCHAR(128) NOT NULL,

    UNIQUE (region_id, name)

-- Иерархическая (родитель-потомок) классификация отраслей
CREATE TABLE industries (
    id         SERIAL PRIMARY KEY,
    parent_id  INT REFERENCES industries(id),
    code       VARCHAR(16),        -- ОКВЭД или внутренний код
    name       VARCHAR(128) NOT NULL,
    icon       VARCHAR(64),        -- эмодзи или имя иконки
    is_leaf    BOOLEAN DEFAULT FALSE
);
```
### Позиции чека
```sql
CREATE TABLE receipt_items (
    id           BIGSERIAL PRIMARY KEY,
    receipt_id   BIGINT REFERENCES receipt_pool(id) ON DELETE CASCADE,
    name_raw     TEXT NOT NULL,
    name_norm    TEXT,             -- нормализованное имя
    qty          NUMERIC(10,3),
    price        NUMERIC(12,2),
    sum          NUMERIC(12,2),
    category_id  INT REFERENCES categories(id),
    industry_id  INT REFERENCES industries(id)
);
CREATE TABLE categories (
    id         SERIAL PRIMARY KEY,
    parent_id  INT REFERENCES categories(id),
    name       VARCHAR(128) NOT NULL,
    keywords   TEXT[]              -- ['молоко','кефир','йогурт']
);
```
### Пользователи пула
```sql
CREATE TABLE public_users (
    id              BIGSERIAL PRIMARY KEY,
    -- Анонимный идентификатор; ФИО не храним
    tg_user_id      BIGINT UNIQUE,     -- для Telegram-бота
    email           VARCHAR(256),       -- опционально, для веб-формы
    phone_hash      VARCHAR(64),        -- SHA-256, если дал телефон
    -- Геймификация
    points          INT DEFAULT 0,
    referral_code   VARCHAR(12) UNIQUE,
    referred_by     BIGINT REFERENCES public_users(id),
    -- Модерация
    trust_level     SMALLINT DEFAULT 0, -- 0 новый, 1 проверенный, 2 доверенный
    is_blocked      BOOLEAN DEFAULT FALSE,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);
CREATE TABLE points_ledger (
    id          BIGSERIAL PRIMARY KEY,
    user_id     BIGINT REFERENCES public_users(id),
    delta       INT NOT NULL,          -- +/- баллы
    reason      VARCHAR(64) NOT NULL,  -- 'receipt', 'referral', 'cashback'
    ref_id      BIGINT,                 -- ссылка на receipt_pool.id
    created_at  TIMESTAMPTZ DEFAULT NOW()
);
```

## 4. Пайплайн обработки чека
Это самая важная часть. От загрузки до попадания в пул — 6 шагов, автоматических.
```
[Пользователь] → [QR/фото/ссылка] → [Парсер] → [Обогащение] → [Классификация] → [Верификация] → [Пул]
```
### Шаг 1. Приём
- **Telegram-бот**: пользователь пересылает текст или фото QR. Бот отвечает через 1–2 секунды.
- **Веб-форма**: drag&drop фото чека или вставка ссылки из приложения ФНС.
- **PWA**: камера → распознавание QR в браузере.
На входе — извлекаем **QR-строку** или ссылку на чек. Это делается через:
- `pyzbar` / `opencv` для QR с фото (уже используется в вашем Dockerfile — там есть OpenCV).
- Парсинг ссылки вида `https://consumer.1-ofd.ru/...` — извлекаем ФД и ФПД.
### Шаг 2. Получение фискальных данных
Запрашиваем у **API ФНС** (`https://irkkt-mobile.nalog.ru:8888/v2/ticket`) или ОФД. У вас уже реализованы эти источники — переиспользуем.
Получаем JSON с полной информацией: продавец, ИНН, дата, сумма, позиции.
### Шаг 3. Дедупликация
Проверяем по `UNIQUE (fiscal_drive, fiscal_doc, fiscal_sign)`. Если чек уже в базе — отвечаем пользователю «этот чек уже есть, спасибо!» и начисляем половинные баллы (чтобы не отбить желание).
### Шаг 4. Гео-обогащение
Это критично для вашей задачи.
```
ИНН продавца → Checko.ru (у вас уже интегрирован) → ЕГРЮЛ → юридический адрес → регион + город
```
Проблема: **юридический адрес ≠ город покупки**. Например, сеть «Магнит» зарегистрирована в Краснодаре, а покупка сделана в Москве. Решение:
1. Если в чеке есть **адрес места расчёта** (в новых ФФД 1.05+ он есть) — берём его. Это самый точный вариант.
2. Если нет — берём адрес из **ККТ** (в чеке часто указывается адрес установки кассы).
3. Если и этого нет — используем юр. адрес продавца как fallback, но помечаем флагом `geo_accuracy = 'low'`.
Реализация: отдельная таблица `regions`/`cities` с маппингом по ФИАС. Можно использовать открытый реестр [ФИАС / ГАР](https://fias.nalog.ru/) — 1 раз в месяц обновляете, всё локально.
### Шаг 5. Классификация по отраслям
Три уровня точности:
**Уровень 1 — по ОКВЭД продавца.** Самый простой. `Checko.ru` отдаёт ОКВЭД. Плюс: не требует ML. Минус: продавец может быть ООО с 20 ОКВЭД, и все чеки попадут в один.
**Уровень 2 — по названию магазина.** Словарь: «Пятёрочка» → Продукты, «Леруа» → Стройматериалы, «Аптека» → Медицина. Заводим таблицу `seller_industry_map (inn_or_name → industry_id)`.
**Уровень 3 — по позициям чека (ML).** Тут уже интересно:
- Собираем обучающий корпус из уже размеченных чеков (можно вручную разметить 5–10 тыс. позиций).
- Обучаем простой классификатор на **FastText** или **RuBERT-tiny** — он отлично работает с русскими названиями товаров. Модель на 30 МБ, крутится на CPU за 2 мс.
- Категории: Продукты, Стройматериалы, Бензин, Аптека, Кафе, Одежда, Техника, Хозтовары, Канцелярия и т.д.
**Практичная схема**: уровень 1 + 2 закрывают 80% случаев, уровень 3 включаем для сложных. Такой пайплайн можно запустить **без ML** за выходные, а модель добавить позже.
### Шаг 6. Верификация
- Проверка через API ФНС (уже сделана на шаге 2).
- Проверка на аномалии: сумма больше 500 000 ₽ для физлица — флаг, ручная проверка.
- Проверка пользователя: `trust_level = 0` → первые 5 чеков идут с задержкой, потом автоматом.
- Антифрод: см. раздел 10.
Итог: статус `verified`, запись падает в пул, пользователю начисляются баллы.

## 6. Личный кабинет «залётного» пользователя
Минималистичный, но с «крючками» вовлечения. На `chek.ymaster.ru/my`:
- **Счётчик баллов** и ближайшая цель («До 500 ₽ — 120 баллов»).
- **История чеков** (только свои, с возможностью скачать PDF).
- **Реферальная ссылка** с копированием в один клик.
- **Лидерборд**: топ-10 по вашему городу за месяц.
- **Ачивки**: «Собрал 50 чеков», «Первый чек из Леруа», «Исследователь: 3 разных отрасли».
- **Оффер для тех, кому надо**: «Ваш бухгалтер может забрать все ваши чеки одним файлом. Отправьте ему ссылку — это бесплатно».

## 7. Админ-панель оператора (то, что видите вы)
Ключевой раздел для вас. Отдельная страница `/admin/pool`:
### Дашборд
- **Счётчики**: всего чеков в пуле, за сегодня, за неделю, активных пользователей.
- **Карта России** с тепловой раскраской по количеству чеков в регионе.
- **Топ-10 городов** по количеству чеков.
- **Диаграмма по отраслям** (пай).
- **Средний чек** по каждой отрасли.
### Раздел «География»
Таблица по регионам: регион → города → количество чеков → средний чек → топ-отрасль.
Пример:
| Регион | Город | Чеков | Средний чек | Топ-отрасль |
|---|---|---|---|---|
| Москва | Москва | 12 340 | 1 240 ₽ | Продукты (54%) |
| Москва | Зеленоград | 210 | 980 ₽ | Стройматериалы (41%) |
| МО | Химки | 890 | 1 100 ₽ | Продукты (62%) |
| СПб | Санкт-Петербург | 4 210 | 1 380 ₽ | Кафе (48%) |
С возможностью выгрузить в Excel/CSV.
### Раздел «Отрасли»
- Всего чеков в отрасли.
- Распределение по регионам.
- Топ-продавцов (ИНН + название).
- Средний чек.
- Динамика за 30/90/365 дней.
### Раздел «Пользователи пула»
- Список пользователей с рейтингом доверия.
- Модерация: заблокировать, повысить trust_level.
- Подозрительные паттерны: один пользователь залил 200 чеков из одного магазина за час.
### Раздел «Качество базы»
- Дубликаты (по ФД+ФПД — уже отсеиваются, но могут быть ложные).
- Чеки без гео-привязки.
- Чеки без отрасли.
- Очередь ручной разметки.
### Модерация
- Кнопка «Одобрить» / «Отклонить» для подозрительных.
- Массовые операции.
- Экспорт отчёта по модерации.

## 8. Как компании-клиенты используют пул
Это вторая сторона монетизации. В вашем существующем приложении добавляем раздел «Подбор чеков из пула».
### Сценарий A. Ручной подбор
Бухгалтер создаёт авансовый отчёт. Открывает «Подбор из пула», фильтрует:
- период (дата чека),
- регион/город,
- отрасль,
- сумма от/до,
- продавец (ИНН).
Видит список подходящих чеков, выбирает нужные, они «привязываются» к компании (`assigned_company_id`), и попадают в авансовый отчёт.
### Сценарий B. Авто-подбор
При создании АО на сумму 5 000 ₽ система сама предлагает 3–5 чеков из пула, суммарно дающих 5 000 ₽ в пределах ±5%. Бухгалтер выбирает подходящий набор.
### Сценарий C. Импорт «своих» сотрудников
Сотрудник компании сдал чек через публичный бот. Система видит, что его телефон совпадает с телефоном сотрудника в компании → чек автоматически привязывается к компании, а не уходит в общий пул.
### Экономика для компании
- **Подписка на пул**: 5 000 ₽/мес за доступ к фильтрам и выгрузке 100 чеков.
- **Pay-per-receipt**: 50 ₽ за чек.
- **Премиум-поиск**: 200 ₽ за чек с точной гео-привязкой и категорией.

## 9. Юридическая часть (152-ФЗ и оферта)
Это **критично**, нельзя пропустить.
### Что хранить и что не хранить
- ❌ **Не храним** ФИО покупателя, телефон, email в чеке — эти данные в чеке обычно и не приходят.
- ✅ Храним только фискальные данные (ФН, ФД, ФПД), ИНН продавца, сумму, дату, позиции.
- ✅ Для идентификации пользователя пула — только анонимный ID + TG-хэш или хэш телефона.
- ✅ Если пользователь даёт email — только для уведомлений, с явным согласием.
### Оферта пользователя пула
Текст-минимум, который должен быть на форме загрузки:
> Отправляя чек, вы подтверждаете, что он ваш, и передаёте его фискальные данные (ФН, ФД, ФПД, ИНН продавца, сумма, состав) в публичную базу «Ямастер Чек-Пул». Персональные данные третьих лиц в базу не попадают. Вы можете отозвать согласие, написав на support@…, при этом ваши баллы сгорают.
### Согласие с офертой
Чек-бокс на форме + сохранение факта согласия в БД (`user_id`, `version`, `timestamp`, `ip_hash`).
### Антифрод
- Один пользователь — не больше 50 чеков в сутки.
- Нельзя загрузить чек из магазина, в котором за последний час уже загружено >100 чеков (признак скрипта).
- Верификация через SMS для вывода баллов.
- ML-детектор аномалий: слишком ровные суммы, слишком регулярные интервалы.

## 2. Реферальная механика
### Как это работает
1. При регистрации пользователь автоматически получает **уникальный код** (например, `YM-A7K9X2`) и ссылку `https://chek.ymaster.ru/r/A7K9X2`.
2. Ссылку можно отправить кому угодно — друзьям, в чат, в соцсети.
3. Когда новый человек переходит по ссылке и **регистрируется**, он привязывается к пригласившему.
4. Пригласивший получает бонус за **действия** приглашённого, не за факт регистрации.
### Схема вознаграждения (защита от накрутки)
Это ключевая часть. Наивная схема «за каждого приглашённого +100 баллов» — ломается за один день: бот создаёт 1000 аккаунтов, получает 100 000 баллов. Поэтому используем **пороговую схему с задержкой**.
**Уровни вознаграждения реферера:**
| Событие у приглашённого | Бонус рефереру | Задержка |
|---|---|---|
| Регистрация по ссылке | **0 баллов** | — |
| Подтверждён email | +5 баллов | 24 часа |
| Первый **верифицированный** чек ≥ 100 ₽ | +20 баллов | 7 дней |
| 5-й верифицированный чек | +50 баллов | 14 дней |
| 20-й верифицированный чек, trust_level ≥ 1 | +150 баллов | 30 дней |
| 50-й верифицированный чек, trust_level ≥ 2 | +500 баллов | 60 дней |
**Почему так:**
- Реферальный бонус приходит **не сразу**, а через задержку — за это время антифрод видит аномалии, а мошенник теряет мотивацию (ему нужно ждать).
- Бонус привязан к **качественному действию** приглашённого, а не к регистрации.
- Максимальный бонус — только после подтверждённого доверия (trust_level 2).
**Дополнительный «хвост» (lifetime):**
- После 20-го чека приглашённого реферер получает **5% от баллов, которые зарабатывает приглашённый** — пожизненно, но с потолком 200 баллов/мес на одного реферала.
- Это создаёт долгосрочную мотивацию, но не даёт мгновенного кэша.
### Ограничения реферальной сети
- **Максимум 50 активных рефералов на пользователя** (первый уровень).
- **Только один уровень** реферальной сети. Никаких «многоуровневых» схем — это сразу превращается в пирамиду и является нарушением.
- **Один реферал = один аккаунт**. Если приглашённый создаст второй — он не сможет привязаться к тому же рефереру (см. антифрод).

## 3. Антифрод: архитектура защиты
Пять независимых слоёв. Даже если один слой обходится, остальные ловят.
```
[Слой 1] Fingerprint       → уникальность устройства
[Слой 2] Network           → IP, subnet, ASN, VPN-детект
[Слой 3] Behavioral        → поведение на сайте
[Слой 4] Graph             → связи между аккаунтами
[Слой 5] Business rules    → правила по чекам и баллам
```
Каждый слой пишет сигналы в общий **журнал событий** (`fraud_signals`), а решающий модуль агрегирует их в **risk_score** для каждого пользователя.
### Слой 1. Device fingerprint
Собираем при регистрации и каждом входе. Библиотека — **FingerprintJS** (open source версия, MIT) или собственный скрипт.
Что собираем:
- **Canvas fingerprint** — рендер скрытого `<canvas>` с текстом и фигурами; хэш результата уникален для GPU+драйвера.
- **WebGL fingerprint** — рендерер, vendor, поддерживаемые расширения.
- **Audio fingerprint** — осциллятор, обработанный `AudioContext`; хэш результата.
- **Список шрифтов** — через `document.fonts.check()`.
- **Разрешение экрана, pixel ratio, глубина цвета**.
- **Часовой пояс, язык, `navigator.languages`**.
- **Платформа, userAgent, hardwareConcurrency, deviceMemory**.
- **Список плагинов** (в старых браузерах).
- **Touch support, Do Not Track, cookies enabled**.
Итог: **Visitor ID** — 32-символьный хэш, стабильный на 90+% между сессиями одного устройства.
```sql
CREATE TABLE device_fingerprints (
    id           BIGSERIAL PRIMARY KEY,
    visitor_id   VARCHAR(64) NOT NULL,   -- FingerprintJS ID
    user_id      BIGINT REFERENCES public_users(id),
    components   JSONB NOT NULL,          -- все собранные компоненты
    first_seen   TIMESTAMPTZ DEFAULT NOW(),
    last_seen    TIMESTAMPTZ DEFAULT NOW(),
    seen_count   INT DEFAULT 1,
    is_suspicious BOOLEAN DEFAULT FALSE
);
CREATE INDEX idx_fp_visitor ON device_fingerprints (visitor_id);
CREATE INDEX idx_fp_user    ON device_fingerprints (user_id);
```
**Ключевой момент**: если один `visitor_id` встречается на **двух и более аккаунтах** — это **красный флаг**. Автоматически:
- Все аккаунты помечаются как связанные.
- Реферальные бонусы замораживаются.
- Админу приходит сигнал `MULTI_ACCOUNT_DEVICE`.
### Слой 2. Network
```sql
CREATE TABLE ip_log (
    id           BIGSERIAL PRIMARY KEY,
    user_id      BIGINT REFERENCES public_users(id),
    ip_address   INET NOT NULL,
    ip_subnet    CIDR,                   -- /24 для IPv4
    asn          INT,
    asn_org      VARCHAR(256),
    country      VARCHAR(2),
    region       VARCHAR(128),
    city         VARCHAR(128),
    is_datacenter BOOLEAN DEFAULT FALSE,
    is_vpn        BOOLEAN DEFAULT FALSE,
    is_tor        BOOLEAN DEFAULT FALSE,
    user_agent   TEXT,
    created_at   TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_ip_user      ON ip_log (user_id);
CREATE INDEX idx_ip_subnet    ON ip_log (ip_subnet);
CREATE INDEX idx_ip_created   ON ip_log (created_at DESC);
```
Что детектируем:
- **Datacenter IP** (MaxMind, IPinfo, локальные базы) — реальный пользователь с домашнего интернета не может иметь IP из Amazon AWS. Если 10 регистраций с одного датацентра — это скрипт.
- **VPN/Proxy/Tor** — пометка, но не блокировка. Некоторые честные пользователи сидят через VPN.
- **Subnet clustering** — если с одной подсети `/24` регистрируется 5+ аккаунтов за сутки — сигнал `SUBNET_CLUSTER`.
- **ASN clustering** — оператор мобильной связи (МТС, Билайн) — норма. Один ASN хостинга — подозрительно.
- **Гео-аномалия** — вход из Москвы и из Новосибирска с разницей 10 минут — невозможно физически.
### Слой 3. Behavioral
Что анализируем:
**Скорость действий:**
- Время от открытия страницы регистрации до submit. Если < 5 секунд — бот.
- Время от регистрации до первого чека. Реальный пользователь — минимум 30 секунд (надо открыть приложение ФНС и получить QR).
- Интервалы между чеками. Идеально ровные интервалы (каждые 60.0 сек) — скрипт.
**Поведение на странице:**
- Движения мыши (через `mousemove`), клики, фокусы.
- Заполнение форм: если все поля заполнены за один тик — автозаполнение ботом.
- Honeypot-поля: скрытые `<input>`, которые реальный пользователь не видит. Если они заполнены — бот.
**Загрузка чеков:**
- Тип файла: реальные фото с камеры телефона имеют EXIF-метаданные (модель, дата, GPS). Скриншоты и сгенерированные файлы — нет.
- Размер фото: чек с камеры телефона — 1–5 МБ. Скриншот — 50–300 КБ. Программная генерация — часто круглые числа.
- Однотипность: 50 чеков с одинаковым углом, яркостью, размытием — сканы одного и того же чека или сгенерированные.
```sql
CREATE TABLE behavioral_events (
    id          BIGSERIAL PRIMARY KEY,
    user_id     BIGINT REFERENCES public_users(id),
    event_type  VARCHAR(64) NOT NULL,   -- 'signup','first_receipt','receipt_upload','login'
    duration_ms INT,                    -- время действия
    mouse_moves INT DEFAULT 0,
    key_presses INT DEFAULT 0,
    honeypot_filled BOOLEAN DEFAULT FALSE,
    extra       JSONB,
    created_at  TIMESTAMPTZ DEFAULT NOW()
);
```
### Слой 4. Graph (связи между аккаунтами)
Это самый мощный слой для детекта реферальных «схем». Строим граф:
```
Узлы:    user, device_fingerprint, ip_subnet, email_domain, phone, payment_method
Рёбра:   связаны, если используют один и тот же узел
```
**Пример**: пользователь A зарегистрировался с `visitor_id = X`. Через час пользователь B пришёл по реферальной ссылке от A и зарегистрировался с тем же `visitor_id = X`. **Это один человек с двумя аккаунтами**. Связь мгновенно детектируется.
Реализация: PostgreSQL + рекурсивные CTE, либо графовая БД (Neo4j, но это оверкилл). Для старта хватит SQL.
```sql
-- Найти все аккаунты, связанные с данным через device fingerprint
WITH RECURSIVE cluster AS (
    SELECT user_id, visitor_id
    FROM device_fingerprints
    WHERE visitor_id IN (
        SELECT visitor_id FROM device_fingerprints WHERE user_id = $1
    )
    UNION
    SELECT df.user_id, df.visitor_id
    FROM device_fingerprints df
    JOIN cluster c ON df.visitor_id = c.visitor_id
)
SELECT DISTINCT user_id FROM cluster;
```
Полученный кластер — **«подозрительная группа»**. Если в ней есть реферальные связи — это автоматический сигнал `REFERRAL_FRAUD`.
Дополнительно:
- **Email-домены**: 10 аккаунтов с `@mailinator.com` — сигнал.
- **Схожие email**: `ivan.petrov+1@`, `ivan.petrov+2@` — сигнал.
- **Схожие имена**: «Иван Петров», «Иван Петрович», «Ivan Petrov» — сигнал.
- **Один платёжный реквизит** на нескольких аккаунтах при выводе — 100% мультиаккаунт.
### Слой 5. Business rules
Простые, но эффективные правила. Проверяются при каждом действии:
| Правило | Сигнал | Действие |
|---|---|---|
| > 5 регистраций с одной `/24` за сутки | `SUBNET_CLUSTER` | Ручная проверка |
| > 3 аккаунта с одного `visitor_id` | `MULTI_ACCOUNT_DEVICE` | Блокировка всех |
| Реферал зарегистрировался < 60 сек после перехода по ссылке | `FAST_REFERRAL` | Бонус заморожен |
| Реферал и реферер с одной `/24` в момент регистрации | `SAME_SUBNET_REFERRAL` | Бонус отменён |
| 20+ чеков за час от одного пользователя | `RECEIPT_FLOOD` | Rate limit, ручная проверка |
| 5+ чеков с одинаковым `total_sum` подряд | `SUSPICIOUS_PATTERN` | Ручная проверка |
| Чек загружен 3 раза с разных аккаунтов | `DUPLICATE_RECEIPT` | Дедупликация, флаг |
| Вывод баллов на новый телефон без истории | `WITHDRAWAL_FRESH` | SMS-подтверждение |
| Все чеки за неделю — из одной отрасли, ровные суммы | `BOT_PATTERN` | Ручная проверка |

## 4. Risk score и уровни доверия
Каждый пользователь имеет **risk_score** (0–100). Считается как сумма весов всех сигналов.
```sql
CREATE TABLE user_risk (
    user_id      BIGINT PRIMARY KEY REFERENCES public_users(id),
    risk_score   SMALLINT DEFAULT 0,
    trust_level  SMALLINT DEFAULT 0,   -- 0=новый, 1=проверенный, 2=доверенный, 3=партнёр
    last_calc_at TIMESTAMPTZ,
    flags        TEXT[] DEFAULT '{}'
);
```
**Веса сигналов:**
| Сигнал | Вес |
|---|---|
| `MULTI_ACCOUNT_DEVICE` | +60 |
| `REFERRAL_FRAUD` | +50 |
| `SAME_SUBNET_REFERRAL` | +40 |
| `BOT_PATTERN` | +40 |
| `RECEIPT_FLOOD` | +30 |
| `VPN_OR_PROXY` | +15 |
| `DATACENTER_IP` | +25 |
| `SUBNET_CLUSTER` | +20 |
| `FAST_REFERRAL` | +10 |
| `NEW_EMAIL_DOMAIN` | +5 |
**Уровни и последствия:**
| Risk score | Trust level | Что разрешено |
|---|---|---|
| 0–20 | **0 — новый** | Загрузка чеков, задержка баллов 24 ч, лимит 10 чеков/сутки |
| 21–40 | **1 — проверенный** | Лимит 50 чеков/сутки, баллы зачисляются сразу |
| 41–70 | **2 — доверенный** | Вывод баллов, повышенные лимиты, реферальные бонусы |
| 71+ | **⚠ Карантин** | Все действия заморожены, требуется ручная проверка |
| 100 | **🚫 Заблокирован** | Аккаунт заблокирован, баллы аннулированы |
**Как trust_level растёт:**
- Автоматически при накоплении верифицированных чеков + снижении risk_score.
- Вручную админом (при разборе сигнала).

## 5. Система сигналов и алертов
Каждый сигнал — запись в БД + опциональное уведомление админу.
```sql
CREATE TABLE fraud_signals (
    id           BIGSERIAL PRIMARY KEY,
    user_id      BIGINT REFERENCES public_users(id),
    signal_type  VARCHAR(64) NOT NULL,
    severity     SMALLINT NOT NULL,     -- 1=info, 2=warning, 3=critical
    weight       SMALLINT NOT NULL,     -- вклад в risk_score
    details      JSONB,                 -- контекст: IP, device, время
    related_users BIGINT[],             -- если замешаны другие
    status       VARCHAR(16) DEFAULT 'new', -- new/reviewing/resolved/false_positive
    resolved_by  BIGINT,                -- админ
    resolved_at  TIMESTAMPTZ,
    created_at   TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_signals_user   ON fraud_signals (user_id);
CREATE INDEX idx_signals_status ON fraud_signals (status, severity DESC);
CREATE INDEX idx_signals_type   ON fraud_signals (signal_type);
```
### Уведомления админу
Три канала (все опциональны, настраиваются):
1. **Веб-интерфейс**: раздел `/admin/fraud` — лента сигналов, фильтры, действия.
2. **Email**: раз в день дайджест критичных сигналов на `admin@ymaster.ru` (можно отключить).
3. **Webhook**: на внешний сервис (n8n, Make,自定义) — для интеграции с чем угодно.
Уведомляем **только о severity ≥ 2**, иначе админ утонет.

## 7. Схемы мошенничества и как их ломает система
### Схема 1. «Ферма аккаунтов»
Пользователь создаёт 50 аккаунтов через скрипт, каждый приглашает «друг друга», копит баллы.
**Детект:**
- Все 50 аккаунтов с одного `visitor_id` → `MULTI_ACCOUNT_DEVICE`.
- Регистрации с интервалом < 60 сек → `BOT_PATTERN`.
- Подсеть одна → `SUBNET_CLUSTER`.
**Результат:** блокировка всех 50, аннулирование баллов, IP в чёрный список.
### Схема 2. «Взаимные рефералы»
Группа из 10 человек создаёт 10 аккаунтов и каждый приглашает остальных 9 (циклическая схема).
**Детект:**
- Граф связей образует **плотный кластер** (10 узлов, 45 рёбер).
- Нормальный реферальный граф — **дерево** (звезда), а не полный граф.
- Алгоритм: коэффициент кластеризации. Если > 0.7 — сигнал `REFERRAL_CYCLE`.
**Результат:** все бонусы аннулируются, все аккаунты — на ручную проверку.
### Схема 3. «Накрутка чеками»
Пользователь загружает один и тот же чек с разных аккаунтов или генерирует чеки с вымышленными ФД+ФПД.
**Детект:**
- Дедупликация по `(fiscal_drive, fiscal_doc, fiscal_sign)` — дубликаты отсеиваются на входе.
- Проверка через API ФНС — если чек не найден, отклоняется.
- Аномалии: 30 чеков за час, ровные суммы, одинаковые интервалы.
**Результат:** `RECEIPT_FLOOD`, `BOT_PATTERN`, rate limit, карантин.
### Схема 4. «Реферальный трюк с VPN»
Пользователь создаёт второй аккаунт через VPN, приглашает «себя», получает бонус.
**Детект:**
- VPN-детект → +15 к risk_score (не блокировка, но флаг).
- Device fingerprint совпадает → `MULTI_ACCOUNT_DEVICE`.
- Behavioral: схожие движения мыши, одинаковое время сессии, одинаковые часовые пояса.
**Результат:** бонус отменяется, аккаунт-реферал блокируется, основной — в карантин.
### Схема 5. «Социальная инженерия»
Пользователь просит друзей зарегистрироваться и сдать чеки «для него», не раскрывая, что это его реферальная программа.
**Детект:** сложно. Помогает:
- Лимит на количество рефералов (50).
- Бонус начисляется только за **реальные чеки реферала** — если друг не сдаёт чеки, бонуса нет.
- Lifetime-хвост 5% с потолком 200 баллов/мес — ограничивает масштаб.
- Публичное описание программы — если пользователь врал, это уже моральный вопрос, но не технический. Юридически: в оферте прописать, что реферал должен быть уведомлён.

### Middleware для сбора данных
FastAPI middleware перехватывает каждый запрос:
```python
@app.middleware("http")
async def collect_request_context(request: Request, call_next):
    ctx = {
        "ip": get_client_ip(request),
        "user_agent": request.headers.get("user-agent"),
        "visitor_id": request.headers.get("x-visitor-id"),  # из JS
        "accept_lang": request.headers.get("accept-language"),
        "timestamp": datetime.utcnow(),
    }
    request.state.ctx = ctx
    response = await call_next(request)
    return response
```
### Асинхронный анализ
Сигналы и risk_score считаются **не в момент запроса**, а отложенно, через ARQ (async Redis queue):
```python
@arq.job
async def analyze_user(ctx: dict, user_id: int, trigger: str):
    # 1. Загрузить все сигналы пользователя
    # 2. Пересчитать risk_score
    # 3. Обновить trust_level
    # 4. Если critical — уведомить админа
    # 5. Если risk_score > 70 — поставить карантин
    ...
```
Задачи ставятся в очередь при:
- регистрации,
- загрузке чека,
- переходе по реферальной ссылке,
- запросе вывода баллов,
- раз в сутки — полный пересчёт.
### FingerprintJS на фронте
В `base.html`:
```html
<script>
  import FingerprintJS from '@fingerprintjs/fingerprintjs';
  const fp = await FingerprintJS.load();
  const result = await fp.get();
  const visitorId = result.visitorId;
  // Сохраняем в cookie на 1 год
  document.cookie = `ym_vid=${visitorId}; max-age=31536000; path=/; SameSite=Lax`;
  // Добавляем в заголовки всех fetch
  const origFetch = window.fetch;
  window.fetch = function (...args) {
    const [url, opts = {}] = args;
    opts.headers = { ...opts.headers, 'X-Visitor-Id': visitorId };
    return origFetch.call(this, url, opts);
  };
</script>
```
### Honeypot-поля
В форму регистрации:
```html
<form method="post" action="/auth/signup">
  <input type="text" name="email" required>
  <input type="password" name="password" required>
  <!-- Honeypot: скрыт через CSS, бот заполнит -->
  <div style="position:absolute;left:-9999px" aria-hidden="true">
    <input type="text" name="website" tabindex="-1" autocomplete="off">
  </div>
  <button type="submit">Создать аккаунт</button>
</form>
```
На бэке:
```python
if form.get("website"):
    # Бот. Молча создаём «теневой» аккаунт, который ничего не сможет.
    return create_honeypot_user(form)
```
**Важно**: не отвечаем ошибкой — бот не должен понять, что его раскусили. Просто создаём «мёртвый» аккаунт, который никогда не получит баллы.

## 9. Юридические аспекты (152-ФЗ)
Device fingerprint, IP, поведение — это всё **персональные данные** по 152-ФЗ (косвенно идентифицирующие). Нужно:
1. **Согласие в оферте** — отдельным пунктом: «Мы собираем технические данные об устройстве и подключении для защиты от мошенничества».
2. **Cookie-баннер** — с настройками (аналитические / необходимые / антифрод).
3. **Хранение** — IP и fingerprint хранятся **не дольше 12 месяцев**, потом анонимизируются (обрезаем последний октет IP, хэшируем fingerprint).
4. **Доступ** — только admin и antifraud-модуль.
5. **Уведомление в РКН** — стандартное, у вас уже должно быть.
В оферте пользователя пула отдельный раздел:
> **6. Противодействие злоупотреблениям**
> 6.1. Сервис анализирует технические характеристики устройства, IP-адрес и поведение пользователя для предотвращения создания множественных аккаунтов и накрутки баллов.
> 6.2. При выявлении признаков злоупотребления баллы могут быть аннулированы, а аккаунт — заблокирован без права на восстановление.
> 6.3. Пользователь вправе запросить информацию о своём risk_score, написав на support@…

## 10. Метрики антифрода
Отслеживайте с первого дня:
| Метрика | Целевое значение |
|---|---|
| Доля аккаунтов с risk_score > 40 | < 5% |
| Ложноположительные срабатывания | < 2% |
| Средний risk_score по базе | < 20 |
| Время реакции на critical-сигнал | < 1 час |
| Доля реферальных бонусов, отменённых антифродом | 10–20% (норма) |
| Количество кластеров мультиаккаунтов в неделю | 5–50 |
Если доля отменённых бонусов **> 40%** — вы слишком агрессивны, страдают честные. Если **< 5%** — вы не ловите мошенников.

## 💎 Итог
**Ядро системы — не запрет, а ограничение скорости выгоды.** Мошенник должен получать баллы **медленнее**, чем его поймает антифрод. Задержка бонусов, пороговые триггеры, привязка к trust_level — всё это делает накрутку **экономически бессмысленной**: время, потраченное на ферму аккаунтов, не окупается 200 баллами.
**Ключевые принципы:**
1. **Не наказывать за регистрацию** — только за попытку вывода или накрутки.
2. **Не блокировать сразу** — карантин + ручная проверка для пограничных случаев.
3. **Логировать всё** — каждое действие, каждый сигнал, каждое решение.
4. **Прозрачность для пользователя** — если он не мошенник, он должен иметь возможность оспорить блокировку.
5. **Многослойность** — fingerprint + IP + поведение + граф + правила. Даже если один слой обойдут, четыре других сработают.
