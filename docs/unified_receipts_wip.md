# Единая запись чека: экспериментальная миграция на копии

**Не готово к эксплуатации.** Реестр и Чек-Пул по-прежнему читают и изменяют
прежние таблицы. Прототип не синхронизирует новые документы после создания
снимка, не переключает API и не является миграцией работающего сервера.
Не подменяйте им рабочую базу и не используйте его результат для учёта.

## Что сделано

`python -m qa.migrate_receipt_copy --source <sqlite-источник> --output <новый-файл>`
создаёт отдельную копию средствами SQLite backup и добавляет в неё:

- единые фискальные тройки и согласованные дату, сумму и операцию;
- ссылки на исходные записи реестра и пула, а также на их позиции;
- таблицу исключительного владения компании с единственной строкой на чек;
  старое владение переносится только если оно однозначно, конфликтующие
  назначения остаются без выбранного владельца и подсчитываются отдельно;
- пометки неоднозначности: дата (1), сумма (2), операция (4), расхождение
  компаний (8). Неоднозначные общие реквизиты не выбираются автоматически;
- подсчёт записей и позиций без связи из-за отсутствующих реквизитов.

Исходные таблицы, позиции, частные поля, назначения, баллы и история донора
не удаляются и не перезаписываются. Заданный файл результата должен не
существовать; исходный файл открывается только для чтения. Команда проверяет
целостность копии, связи и согласованность общих полей. При ошибке созданная
копия удаляется. PostgreSQL не поддерживается этим прототипом.

`qa/unified_receipt_preview.py` содержит экспериментальные внутренние функции
чтения отдельных представлений компании и донора. `qa/unified_claims.py` —
прототип транзакционного закрепления чека из пула без создания второго чека и
без обращения к ФНС; выполняет проверку роли, назначения, лимита, актуальности
снимка и использует общий замок фискальной тройки. Вызывающий обязан передать
аутентифицированного пользователя и завершить транзакцию commit/rollback.
Это не маршруты API и не замена существующим проверкам доступа. Любые изменения старых таблиц после
миграции делают снимок устаревшим; повторный запуск на том же выходном файле
не поддерживается.

## Проверено и остаётся сделать

На синтетической копии с тестовыми аккаунтами запускалось существующее
приложение; проверены права компании и донора, позиции и баллы. Это проверка
совместимости старых маршрутов с добавленными таблицами, **не проверка работы
приложения на единой модели**. Конфликты суммы и принадлежности специально
создавались в тестах; реальные базы не исследовались. Два SQLite-потока
соревновались за один чек и за квоту одной компании: при повторной проверке
одна операция выигрывает, другая получает отказ, баллы донора остаются прежними.
Это не проверка транзакций PostgreSQL и не переключение действующего сервиса.

До завершения нужны транзакционная синхронизация и переключение всех путей
приёма, подбора, редактирования и удаления; миграция и откат для SQLite и
PostgreSQL; разрешение исторических конфликтов без утраты данных и с защитой
прав; повторная сквозная проверка баллов, истории, квот и интеграций на копии
реальных данных. Доказательство успешной проверки ФНС нельзя придумывать по
статусу ручной модерации.
