# Единый фискальный документ

Цель: один фискальный чек хранится один раз в каноническом слое, а компании
видят только свои чеки. Перенос между компаниями меняет владельца, а не
создаёт второй чек. Старые таблицы `receipts` и `pool_receipts` сохранены как
совместимые проекции для действующих API, 1С, баллов и истории Чек-Пула.

## Канонические таблицы

- `unified_documents` — одна запись на полную фискальную тройку ФН+ФД+ФП
  (`identity_key`, UNIQUE). Неполные исторические тройки не склеиваются.
- `unified_items` — единый набор позиций документа.
- `unified_ownership` — одна строка владения компанией (`company_id` может быть
  NULL для общего пула/платформы) и автор сотрудника (`created_by`). Внешних
  ключей БД на `companies`/`users` нет намеренно: после отката на версию без
  единого реестра старый код должен свободно удалять компании (см. ниже).
- `unified_origins` — ссылки на совместимые проекции `registry` и `pool`.
  Сырые ответы ФНС, персональные данные, баллы и согласия остаются в исходных
  таблицах и не копируются в канонический слой.
- `unified_events` — журнал операций (создание, закрепление, перенос,
  разрешение конфликта, удаление проекции). Значения фискальных полей и ПДн
  в журнал не пишутся.
- `unified_company_links` (v1.70.85) — компании у чека помимо владельца:
  заявки (`claim`: пытались учесть чужой чек) и прежние владельцы
  (`former_owner`). Одна строка на пару (чек, компания), без внешнего ключа на
  `companies`. Правила и решения — раздел «Заявки компаний» ниже.

## Транзакционные правила

1. Дедупликация идёт по общему замку `receipt_identity_locks` и UNIQUE
   `identity_key`. SQLite и PostgreSQL используют один и тот же контракт.
2. Создание чека в реестре или пуле регистрирует канонический документ в той
   же транзакции. Повторное сканирование не создаёт второй документ.
3. Подбор/перенос из пула закрепляет существующий документ за компанией и
   создаёт только учётную проекцию, если её ещё нет. Баллы не начисляются
   повторно, запрос в ФНС не выполняется.
4. Перемещение между компаниями (`/api/v1/unified/documents/{id}/move` и
   старый `/api/v1/receipts/move`) атомарно меняет `unified_ownership` и все
   проекции. Поддерживаются `expected_version` и `idempotency_key`.
   - `/api/v1/receipts/move` переносит пачкой (фаза 0 единой базы, T-33):
     тройки блокируются одной вставкой в порядке ключа, записи, источники и
     владельцы выбираются и обновляются пачками, политика и правила поставщиков
     пересчитываются пакетно. Результат — как у поштучного переноса (тест
     сравнивает с прежним циклом); чек на разборе отклоняет всю пачку (409).
     1000 чеков — 0,36–0,48 с вместо 4,9 с, число SQL-операций не зависит от
     размера пачки.
5. Права проверяются по текущему состоянию БД после получения блокировок.
   Сотрудник видит только свои чеки, бухгалтер/руководитель — чеки своей
   компании, администратор — все. Конфликт принадлежности скрывает чек от
   компаний до разрешения администратором.
   - Экраны реестра и пула фильтруют по компании и автору штатными фильтрами
     рабочих таблиц; единый слой добавляет к ним только скрытие документов на
     разборе принадлежности (и удалённых). Расхождение владельца без флага
     разбора чек не прячет и чужой компании не показывает.
   - `/api/v1/unified/documents*` для штатных ролей требует согласия живых
     проекций: каждая копия чека принадлежит компании пользователя, хотя бы
     одна подтверждает доступ (для сотрудника — его собственный чек).
6. Удаление учётной проекции не стирает пуловую историю: канонический документ
   остаётся, пока есть хотя бы один источник. Если источников не осталось,
   документ помечается удалённым и может быть переиспользован при новом скане.

## Конфликты

Backfill и строгие операции помечают расхождения битовой маской `review_flags`:
дата, сумма, операция, принадлежность, позиции, неполная тройка, продавец,
подтверждение ФНС. Конфликтующие документы не получают владельца автоматически
и не переносятся до разбора. Администратор может разрешить конфликт
принадлежности через `/api/v1/unified/documents/{id}/resolve-ownership` — на
экране «Разбор конфликтов» (см. ниже).

## API

- `GET /api/v1/unified/stats` — счётчики и конфликты (администратор).
- `GET /api/v1/unified/documents` — список канонических чеков с изоляцией.
  `conflicts=true` — только блокирующие пометки у неудалённых документов (как
  счётчик `stats`); `flag=<маска>` — только чеки с этими битами `review_flags`.
- `GET /api/v1/unified/documents/{id}` — карточка и журнал. Для штатных ролей —
  без сведений о других организациях (T-32): чужая компания, её сотрудник и
  администратор платформы заменены на `null` с признаками `from_company_hidden`,
  `to_company_hidden`, `actor_hidden`, `created_by_hidden`; в `details` — только
  ключи без сведений о других организациях; причина сверки — только код,
  причина решения спора не отдаётся. В списке автор из другой организации тоже
  скрыт. Администратор видит всё.
- `GET /api/v1/unified/documents/{id}/review` — карточка разбора (администратор):
  живые копии с компаниями, кандидаты во владельцы, журнал с именами сотрудников
  и компаний. Только чтение: висячие ссылки не удаляет (это делает сверка).
- `POST /api/v1/unified/documents/{id}/move` — перенос (администратор).
- `POST /api/v1/unified/documents/{id}/resolve-ownership` — разрешение
  конфликта принадлежности (администратор).

## Экран «Разбор конфликтов» (#9, выпуск 1.70.83)

- Пункт меню администратора «Разбор конфликтов» (`#/conflicts`); значок у пункта —
  число конфликтов из `stats`. Других ролей экран не касается (пространство роли
  в `app/services/rbac.py` и `ROLE_SPACE` в `app.js`).
- Список — `documents?conflicts=true` с фильтром по причине (`flag`); карточка —
  `…/review`: причины с пояснениями, копии по компаниям, журнал.
- Решение спора о владельце — `resolve-ownership`: «закрепить за компанией»
  (сначала компании, у которых есть копия) или «оставить без владельца»; причина
  обязательна (3–500 символов) и пишется в журнал; `expected_version` из карточки.
  Если чек за это время изменили, сервер отвечает 409 и экран предлагает открыть
  карточку заново — решение другого администратора не перезаписывается.
- Расхождения данных (дата, сумма, операция, позиции, продавец) — на экране только
  просмотр: действия для них нет. При сохранении копии в реестре пометка поля
  снимается, только если поле изменилось, а копия в Чек-Пуле переписывается по
  единой записи, поэтому пометка может остаться при совпавших копиях —
  [#22](https://github.com/Rimlin-UNC/1c_chek/issues/22).

## Заявки компаний (выпуск 1.70.85, «Единая база», T-34)

- Отказ «чек у другой организации» на скане QR, фото, PDF, ручном вводе, в
  переносе и подборе из Чек-Пула записывает заявку (`app/unified/links.py`).
  Сотрудник видит прежний отказ и «Заявка передана администратору.»; число —
  никогда. Сбой записи не меняет ответ (точка сохранения).
- Число организаций = владелец + заявки `open` и `declined`; прежние
  владельцы, `void`, `transferred` и удалённые компании не считаются.
- Администратор: `GET /api/v1/unified/claims`, `GET …/documents/{id}/companies`,
  `POST …/links/{id}/transfer|decline|void` (версия чека и причина), вкладка
  «Заявки» на экране «Разбор конфликтов». Штатным ролям — 403; решения по
  заявкам не попадают ни в их журнал карточки, ни в ленту событий.
- Перемещение отмечает прежнего владельца и исполняет заявку получателя;
  решение спора даёт проигравшей стороне заявку «отклонена»; сверка при старте
  (`links_on_startup`) закрывает заявки удалённых компаний.
- Задним числом: `python -m app.unified.backfill --claims-only [--dry-run]` —
  отказы /scan из `audit_log` и пары «реестр ↔ пул другой компании». Подробно —
  [single_base_design.md, раздел 10](single_base_design.md#10-фазы-12-сделано-t-34).

## Число организаций для компаний и Q-24 (выпуск 1.70.86, «Единая база», T-35)

- Показ числа компаниям — только с разрешения администратора, по умолчанию
  выключен. Вкладка «Показ компаниям» на экране «Разбор конфликтов»;
  `GET`/`PUT /api/v1/unified/visibility` с телом `{mode, roles, company_ids}`:
  режим `off` / `all` / `selected` (флаг `companies.show_companies_count`),
  роли `accountant` и `manager` (`app/unified/visibility.py`).
- Поле `companies_count` в `GET /api/v1/receipts` и `GET /api/v1/receipts/{id}`:
  администратору — всегда, бухгалтеру и руководителю — с разрешения, остальным —
  никогда. Только число и только по чекам, которые роль и так видит. Считается
  одним запросом на страницу (`links.companies_counts`), правило — как у списка
  администратора. На экране: значок «🏢 N» при N ≥ 2 и строка «Организаций» в
  карточке.
- Администратору — фильтр «Организаций 🏢» → «две и больше» в реестре
  (`multi_company=true`).
- Пакетное перемещение (`POST /api/v1/receipts/move`, Q-24): если в пачке есть
  чек на разборе, ответ 409 перечисляет такие чеки
  (`detail.blocked: [{receipt_id, reasons}]`, `detail.movable`), и не
  перемещается ни один чек. `skip_blocked: true` («Переместить остальные» в
  окне) переносит остальные; пропущенные возвращаются в `skipped`. Подробно —
  [single_base_design.md, раздел 11](single_base_design.md#11-фаза-3-сделано-t-35-и-решение-q-24).

## Обновление с 1.70.80, откат и сверка (выпуск 1.70.82)

- Обновление только добавляет таблицы `unified_*` (`create_all` в `init_db`;
  в 1.70.85 — шестую, `unified_company_links`).
  Существующие таблицы и строки не меняются, перенос архива сам не запускается.
- Чек из архива попадает в единый реестр при первой правке, проверке ФНС или
  загрузке данных. Это «мягкая» регистрация в точке сохранения (SAVEPOINT):
  конфликт с уже существующей единой записью или сбой не блокируют правку —
  чек остаётся в прежнем режиме, причина уходит в журнал.
- Проверка ФНС и данные внешних источников синхронизируются через
  `sync_registry_safely`: ответ ФНС оплачен квотой и сохраняется всегда, даже
  если единый реестр нашёл расхождение (откатывается только синхронизация).
- Откат через «Последние рабочие версии» на 1.70.80 безопасен: старый код не
  знает таблиц `unified_*` и работает с базой как раньше, в том числе удаляет
  компании (поэтому у `unified_ownership` нет внешних ключей на legacy-таблицы).
- При каждом старте `app.unified.reconcile` сводит канон к рабочим таблицам:
  снимает ссылки на удалённые старой версией строки (документ без ссылок
  закрывается), выравнивает владельца и автора, если все живые копии указывают
  на одну компанию. Документы на разборе не трогаются, расходящиеся копии —
  в журнал. Каждое исправление — событие `reconcile`.
- Неполная тройка (`REVIEW_INCOMPLETE_IDENTITY`) — пометка, а не конфликт: она
  не входит в `REVIEW_BLOCKING`, такой чек переносится между компаниями.
- Репетиция: `python -m qa.upgrade_rehearsal --from-ref b3db4fe` — база
  старой версией → обновление → откат → повторное обновление → перенос архива
  на копии; 26 проверок, рабочая база не используется.

## Backfill существующей базы

Миграция добавляющая и идемпотентная. Она не удаляет и не перезаписывает
исходные строки, не меняет баллы и согласия.

```bash
python -m app.unified.backfill --dry-run
python -m app.unified.backfill --batch-size 500
python -m app.unified.backfill --claims-only --dry-run   # v1.70.85: только заявки
```

С 1.70.85 после регистрации архива наполняются и заявки компаний (ключ
`claims` в отчёте); `--claims-only` делает только этот шаг.

Реестр обрабатывается первым: его уточнённые данные и позиции предпочтительнее
пуловых. Повторный запуск регистрирует только недостающие проекции.

Перенос архива **не обязателен** для работы. Запускать его — только после
резервной копии и `--dry-run`: чеки со спорной принадлежностью (один
фискальный чек у двух организаций) уходят на разбор и скрываются от компаний
до решения администратора. Спор о владельце решается на экране «Разбор
конфликтов» (#9, выпуск 1.70.83); перенос архива на рабочей базе — только после
резервной копии, `--dry-run` и решения владельца (#10).

## Ограничения текущего этапа

Канонический слой работает рядом с легаси-проекциями; полное удаление старых
таблиц не выполнялось. Сырые ответы и частные учётные поля по-прежнему живут в
исходных таблицах. Это сознательный совместимый этап: он убирает второй
фискальный смысл и вторую строку владения, не ломая историю и интеграции.

Следующий этап принят владельцем 02.11.2026 (ADR-20). Фаза 0 — пакетный перенос и
журнал карточки без чужих организаций — выпущена в 1.70.84; дальше заявки других
компаний и число организаций по чеку. Подробно — в
[`single_base_design.md`](single_base_design.md),
[#24](https://github.com/Rimlin-UNC/1c_chek/issues/24).
