# Единый фискальный документ

Цель: один фискальный чек хранится один раз в каноническом слое, а компании
видят только свои чеки. Перенос между компаниями меняет владельца, а не
создаёт второй чек. Старые таблицы `receipts` и `pool_receipts` сохранены как
совместимые проекции для действующих API, 1С, баллов и истории Чек-Пула.

## Канонические таблицы

- `unified_documents` — одна запись на полную фискальную тройку ФН+ФД+ФП
  (`identity_key`, UNIQUE). Неполные исторические тройки не склеиваются.
- `unified_items` — единый набор позиций документа.
- `unified_ownership` — одна строка владения компанией (`company_id` может быть
  NULL для общего пула/платформы) и автор сотрудника (`created_by`).
- `unified_origins` — ссылки на совместимые проекции `registry` и `pool`.
  Сырые ответы ФНС, персональные данные, баллы и согласия остаются в исходных
  таблицах и не копируются в канонический слой.
- `unified_events` — журнал операций (создание, закрепление, перенос,
  разрешение конфликта, удаление проекции). Значения фискальных полей и ПДн
  в журнал не пишутся.

## Транзакционные правила

1. Дедупликация идёт по общему замку `receipt_identity_locks` и UNIQUE
   `identity_key`. SQLite и PostgreSQL используют один и тот же контракт.
2. Создание чека в реестре или пуле регистрирует канонический документ в той
   же транзакции. Повторное сканирование не создаёт второй документ.
3. Подбор/перенос из пула закрепляет существующий документ за компанией и
   создаёт только учётную проекцию, если её ещё нет. Баллы не начисляются
   повторно, запрос в ФНС не выполняется.
4. Перемещение между компаниями (`/api/v1/unified/documents/{id}/move` и
   старый `/api/v1/receipts/move`) атомарно меняет `unified_ownership` и все
   проекции. Поддерживаются `expected_version` и `idempotency_key`.
5. Права проверяются по текущему состоянию БД после получения блокировок.
   Сотрудник видит только свои чеки, бухгалтер/руководитель — чеки своей
   компании, администратор — все. Конфликт принадлежности скрывает чек от
   компаний до разрешения администратором.
6. Удаление учётной проекции не стирает пуловую историю: канонический документ
   остаётся, пока есть хотя бы один источник. Если источников не осталось,
   документ помечается удалённым и может быть переиспользован при новом скане.

## Конфликты

Backfill и строгие операции помечают расхождения битовой маской `review_flags`:
дата, сумма, операция, принадлежность, позиции, неполная тройка, продавец,
подтверждение ФНС. Конфликтующие документы не получают владельца автоматически
и не переносятся до разбора. Администратор может разрешить конфликт
принадлежности через `/api/v1/unified/documents/{id}/resolve-ownership`.

## API

- `GET /api/v1/unified/stats` — счётчики и конфликты (администратор).
- `GET /api/v1/unified/documents` — список канонических чеков с изоляцией.
- `GET /api/v1/unified/documents/{id}` — карточка и журнал.
- `POST /api/v1/unified/documents/{id}/move` — перенос (администратор).
- `POST /api/v1/unified/documents/{id}/resolve-ownership` — разрешение
  конфликта принадлежности (администратор).

## Backfill существующей базы

Миграция добавляющая и идемпотентная. Она не удаляет и не перезаписывает
исходные строки, не меняет баллы и согласия.

```bash
python -m app.unified.backfill --dry-run
python -m app.unified.backfill --batch-size 500
```

Реестр обрабатывается первым: его уточнённые данные и позиции предпочтительнее
пуловых. Повторный запуск регистрирует только недостающие проекции.

## Проверки

- `tests/test_unified_receipts.py` — слияние источников, карантин конфликтов,
  перенос без второго документа, журнал, идемпотентность, устаревшая версия,
  конкурентный перенос, синхронизация правок и удаление проекции.
- `tests/test_unified_postgres.py` — живой PostgreSQL в отдельной схеме
  (только при `UNIFIED_POSTGRES_TEST_URL`): UNIQUE-идентичность и конкурентный
  перенос. Не запускается против рабочей базы.
- Старые маршруты реестра, пула, ролей и 1С остаются покрыты полным набором
  тестов.

## Ограничения текущего этапа

Канонический слой работает рядом с легаси-проекциями; полное удаление старых
таблиц не выполнялось. Сырые ответы и частные учётные поля по-прежнему живут в
исходных таблицах. Это сознательный совместимый этап: он убирает второй
фискальный смысл и вторую строку владения, не ломая историю и интеграции.
