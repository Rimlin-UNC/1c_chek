# Доступ к платному API для компаний и ИП — как это устроено

> Версия механизма: v1.70.45. Документ описывает **контур B2B**: кто и как получает
> доступ к разделу «API для бизнеса», какие проверки проходит компания, что делает
> автоматика и где подключается администратор.
>
> Техническое описание самих методов API — [docs/API.md](API.md).

---

## 1. Задача и решение

**Задача владельца.** Раздел «API для бизнеса» не должен быть виден посторонним.
Его видят только те, кто подтвердил статус компании через официальную (корпоративную)
почту. Раздел — отдельная страница со своими страницами: документация API, тарифы
и состав, кнопка «Обсудить подключение». Администратор видит всё, но каждый такой
блок помечен «Это не видит никто». Нужны формы и автоматизация с небольшой
модерацией: администратор выбирает полную автоматизацию, частичную или отмену.

**Решения, принятые владельцем** (обязательны к исполнению):

| Вопрос | Решение |
|---|---|
| Как подтверждаем статус | Корпоративная почта (ссылка) **и** карточка ЕГРЮЛ/ЕГРИП по ИНН через Checko; если ключ Checko не настроен — контрольная сумма ИНН и тип (10 = ООО, 12 = ИП) |
| Почта | `chek@ymaster.ru` везде: интерфейс, письма, документация |
| Точка входа | Полноценный кабинет компании: регистрация (почта + пароль), подтверждение, заявка, затем ключ, лимиты и история вызовов |
| Автоматизация | По умолчанию **частичная**: проверки выполняет автоматика, ключ выдаёт администратор в один клик |

## 2. Архитектура: третий контур

В приложении уже есть два раздельных контура:

- **ядро** (`app/`, `app/routers/`) — корпоративные пользователи: администратор,
  бухгалтер, сотрудник, руководитель; свой JWT `typ=core`;
- **Чек-Пул** (`app/pool/`) — участники-сдатчики чеков; свой JWT `typ=pool`,
  свои пароли, своя таблица токенов.

Клиент платного API — это **ни то, ни другое**: не сотрудник и не сдатчик чеков.
Смешивать его с участниками пула нельзя (испортит счётчики участников, рейтинги
и баллы), с пользователями ядра — тоже (дал бы доступ во внутренний кабинет 1С).

Поэтому добавлен третий контур — `app/b2b/`:

```
app/b2b/
  models.py         таблицы контура + добавляющая миграция ensure_b2b_schema()
  verify.py         проверки статуса компании (почта, ИНН, реестр, дубли, риск)
  pipeline.py       конвейер: три режима автоматизации и переходы состояний
  letters.py        письма контура (через SMTP-настройки Чек-Пула)
  auth.py           JWT typ=b2b, пароли PBKDF2 ядра, зависимости доступа
  content.py        содержимое закрытых страниц — собирается из кода, не вручную
  router_public.py  /api/v1/b2b/*       — кабинет компании
  router_admin.py   /api/v1/b2b-admin/* — модерация (только администратор)
  assets/           схемы API (не отдаются публично — только через гейт)
```

Правила контура, унаследованные от пула:

1. **Токены ядра не проходят в контур и наоборот.** `typ` в JWT проверяется первым;
   `b2b`-токен не открывает кабинет пула, `pool`-токен не открывает кабинет B2B.
2. **Пароли хешируются функцией ядра** (PBKDF2), в БД только хэш.
3. **Одноразовые токены хранятся хэшем** (SHA-256), с назначением (`purpose`),
   сроком и отметкой об использовании — как `pool_tokens`.
4. **Миграция только добавляющая**: `create_all` для новых таблиц, существующие
   колонки не изменяются и не удаляются.
5. **Почта не ломает приём данных**: сбой SMTP возвращает признак ошибки, а не
   исключение; регистрация при этом остаётся возможной (письмо можно выслать повторно).

## 3. Модель данных

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `b2b_companies` | кабинет компании/ИП | `email` (уникальный), `password_hash`, `company_name`, `inn`, `kind`, `status`, `consent_version`, `ip_hash` |
| `b2b_applications` | заявки на подключение | `company_id`, `tariff`, `task`, `expected_volume`, `status`, `auto_mode`, `key_id`, `decided_by` |
| `b2b_checks` | журнал проверок | `company_id`, `kind`, `ok`, `hard`, `detail` |
| `b2b_tokens` | одноразовые ссылки | `token_hash`, `purpose` (`verify`, `reset`), `expires_at`, `used_at` |
| `b2b_events` | аудит контура | `company_id`, `actor` (`company`, `admin`, `system`), `action`, `details` |

Ключ API остаётся в таблице пула (`pool_api_keys`) — контур B2B **не заводит второй
реестр ключей**: лимиты, счётчики и отзыв работают через уже проверенный механизм
`app/pool/router_api.py`. В заявке хранится только ссылка `key_id`.

### Состояния компании

```
new ──регистрация──▶ email_pending ──ссылка из письма──▶ checks
checks ──проверки пройдены──▶ verified        (страницы раздела открыты)
checks ──проверки не пройдены──▶ rejected     (причина в письме и в кабинете)
verified ──решение администратора──▶ rejected | blocked
```

### Состояния заявки

```
new ──автоматика──▶ approved (режим «полная») | parked (режимы «частичная», «отмена»)
parked ──администратор──▶ approved | rejected
approved ──отзыв ключа──▶ revoked
```

`verified` — подтверждён **статус компании** (право видеть раздел).
`approved` — одобрена **заявка** (право пользоваться API, выдан ключ). Это два разных
решения: раздел можно показать раньше, чем согласованы лимиты.

## 4. Проверки статуса компании

Порядок проверок в `app/b2b/verify.py`. Каждая пишет строку в `b2b_checks`
с признаком `hard` (обязательная) или мягкая (влияет на решение, но не блокирует сама).

| № | Проверка | Что делает | Обязательная |
|---|---|---|---|
| 1 | `email_format` | Формат и длина адреса | да |
| 2 | `email_domain` | Домен не из списка бесплатной почты (mail.ru, yandex.ru, gmail.com, …). Администратор может разрешить исключения переключателем | да |
| 3 | `inn_format` | Нормализация, контрольная сумма, тип: 10 цифр = ООО, 12 = ИП | да |
| 4 | `registry` | Карточка Checko: организация существует, статус «действующее», наименование совпадает с указанным (порог совпадения 0.55 по `similar_ratio`). Если ключ Checko не настроен — мягкая проверка по формальным признакам с явной пометкой | да (если `b2b_require_registry=1`) |
| 5 | `duplicate` | Тот же ИНН или та же почта уже зарегистрированы — не плодим дубли | да |
| 6 | `risk` | `risk_assessment()` по карточке: возраст, уставный капитал, статус. Высокий риск не отклоняет сам, а передаёт решение администратору | нет |

**Почему почта и реестр вместе.** В карточке ЕГРЮЛ/ЕГРИП нет адреса электронной почты,
поэтому реестр подтверждает существование и действительность организации по ИНН,
а корпоративный ящик — что заявитель действительно представляет эту организацию.
Двух факторов достаточно для доступа к разделу; ключ API выдаётся только после
одобрения заявки.

## 5. Конвейер и три режима автоматизации

Режим хранится в настройке `b2b_auto_mode` и переключается администратором
в разделе `#/b2badmin`. Значения:

| Режим | Что делает автоматика | Что делает администратор |
|---|---|---|
| `full` — «Полная автоматизация» | Проверки → `verified` → заявка `approved` → ключ выдан → письма | Смотрит журнал; может отозвать |
| `partial` — «Частичная автоматизация» (**по умолчанию**) | Проверки → `verified`; заявка остаётся в очереди `parked` | Одобряет заявку и выдаёт ключ в один клик |
| `off` — «Без автоматизации (всё вручную)» | Ничего: проверки не запускаются сами, статус не меняется | Всё вручную, включая запуск проверок кнопкой «Перепроверить» |

Названия в кавычках — это то, что администратор видит в списке выбора режима
(`pipeline.MODE_TITLES`); в указании владельца они звучали как «полная
автоматизация, частичная либо отмена».

Дополнительные переключатели (тонкая настройка без смены режима):

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `b2b_enabled` | `0` | Контур включён: регистрация и вход работают |
| `b2b_auto_mode` | `partial` | Режим автоматизации |
| `b2b_auto_issue_key` | `1` | В режиме `full` ключ выдаётся автоматически |
| `b2b_require_registry` | `1` | Карточка реестра обязательна: при настроенном ключе Checko красная проверка реестра (нет организации, не действующая, наименование не совпадает) блокирует автоматическое подтверждение статуса. `0` — та же проверка остаётся замечанием, которое видит администратор, но не блокирует автоматику |
| `b2b_allow_free_domains` | `0` | Разрешить бесплатные почтовые домены |
| `b2b_notify_admin` | `1` | Писать администратору о новой заявке |
| `b2b_notify_email` | пусто | Куда писать администратору; пусто — `settings.VENDOR_EMAIL` (`chek@ymaster.ru`) |

Карточка ЕГРЮЛ/ЕГРИП запрашивается через существующий сервис Checko: ключ
берётся из настройки приложения `checko_api_key` (`services/checko.py`,
`SETTING_KEY`). Ключ не настроен — проверка реестра выполняется по формальным
признакам ИНН и помечается в журнале, решение принимает администратор.

Любое решение — автоматическое или ручное — попадает в `b2b_events`, а действия
администратора дополнительно пишутся в общий журнал аудита ядра (`log_action`):
`b2b_company_verified`, `b2b_company_rejected`, `b2b_company_blocked`,
`b2b_company_unblocked`, `b2b_application_approved`,
`b2b_application_rejected`, `b2b_key_revoked`, `b2b_config_changed`,
`b2b_letter_resent`.

### Тарифы и лимиты

Тариф — это лимиты ключа, состав методов одинаков на любом тарифе
(цифры — из кода `app/pool/router_api.py`, а не из документа):

| Тариф | Запросов в час | Квота в месяц |
|---|---|---|
| Старт | 60 (`DEFAULT_RATE`) | 5 000 (`DEFAULT_QUOTA`) |
| Бизнес | 300 | 30 000 |
| Аналитика | 1 200 | 150 000 |

Стоимость не публикуется ни на одной странице: она назначается при подключении
и сообщается по запросу. Цены из внутреннего `docs/plan.md` в контур не попадают —
это заперто тестом.

## 6. Страницы и доступ

Публичный лендинг (`/`) больше **не содержит** раздела «API для бизнеса» и ссылки на
него: пункт убран из блока вопросов вместе с секцией и её стилями.

Контур живёт на отдельной странице `/b2b/` (как мини-приложение MAX живёт на
`/maxapp/`): свои `index.html`, `b2b.css`, `b2b.js`, своя авторизация, своё
хранилище токена. Ссылки на `/b2b/` с публичных страниц нет — адрес сообщается
заинтересованным компаниям напрямую.

| Страница кабинета | Кто видит | Содержимое |
|---|---|---|
| `#/start` | все | Что нужно сделать компании или ИП: шаги регистрации, требования, как узнать стоимость |
| `#/register`, `#/login` | все | Формы регистрации и входа |
| `#/confirm` | все | Подтверждение корпоративной почты по ссылке из письма |
| `#/hub` | `verified` | Раздел «API для бизнеса»: состав, схема доступа, требования |
| `#/docs` | `verified` | Документация API: шесть методов, параметры, ответы, коды отказов |
| `#/tariffs` | `verified` | Тарифы и состав: лимиты, что входит, чего нет ни на одном тарифе |
| `#/contact` | `verified` | «Обсудить подключение»: задача, ожидаемый объём, тариф → заявка |
| `#/cabinet` | `verified` | Статус, проверки, заявки, префикс ключа, расход лимитов |

Защита содержимого — **на сервере**, а не только в интерфейсе:

- `GET /api/v1/b2b/content` и `GET /api/v1/b2b/diagram/{name}` требуют `b2b`-токен
  **и** статус `verified`; иначе `401` / `403` с внятным текстом;
- схемы API вынесены из `app/static/` в `app/b2b/assets/` — публичного адреса у них
  больше нет, отдаются только текстом через закрытый маршрут;
- содержимое страниц собирается в `app/b2b/content.py` из кода сервиса (маршруты
  берутся из роутера `router_api.py`), поэтому страница не может разойтись с
  реальностью — расхождение ловит тест;
- раздел администратора (`docs/API.md`, §10) в клиентские страницы **не входит**.

## 7. Администратор

Раздел `#/b2badmin` в основной SPA (пункт меню `admin-only hidden`). Каждый блок
раздела несёт пометку **«Это не видит никто»** — так владелец отличает внутренние
поверхности от клиентских.

Что может администратор:

1. видеть сводку: сколько компаний по статусам, размер очереди заявок, текущий режим;
2. переключать режим автоматизации (`full` / `partial` / `off`) и переключатели;
3. открывать карточку компании: данные, все проверки с подробностями, заявки, события;
4. подтвердить статус вручную, отклонить с причиной, заблокировать и разблокировать;
5. запускать перепроверку (нужно в режиме «отмена»);
6. одобрять заявку в один клик — с выдачей ключа и лимитами тарифа;
7. отклонять заявку с причиной (причина уходит в письме);
8. отзывать выданный ключ;
9. повторно отправлять письмо подтверждения;
10. видеть журнал контура.

Ключ показывается **один раз** — в ответе на одобрение (в БД только SHA-256 хэш),
как в существующем механизме выдачи ключей пула. В письмах полный ключ не
отправляется: письмо содержит ссылку на кабинет, где ключ виден один раз после
одобрения. Это осознанное решение — письмо может быть переслано.

## 8. Письма

Отправка — через `app/pool/mailer.py` (те же SMTP-настройки, что задаёт
администратор; адрес отправителя и `chek@ymaster.ru` в подписи).

| Письмо | Кому | Когда |
|---|---|---|
| Подтверждение корпоративной почты | компании | после регистрации и по кнопке «выслать повторно» |
| Статус компании подтверждён | компании | после зелёных проверок |
| Заявка одобрена — ключ в кабинете | компании | после одобрения (ссылка, ключа в письме нет) |
| Отказ с причиной | компании | после отклонения |
| Новая заявка в очереди | администратору | при `b2b_notify_admin=1` |

Ссылки в письмах строятся от `public_base_url` (настройка администратора),
токены одноразовые: подтверждение почты — 24 часа, восстановление доступа — 1 час.

## 9. Безопасность контура

- пароль не короче 8 символов, в БД только PBKDF2-хэш;
- одноразовые токены — SHA-256, срок, однократное использование;
- попытки входа ограничены по окну времени (блок на 15 минут после серии неудач);
- регистрация ограничена по IP (не более 5 в час) — защита от перебора;
- формы с полем-ловушкой (honeypot) и минимальным временем заполнения: боты
  получают «успех», но запись не создаётся;
- согласие на обработку персональных данных фиксируется **до** отправки формы,
  с версией оферты и временем (`consent_version`, `consent_at`);
- IP и User-Agent пишутся хэшем, как в `pool_leads`;
- ответы не содержат трассировок, SQL и путей на диске;
- все маршруты администратора — за `require_admin` ядра.

## 10. Приёмка

Механизм закрыт тестами `tests/test_v17045.py`:

1. регистрация, подтверждение почты, вход, отказы и их тексты;
2. все шесть проверок: зелёные и красные сценарии, включая отсутствие ключа Checko;
3. три режима автоматизации: полный, частичный, отмена;
4. гейт содержимого: `401` без токена, `403` без `verified`, `200` после подтверждения;
5. страницы собираются из кода: маршруты и тексты отказов не расходятся с
   `router_api.py`; цены из `docs/plan.md` не появляются нигде;
6. администратор: сводка, режимы, одобрение с выдачей ключа, отказ, отзыв, маркер
   «Это не видит никто» в каждом ответе;
7. публичный лендинг не содержит раздела и ссылки; схемы недоступны по старому адресу;
8. почта `chek@ymaster.ru`: старого адреса в репозитории нет.

## 11. Границы механизма (чего здесь нет)

- оплата и выставление счётов — вне контура: подключение согласуется вручную,
  стоимость сообщается по запросу;
- самостоятельная смена тарифа компанией — только через администратора;
- продажа сырых чеков, их позиций и данных участников — ни на каком тарифе;
- публичный каталог клиентов — не ведётся.
