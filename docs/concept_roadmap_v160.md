## 2. Сервер: что влезает, а что нет

| Ресурс | Есть | Оценка потребления | Вердикт |
|---|---|---|---|
| RAM | 1 ГБ | uvicorn+SQLite ~150–250 МБ; правила/маппинг — копейки; OCR/LLM локально — сотни МБ и выше | ✅ бизнес-логика; ❌ локальный ИИ/OCR |
| Диск | 10 ГБ | код+venv ≈ 0,3 ГБ; БД ≈ 1–3 КБ/чек → 100 тыс. чеков ≈ 0,5–2 ГБ; бэкапы ротируются (30 копий) | ✅ хватит на годы; следить за фото чеков (лимит+сжатие+retention) |
| Сеть | 50 Мбит, 500 ГБ/мес | REST-JSON крошечный; декод QR на клиенте (фото на сервер не льются); git-fetch мелкий | ✅ запас огромен |
| CPU | — | правила/агрегации — дешёвые; тяжёлое — только наружу (API) | ✅ |

**Страховка:** добавить на сервере swap 1–2 ГБ и мониторинг
`systemctl status` + лог-алерт по RSS — дёшево и спасает от пиков.

**Главный принцип под это железо:** всё «умное» — это *правила и
агрегации в Python* (ноль затрат) либо *внешние API* (нагрузка чужая),
но никогда — тяжёлый локальный софт.

## 3. Оценка концепции: рынок и наша ниша

Рынок автообработки чеков в РФ: модули 1С (Сканер чеков и аналоги),
экосистемы Такском/Контур (упор на маркировку/ЭДО), банковские
«автоавансы» (Т-Банк/Сбер — подотчёт прямо в банке), нишевые сканеры.
Тренды концепции названы верно: AI-OCR, API-first, комплаенс-лимиты,
мультисистемность — это реальные направления.

**Чем мы уже отличаемся (не копировать, а усиливать):**
- **Чек-Пул** — краудсорсинговая база чеков с донорами и баллами: этого
  нет ни у 1С-модулей, ни у банков. Уникальный актив, растёт сам.
- **Офлайн-first** (очередь в PWA) — у большинства конкурентов online-only.
- **1С-конвейер под ключ** (маппинг → АО-1 → выгрузка) для микро/малого бизнеса.

**Позиционирование принимается:** «не сканер, а хаб расходов»,
«прозрачность для всех» — и, критично, **оно реализуется без смены
железа**: руководителю нужны агрегации, сотруднику — простая сдача,
бухгалтеру — правила и лимиты. Всё это — Python+SQLite по силам.

## 4. Карта концепции: что берём, что откладываем

### 🟢 Фаза 1 — реализуемо сейчас (дёшево, высокоценно, влезает с запасом)

1. **«Понимающий» конвейер правил (без LLM)** — v1.61
   Проверки после получения данных источника: сумма позиций ≠ итогу;
   позиция без НДС при запрещённом vat_rate; дубль позиции; нулевая/гигантская
   сумма (аномалия уже есть — расширить). Нарушение → статус `pending`
   с человеческой причиной. Ноль внешних вызовов, ноль RAM.
   *Закрывает «выявлять несоответствия» из концепции бесплатно.*
2. **Комплаенс и лимиты** — v1.62
   Настройки: лимит ₽/чек и ₽/мес на сотрудника; запрещённые категории
   (по статьям расходов); «личные покупки» уже есть (personal_sum).
   Нарушения помечаются в списке чипом и попадают в сводку. Блокировка —
   мягкая (пометка + ручная проверка), не ломаем поток сдачи.
3. **Самообучающийся маппинг** — v1.63
   Бухгалтер поправил статью/сотрудника/комментарий → кнопка
   «Запомнить для этого поставщика (ИНН)» → правило-кандидат →
   применение к будущим чекам (и массово «Применить к N старым»).
   База уже есть: mapping + details_source=manual_edit + ИНН в данных.
4. **Дашборд руководителя** — v1.64
   Добавляющая миграция: поле «проект/отдел» (текст + быстрый выбор);
   разрезы расходов по проектам/статьям/сотрудникам с drill-down до чека;
   графики уже есть (charts.js). Агрегации SQL — копейки.
5. **PDF-чеки** — v1.65
   Текстовые PDF (электронные чеки из почты/банка) в тот же конвейер:
   pypdf (лёгкий) + лимит 2–5 МБ + только для проверенных ролей;
   сканированный PDF без текстового слоя → честное «нет текста, пришлите QR».
   OCR-картинки — НЕ на этом сервере (см. 🟡).
6. **Активный ассистент (Telegram)** — v1.66
   Бот уже в системе: напоминание сотруднику «сдайте чеки за сегодня» в
   18:00, дайджест бухгалтеру по утрам. Геолокацию НЕ делаем (батарея,
   приватность, 152-ФЗ) — время+факты достаточны и бесплатны.
7. **Исходящие webhooks** — v1.67
   Событие «чек verified» → POST на URL компании (секрет + повторы).
   events.py уже есть. Это фундамент «интеграции без границ»: любой
   внешний consumer (включая будущего коннектора МоегоСклада) без
   тяжёлых коннекторов на нашем железе.

### 🟡 Фаза 2 — после Фазы 1 и первых пользователей (внешние расходы/договоры)

8. **LLM-семантика через внешний API** — только наружу: локальную модель
   это железо не потянет. Правила безопасности: отправлять только
   обезличенные строки позиций (без сотрудников/сумм договора), кэш
   ответов по (ИНН, ФД, ФП) — не платить дважды, дневной бюджет запросов.
   ВАЖНО: правила Фазы 1 (п.1) дают 80% пользы за 0 ₽ — LLM лишь
   до-категоризирует то, что правила не смогли. «Бесплатные ИИ-агенты» —
   с оговоркой: бесплатных квот на прод-объёмы не бывает, считать
   бюджет заранее.
9. **OCR фото на сервере** — tesseract на 1 ГБ RAM с 1 worker'ом рискован
   (пики 200–400 МБ на поток). Варианты: OCR в браузере (wasm, нагрузка
   на телефон донора — идеально для Чек-Пула) либо внешний OCR-API с
   жёсткими лимитами. Не раньше спроса.
10. **Банки** — договоры/токены/поддержка; технически легковесно, но
    стартовать с дешёвого: **CSV-выписка → привязка «чек ↔ транзакция»**
    вручную/полуавтоматом. Полные API банков — Phase 2+.
11. **МойСклад** — REST-коннектор поверх webhooks — реалистично;
    SAP/Oracle — не наш профиль на этом сервере.
12. **Кабинет поставщика** — ценный, но отдельный контур с ролями;
    после того как Фаза 1 соберёт спрос.

### 🔴 Не делать на этом сервере (анти-рекомендации)

- Локальная LLM/OCR-пул/векторные БД — RAM/CPU не те; только внешние API.
- Celery+Redis — запрещено владельцем и не нужно: daemon-потоков хватает.
- Переезд на PostgreSQL — на 1 worker SQLite быстрее и проще; вернуться
  к вопросу при >1 worker или >~300 тыс. чеков.
- Приём «всех форматов мира» (скриншоты банков, вложенные EML) —
  расход диска/поддержки большой, ценность малая; PDF-чеков достаточно.

## 6. Риски и как закрываем

- **152-ФЗ:** наружу (LLM/OCR-API) — только обезличенные позиции; ПДн
  (сотрудники, e-mail) остаются на сервере. Внешние вызовы — после
  явного согласия владельца и с ведением журнала вызовов.
- **Квоты ФНС/pke:** новые проверки — по уже полученным данным,
  ДОПОЛНИТЕЛЬНЫХ запросов к источникам не порождают (only-up сохраняем).
- **1 worker:** фоновое — короткие daemon-потоки; пакетные операции
  (масс-применение правил) — батчами по N с паузой.
- **Диск:** с момента включения фото-полей — ретеншн-политика
  (сжатие imaging.py + удаление фото по возрасту, фискальные данные остаются).
- **Обратная совместимость:** каждый пункт Фазы 1 — отдельный блок в
  реестре + версия в 7 местах + CHANGELOG/WHATS_NEW + тесты-замки.

## 7. Резюме

Концепция верная по направлению («сканер → хаб управления расходами»),
но её нужно «заземлить» до нашего железа: **сначала правила, лимиты,
умный маппинг, дашборд руководителя и webhooks — всё это чистый Python,
который влезает с 10-кратным запасом; LLM/OCR/банки — Фаза 2 через
внешние API и по спросу.** Уникальность (Чек-Пул + офлайн + 1С-конвейер)
не разменивается: каждая новая функция надстраивается над работающим
ядром, а не переделывает его.
