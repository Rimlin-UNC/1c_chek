# Первичка для аутсорсинговых бухгалтерий и компаний — проект (03.11.2026)

[База знаний](kb/README.md) · [Стратегия](kb/11_strategy.md) · [ADR-21…24](ARCHITECTURE.md#adr-21)

## Что болит у бухгалтеров (исследование)

| Боль | Что говорят | Источник |
|---|---|---|
| Бухгалтер превращается в «службу сбора первички» | клиенты уверены, что «всё отправили», документы приходят в последний день; напоминания не работают; помогают срок сдачи (до 5–7 числа), письменная фиксация «документов нет», платные повторные напоминания | [Клерк](https://www.klerk.ru/user/2558321/713198/), [Контур](https://kontur-extern.net/blog/kak-buhgalteru-autserseru-opredelit-graniczy-otvetstvennosti-s-klientom) |
| Нет «часа икс» | после срока документы не принимаются в текущий отчёт — только уточнённая декларация за доплату | [Клерк, «Кнопка»](https://www.klerk.ru/blogs/tochka/674037/) |
| Документы приходят откуда угодно | нужна единая точка входа для всех документов клиента | [Контур](https://www.kontur-extern.ru/info/85581-nastroit_sistemu_sbora_pervichnyh_dokumentov) |
| Реестр недостающего строят вручную | по банку видны платежи без закрывающих документов — реестр отдают клиенту; бухгалтеры пишут ботов, которые сами напоминают в Telegram | [Контур](https://kontur-extern.net/blog/kak-buhgalteru-autserseru-opredelit-graniczy-otvetstvennosti-s-klientom), [Клерк](https://www.klerk.ru/user/katerinayahotova1704786739/683231/) |
| Ошибки в первичке | нет обязательных реквизитов, неверные ИНН и КПП, исправления УПД (статус 1 или 2, строка 1а), потерянные оригиналы | [Такском](https://taxcom.ru/baza-znaniy/otchetnost/stati/ispravleniya-pervichnoy-dokumentatsii/), [Главбух](https://www.glavbukh.ru/art/24495-ispravlenie-oshibok-v-upd-kak-ne-poteryat-pravo-na-vychet-nds) |
| Электронный УПД | с 01.04.2026 в ЭДО — только формат 5.03 (ON_NSCHFDOPPR), с 01.01.2026 НДС 22 % | [Диадок API](https://developer.kontur.ru/doc/diadoc-api/docflows/utd.html), [Интеграция](https://integration-software.ru/blog/vygruzka-upd-schet-faktury-scheta-na-oplatu-v-formate-xml) |

## Решения, принятые агентом

- Документы сдают и сотрудники компании-клиента (программа, Telegram, MAX), и бухгалтер.
- Срок сдачи по умолчанию — 5-е число следующего месяца, «час икс» — настройка компании.
- Напоминания — по уже подключённым каналам (Telegram, MAX, почта), без новых сервисов.
- Запрос документа и каждое напоминание записываются в журнал — это и есть письменный след.

## «Что нужно от клиента» (1.70.97): решения

Боль — бухгалтер как «служба сбора первички»: клиент уверен, что «всё отправил», документы приходят в последний
день, напоминания вручную не работают ([Клерк](https://www.klerk.ru/user/2558321/713198/),
[Контур](https://kontur-extern.net/blog/kak-buhgalteru-autserseru-opredelit-graniczy-otvetstvennosti-s-klientom)).

| Вопрос | Решение | Почему |
|---|---|---|
| Что считать недостающим | программа ищет сама: поставщик присылал документы два из трёх прошлых месяцев, а в этом — нет (с обычной суммой — медиана); чеки, не подтверждённые ФНС (`not_found`, `invalid`); УПД с ошибками — нужен исправленный; плюс запросы бухгалтера | бухгалтер не держит в голове, кто и что присылает каждый месяц; повтор поиска дублей не создаёт, отменённое не возвращает |
| Закрытие | пришедший документ закрывает запрос сам: УПД от поставщика за месяц, подтверждённый чек, исправление (тот же номер с номером исправления, без ошибок) | меньше ручной работы и ложных напоминаний |
| Срок | число следующего месяца (по умолчанию 5-е, 1–28) и «час икс» (по умолчанию 18:00 МСК) — настройка компании | решение агента 03.11.2026 (стратегия) |
| Расписание | за 3, 1 и 0 дней до срока в 10:00 МСК (в день срока — не позже чем за час до «часа икс»), после срока — раз в 2 дня, 3 раза, не дольше 30 дней; после простоя сервера отправляется только самое свежее напоминание, пачки нет | клиенту не приходит «залп» сообщений |
| Кому | общие запросы — руководителю (и сотрудникам, если выбрано) и на почту клиента; чек без подтверждения ФНС — лично тому, кто сканировал; сотрудника в компании нет — руководителю | адресность; общие запросы, которые некому доставить, видны в предпросмотре и в журнале |
| Каналы | только подключённые в программе: Telegram и MAX (по привязке пользователя), почта (SMTP) | без новых сервисов (решение агента 03.11.2026) |
| Включение | автонапоминания включает бухгалтер для каждой компании; без этого программа клиенту не пишет | клиент не получит сообщений без решения бухгалтера |
| Журнал | каждое сообщение — запись с каналом, получателем и текстом; создание, получение, отмена — тоже; записи не удаляются, запросы не удаляются, а отменяются с причиной | письменный след на случай «я всё отправил» |
| Дисциплина клиента | доля документов, полученных в срок, за три месяца | аргумент для разговора о сроках и платных повторных напоминаниях |

Тесты (только синтетика): расписание на фиксированных датах, окно и «без пачки», поиск недостающего и
самозакрытие, адресность и отсутствие повторов, недоставленные и «некому отправить» — в журнале, изоляция компаний
в API. Код — `app/docreq/` (`service.py`, `router.py`, `models.py`), экран — `app/static/js/docreq.js`; тесты —
`tests/test_docreq.py`, `tests/js/docreq.test.js`.

## Банковская выписка (1.70.98): решения

Платежи без документов — ещё один источник «Что нужно от клиента»: аутсорсер передаёт клиенту реестр платежей без
закрывающих документов ([Контур](https://kontur-extern.net/blog/kak-buhgalteru-autserseru-opredelit-graniczy-otvetstvennosti-s-klientom)).
Владелец ([#30](https://github.com/Rimlin-UNC/1c_chek/issues/30)): часть покупок прошла по корпоративным картам, часть
сотрудник оплатил сам — ему нужно вернуть деньги.

| Вопрос | Решение | Почему |
|---|---|---|
| Формат | выгрузка «в 1С» из интернет-банка — «1CClientBankExchange» (файл kl_to_1c.txt), кодировки Windows (cp1251), DOS (cp866) и UTF-8; до 5 МБ и 20 000 операций | этот формат дают все банки, он же загружается в 1С |
| Что храним | только списания, которым нужны документы: оплаты поставщикам и покупки по картам — дата, номер, сумма, ИНН и наименование получателя, назначение до 210 знаков, последние 4 цифры карты; файл не храним, полных счетов, БИК и банков нет | минимум банковских данных (ADR-28) |
| Что не нужно | налоги и взносы (счёт казначейства, реквизиты бюджетного платежа, ЕНП, НДФЛ, страховые взносы), зарплата, комиссии банка, кредиты и займы, выдача под отчёт и снятие наличных, поступления, переводы между своими счетами — только считаются | документы на них не нужны; «в т.ч. НДС» в назначении — не признак налога, иначе пропали бы все оплаты поставщикам |
| Покупка по карте | ищем чек на ту же сумму за 3 дня до списания или днём позже; несколько — ближайший по дате | списание по карте приходит позже покупки |
| Оплата поставщику | УПД или счёт-фактура того же ИНН на ту же сумму (документ — за 120 дней до оплаты или в течение 60 дней после); документ с номером из назначения платежа («по счёту № 45») — частичная оплата; чек этого продавца на ту же сумму ±5 дней | постоплата, предоплата и частичная оплата; чек при оплате по счёту выдают многие продавцы |
| Без документа | запрос «платёж без документов» в «Что нужно от клиента» за месяц операции; покупка по карте сотрудника (карта указана в настройках) — запрос ему лично; пришёл чек или УПД — запрос закрывается сам; «документы не нужны» — запрос отменяется с причиной | один список недостающего и одно расписание напоминаний |
| К возмещению | чеки за период выписок, которых в выписках нет: сотрудник платил сам; к возмещению — сумма «к учёту» (без личных покупок); последние 3 дня выписки ждут следующую; решение «возмещено» или «не возмещать» с причиной; таблица CSV для авансового отчёта | деньги сотруднику возвращает бухгалтер, программа только находит и считает |
| Защита | выписка другой организации (ИНН своей стороны не совпадает с ИНН компании) — отказ; тот же файл — отказ; пересекающиеся выписки — операция не задваивается (отпечаток) | у аутсорсера десятки клиентов — легко выбрать не ту компанию |
| Срок хранения | по умолчанию 1095 дней (3 года — глубина налоговой проверки), от 30 до 3650; старые операции удаляются, открытые запросы по ним отменяются | банковские данные не копятся без нужды |
| Права | бухгалтер — своя компания, администратор — выбранная; чужие выписки, операции и чеки — 404 | как у первички и «Что нужно от клиента» |

Тесты (только синтетика): разбор трёх кодировок и многострочного назначения, отказ на чужих файлах, виды операций
(в том числе «НДС» в назначении), сопоставление с чеками и УПД, запросы и их самозакрытие, отказ от выписки другой
организации, изоляция компаний, «к возмещению» и CSV, срок хранения. Код — `app/bank/` (`parser.py`, `service.py`,
`router.py`, `models.py`), экран — `app/static/js/bank.js`; тесты — `tests/test_bank.py`, `tests/js/bank.test.js`.

## Банк по API (1.70.99): решения

Запрос владельца 04.11.2026: данные банка по API, начать с Точки, способ — OAuth 2.0; в карточке компании — выбор банка
и то, что банк даёт для доступа. Формат — открытая документация и спецификация OpenAPI Точки
([developers.tochka.com](https://developers.tochka.com/docs/tochka-api/)); решение — ADR-29, задача — T-66
([#51](https://github.com/Rimlin-UNC/1c_chek/issues/51)).

| Вопрос | Решение | Почему |
|---|---|---|
| Способ доступа | OAuth 2.0 — основной; JWT-ключ из интернет-банка — второй способ | доступ подтверждает сам клиент в своём банке, срок разрешения виден, отозвать можно в интернет-банке; JWT — кому так проще |
| Где настраивается | блок «Банк по API» в карточке компании (администратор) и на экране «Банк: выписка» (бухгалтер своей компании): банк, способ, дата начала загрузки, адрес возврата | так просил владелец; бухгалтер работает с выпиской каждый день |
| Чьё приложение OAuth | своё у компании (client_id и client_secret из «Интеграции и API» → «Подключить OAuth») или общее приложение сервера — `TOCHKA_CLIENT_ID` и `TOCHKA_CLIENT_SECRET` в `.env` | облако для аутсорсеров — одно приложение «Ямастер Чек»; своя установка — своё приложение |
| Ход подключения | токен приложения (`client_credentials`) → разрешение (consent) только на чтение: счета, клиенты, выписки, транзакции; срок — год → клиент входит в Точку и подтверждает → код (живёт 5 минут) → токены | как в документации банка; платежей и СБП в разрешении нет |
| Защита возврата | отметка `state` — случайная, одноразовая, 15 минут; возврат без неё, с чужой или старой — отказ без привязки | возврат открывает браузер без входа в программу: компанию определяет только отметка |
| Токены | access_token (сутки) продлевается сам за 5 минут до конца; новый refresh_token (30 дней) сохраняется сразу — старый банк больше не принимает; отказ продления — «нужно подключить заново» | регулярная загрузка сама держит подключение живым |
| Компания и счета | компания в банке — по ИНН (нет ИНН и одна компания — она); счета — открытые; загружаются рублёвые, валютные показываются с пометкой «не загружается» | у аутсорсера десятки клиентов — нельзя загрузить чужую выписку |
| Выписка | раз в 6 часов и по кнопке «Загрузить сейчас»; одна выписка в программе на счёт и месяц, дополняется; первый раз — с 1-го числа прошлого месяца (или с выбранной даты, не дальше года); дальше — с начала месяца, где последний загруженный день минус 3 дня | итоги месяца полные, поздние проводки не теряются, список выписок не разрастается |
| Не готова | банк готовит выписку асинхронно: ждём около 20 секунд, не готова — номер заказа сохраняется и программа заберёт её через 3 минуты, не заказывая заново | у банка свой темп |
| Разбор | транзакция переводится в поля формата 1С и проходит тот же классификатор и то же сопоставление, что и файл; вид документа «Банковские карты» — покупка по карте; только проведённые операции (Booked) | одни правила для файла и API |
| Дубли | по отпечатку операции и, для платежей с номером, по дате, сумме, номеру и ИНН — операция из файла и из API не задвоится; покупки по карте без номера по второму ключу не сравниваются | два одинаковых кофе в один день — разные операции |
| Секреты | client_secret, JWT-ключ, токены и идентификаторы счетов (с полным номером) — только зашифрованными (`services.secretbox`); в браузер — признаки «задан» и последние 4 цифры счетов; в журнал — без секретов | банковский доступ — самое чувствительное, что есть в программе |
| TLS | enter.tochka.com работает только на сертификатах Минцифры: корневой и выпускающий — в составе программы (`app/certs/russian_trusted_ca.pem`, отпечаток корневого сверен с двумя независимыми копиями); повтора без проверки сертификата нет | по этому каналу идут секреты |
| Сбои | банк недоступен или ограничил частоту — повтор через 30 минут; доступ отозван или истёк — «нужно подключить заново»; одна загрузка за раз; не больше трёх компаний за минуту | фоновая работа не должна мешать серверу |

**Эскалация напоминаний (T-67, [#52](https://github.com/Rimlin-UNC/1c_chek/issues/52)).** Модуль 5 видения владельца: личный
запрос (чек сотрудника, покупка по его карте) открыт дольше N дней — его видит и руководитель (роль «руководитель») и
общая почта клиента; в напоминании пункт отмечен «⚠» с именем сотрудника и числом дней, в журнале — «Передано
руководителю», один раз на запрос. N — настройка «Срок и напоминания», по умолчанию 3, 0 — не передавать. Возраст
запроса считается от момента напоминания, а не от часов сервера.

Тесты (только синтетика, в сеть не ходят): синтетический банк на `httpx.MockTransport` — вход по OAuth и привязка
компании, одноразовая отметка, продление токена и отказ, выписка «не готова», дубли с файлом, JWT-ключ и чужая компания,
права и проверка ввода, общее приложение сервера, фоновая загрузка и сбои банка, разбор транзакций, TLS; панель — в jsdom
и в браузере (Playwright). Код — `app/bank/tochka.py` (клиент банка), `app/bank/connect.py` (подключение и загрузка);
тесты — `tests/test_bank_api.py`, `tests/test_docreq_escalation.py`, `tests/js/bank_api.test.js`.

## Выгрузка в 1С (1.70.96): что выбрали и почему

Задача T-60 просила EnterpriseData — как у выгрузки чеков. Проверка показала, что одного его мало: наш пакет
EnterpriseData — упрощённый, типовая 1С без обработки или расширения (T-52) его не загрузит, а тестовой базы 1С
для проверки расширения нет. Зато в 1С:Бухгалтерии 3.0 есть типовая кнопка **«Покупки → Поступление (акты,
накладные, УПД) → Загрузить → Из файла»**: она принимает XML УПД в формате ФНС — так загружают документы из ЭДО
Лайт и от поставщиков без оператора ЭДО — создаёт поступление и предлагает сопоставить номенклатуру
([пример](https://infoblog.mywebguide.ru/articles/page_015330.html), [Инфостарт](https://forum.infostart.ru/forum8/topic255630/),
[Интеграция](https://integration-software.ru/blog/vygruzka-upd-schet-faktury-scheta-na-oplatu-v-formate-xml)).
Официальная схема ФНС 5.03 у нас уже есть (1.70.95), поэтому главный путь — **файл УПД, собранный из реестра и
проверенный по схеме до выдачи**; EnterpriseData и API для 1С тоже сделаны — по условиям задачи и для T-52.

| Вопрос | Решение | Почему |
|---|---|---|
| Откуда файл | собирается из реквизитов реестра | исходный XML не хранится (1.70.94), а у PDF, сканов и ручного ввода его и нет; так и бумажный документ попадает в 1С |
| Подписант | обязателен по схеме — ФИО «не указана / не указано», пояснение в «ДопСведПодп» | подписанта в реестре нет, выдумывать человека нельзя; файл — для своей 1С, юридической силы не имеет |
| Адреса, сведения о передаче, акциз | не пишутся | в схеме 5.03 необязательны, в реестре их нет |
| Что нельзя собрать честно | документ не выгружается, причина — в окне до скачивания | нет номера или даты, у продавца нет ИНН (иностранец), ИП без фамилии и имени, отрицательные суммы, ставка или валюта не из перечня |
| Повторы | постоянный ИдФайл по id документа; без отметок — только невыгруженные; повторно — только отмеченные вручную | 1С и бухгалтер видят тот же файл; повтор — осознанный |
| Ошибки проверки | по умолчанию не выгружаются, флажок «и документы с ошибками» | условие T-60 |
| Кодировка | windows-1251, как у файлов ЭДО; символы вне неё — ссылками `&#NNN;` | файл читается любой 1С |

Проверено тестами (только синтетика): каждый вариант (юрлицо, ИП, физлицо-покупатель, СЧФ, ДОП, исправление,
без НДС, 22/122, валюта) проходит официальную схему ФНС и читается обратно нашим разбором с теми же реквизитами;
сквозной путь «PDF печатной формы → сверка → файл для 1С»; браузерный сценарий скачивает файл и проверяет его.
Проверить загрузку в настоящую 1С без тестовой базы нельзя — **требует уточнения** (та же база нужна для T-52).

Код: `app/primary/export1c.py` (файл УПД, EnterpriseData, формат для 1С), маршруты — `app/primary/router.py`
(`/export/check`, `/export`) и `app/routers/onec.py` (`/onec/v1/primary/*`); тесты — `tests/test_primary_export.py`,
`tests/js/primary_export.test.js`.

## Решения по УПД (1.70.94)

- Исходный XML не хранится: только реквизиты, строки, итог проверки и отпечаток файла (SHA-256) — для поиска дублей.
- Документ с ошибками сохраняется со статусом «Ошибки»: его видно в реестре и можно разобрать с поставщиком. Не принимаются только титул покупателя, корректировочные документы (УКД) и файлы с неизвестной функцией.
- УПД, загруженный бухгалтером, попадает в его компанию, даже если покупатель в документе другой, — с замечанием. Администратор без выбранной компании получает компанию по ИНН покупателя, если она одна.
- Дубль — тот же файл или тот же документ: ИНН продавца, номер, дата и номер исправления; исправление — новый документ.
- Коды маркировки не сохраняются; подписи и печатные формы из архива пропускаются.
- Разбор XML — defusedxml без DTD; лимиты: файл 5 МБ, архив 20 МБ, распакованное 50 МБ, 50 документов за раз.
- Код: `app/primary/` (разбор и проверка — `upd.py`), экран — `app/static/js/primary.js`, тесты — `tests/test_primary_upd.py` и `tests/js/primary.test.js`.

## Комбайн первички (1.70.95): что взяли и почему

Условие владельца (04.11.2026): сервер 1 ГБ памяти и 2 ядра в Москве, полностью бесплатный контур, приём
и обработка УПД 5.03 только на локальных открытых компонентах; сравнить механизмы на GitHub и внедрить лучшее.
Это решение заменяет прежний план «готовый сервис распознавания» (T-54, ADR-23), см. ADR-25.

### Замеры (синтетический УПД, 2 ядра, Tesseract 5.5.3, модели tessdata_fast)

| Вход | Время | Пик памяти процесса | Итог |
|---|---|---|---|
| PDF с текстовым слоем | 0,1 с | 37 МБ | 10 из 10 полей, 3 строки, итоги |
| Скан 200 точек на дюйм | 1,5 с | 106 МБ | 10 из 10 полей |
| Скан 300 точек на дюйм | 1,8–2,1 с | 140–150 МБ | 10 из 10 полей |
| Фото (наклон 1,6°, размытие, шум, JPEG) | 1,5 с | 73 МБ | 9 из 10; неверный КПП помечен «проверьте» |
| Книжный скан альбомного УПД | 5,9 с | 121 МБ | 10 из 10, поворот найден сам |

Найдено замером и исправлено: автоматическая разметка Tesseract разносит подписи и значения по разным
блокам — строки собираются заново по координатам слов с поправкой на наклон; растяжение контраста на шумном
фото теряло строки — убрано; уверенность Tesseract на перевёрнутом листе обманчива — поворот выбирается по
опорным словам формы.

### Совет по серверу

- **1 ГБ и 2 ядер хватает**: XML и PDF почти ничего не стоят, скан — 1,5–2 с и до 150 МБ в отдельном
  процессе, по одному документу за раз. Это около 1 800 страниц в час — больше, чем нужно аутсорсеру.
- **Страховка за 0 ₽**: файл подкачки 1–2 ГБ (это советовала и концепция v1.60). Последний замер виден в
  «Первичке»: время и память распознавания на вашем сервере.
- **Увеличивать до 2 ГБ** — только если на этот же сервер переедет PostgreSQL, одновременно работают десятки
  пользователей или понадобится RapidOCR для плохих фото. Локальная LLM не окупается ни на каком разумном тарифе.

### Решения по комбайну (1.70.95)

- Черновик из PDF, скана или фото в базу не пишется: бухгалтер сверяет поля (неуверенные — с пометкой ⚠,
  ненайденные — пунктиром) и нажимает «Сохранить». При сохранении сервер проверяет всё заново.
- Подпись черновика (HMAC на секрете сервера, 24 часа) не даёт выдать ручной ввод за распознанный файл.
- Источник виден в реестре и карточке: файл ЭДО, PDF, скан или фото, введён вручную. Не-XML — «не электронный
  документ ЭДО: оригинал — на бумаге или в PDF».
- Сами файлы по-прежнему не хранятся — только реквизиты и SHA-256 (дубли). Хранение сканов требует решения
  о месте на диске и копиях — вопрос владельцу, когда понадобится архив.
- Несоответствие схеме ФНС — замечание, а не отказ: операторы ЭДО проверяют сами, а редакции схемы меняются.
- Подсказки названий: продавец — из прошлых документов, покупатель — из карточки компании («Подставить»).
- Распознавание — в отдельном процессе с пониженным приоритетом, одним потоком и тайм-аутом 150 с;
  одновременно один документ (файловая блокировка); до 5 страниц, картинка до 60 Мп.
- Модели скачивает администратор кнопкой «Скачать модели (8 МБ)»; каждый файл сверяется по хешу git-объекта.
  Если колесо tesserocr на сервере не встало, можно поставить пакеты `tesseract-ocr` и `tesseract-ocr-rus` —
  программа найдёт системный Tesseract сама.
- Код: `app/primary/schema.py` (XSD), `print_form.py` (печатная форма), `ocr.py` и `ocr_worker.py`
  (распознавание), `service.py` и `router.py` (черновик → подтверждение); схема — `app/primary/xsd/`
  (происхождение и хеши — `README.md` там же); тесты — `tests/test_primary_recognize.py`,
  `tests/js/primary_recognize.test.js`.

### Замер (синтетика, 2 ядра, GitHub Actions)

Инструмент — [`qa/ocr_bench.py`](../qa/ocr_bench.py), задание «OCR bench»
([`.github/workflows/ocr-bench.yml`](../.github/workflows/ocr-bench.yml)). Документы — только синтетика (ADR-14):
печатная форма УПД из `tests/fixtures/primary` в шести видах (скан 300 и 200 точек, фото с наклоном и тенью,
плохое качество, дефекты печати, лист боком) и искусственный кассовый чек. Каждый движок работает в своём
окружении и процессе на двух ядрах (`taskset`), в один поток: второй поток не ускорил ни один движок, только
удвоил процессорное время. Итог — поля черновика УПД после нашего разбора `print_form`, как их увидит бухгалтер.
«Тихая ошибка» — неверное значение без пометки «проверьте». Прогоны:

Второе прочтение: сначала Tesseract, затем ещё один движок. Поля сводит тот же `parse_variants`, что и в

По видам документов. На фото у Tesseract 7 полей из 10 и 58 % слов, у Tiny — 7 и 94 %, у Indra — 9, у Occular — 10.
На дефектах печати у Tesseract 7 полей, у Indra и Medium — 10. На чистых сканах у всех 9–10. Кассовый чек (ФН, ФД,
ФП, ИНН, итог, дата) все движки прочли целиком; слова — от 82 % (Tesseract, Indra) до 98 % (Medium).

Что ещё нашёл замер:
- Детектор RapidOCR по умолчанию работает на 2000 точках и держит до 900 МБ. На 1280 точках он находит те же
  строки примерно при 570 МБ.
- Рецепт из карточки модели (вход строки не уже 640 точек) стоит 0,8 с на страницу и даёт +3 поля.
- RapidOCR читает и лист боком, поэтому поворот надо определять по вертикальным строкам, а не только по опорным
  словам.
- Tesseract путает похожие буквы в номере: «YT-215» латиницей вместо «УТ-215». Это тихая ошибка, и её можно
  превратить в пометку «проверьте».

### Вывод и план (T-77)

- **Второе прочтение RapidOCR + PP-OCRv6 Tiny Cyrillic — выпущено в 1.70.109** (решение владельца 06.11.2026, Q-30; [ADR-39](ARCHITECTURE.md#adr-39)).
  - Всё под Apache-2.0, без порогов выручки. Модель весит 2,5 МБ, детектор уже лежит в колесе rapidocr.
  - Tesseract остаётся первым: он лёгкий, и разбор под него настроен. Второе прочтение запускается, только когда
    в черновике есть ненайденные или сомнительные поля.
  - На синтетике — 57 полей из 60 вместо 51 и 7 строк целиком из 18 вместо 1.
  - Цена для сомнительного документа — плюс 2,5 с и до 0,5 ГБ памяти в отдельном процессе (по одному документу,
    как сейчас). На диске — около 100 МБ (onnxruntime и rapidocr).
- **Не берём Occular.**
  - Пик 2,0–2,5 ГБ — больше всей памяти сервера.
  - Веса платные для организаций от 20 млн ₽ выручки или от 8 сотрудников.
  - PyMuPDF под AGPL, установка — 670 МБ.
- **Не берём Indra.**
  - Технически она сильна: 57 полей, 0,9 с.
  - Но веса нельзя использовать продукту, который конкурирует с любым продуктом Datalab, и лицензия
    распространяется на результат распознавания. Это не «некритичный лимит» по ADR-38, а ту же точность даёт
    свободная связка.
- **Не берём PP-OCRv6 Medium и приём «Tesseract + детектор».** Medium тратит 46 с на страницу на двух ядрах.
  Детектор для нашей формы полей не добавляет: строки мы уже собираем по координатам слов.
- **Дёшево и без нового движка.** Номер документа только из «похожих» латинских букв помечать «проверьте».
  Тихая ошибка станет видимой, а второе прочтение подставит верное значение.
- **Сервер.** Подкачка 2 ГБ. Второй движок — только в отдельном процессе под тем же замком «один документ за раз».
- **Настоящие документы** проверяются только на сервере владельца: последний замер в «Первичке» покажет время
  и память. Сами документы сюда не передаются (ADR-14).
- **Решение владельца (06.11.2026, Q-30): «Да, делать в 1.70.109».** Сделано — см. ниже.

### Как сделано в 1.70.109

- **Где решается.** `service.recognize_file` — одна точка для формы, почты и ботов. Tesseract читает первым. Если
  черновик не собрался или в нём не найдено либо под сомнением одно из полей «номер, дата, продавец, ИНН продавца,
  покупатель, ИНН покупателя, строки, итоги», `ocr.recognize(..., second=True)` перечитывает файл, и
  `print_form.parse_variants` сводит шесть вариантов текста.
- **Процесс.** Тот же `ocr_worker.py` с аргументом `second:<папка модели>`: RapidOCR в один поток, детектор на
  1280 точках, рецепт карточки модели (строка не уже 640 точек). Поворот листа — по вертикальным строкам и пробному
  чтению без классификатора переворота; наклон — по кромкам строк. Та же блокировка «один документ за раз»; второе
  прочтение ждёт её не дольше 5 с, иначе остаётся черновик Tesseract с пояснением.
- **Модель.** `data/ocr_models/ppocrv6_tiny_cyrillic`: `inference.onnx` (2 497 057 байт, SHA-256) и `rec_keys.txt`
  (SHA-1 git-объекта), ревизия `4ab2f138` репозитория `metrika-labs/PP-OCRv6_tiny_rec_cyrillic_onnx`; запасной
  источник — hf-mirror.com. Скачивает кнопка «Скачать модели» (или «Скачать модель (2,5 МБ)»). Сбой скачивания
  не мешает Tesseract.
- **Режим.** Настройка `ocr_second_reading`: `auto` (по сомнению, по умолчанию), `always`, `off`. Меняет
  администратор в «Первичке»; `PUT /api/v1/primary/ocr/second` пишет в журнал строку `primary_ocr_second`.
- **Зависимости.** onnxruntime и rapidocr в requirements.txt с маркерами Linux x86_64/aarch64 и Python 3.10+. Где
  колёс нет, pip пакеты пропускает, а панель пишет «не установлены модули».
- **Проверка.** Модульные тесты на подставных движках (`tests/test_v170109.py`); настоящие модели — в задании
  «OCR bench»: модель скачивает код программы, читает рабочий процесс (`worker_second`).
- **Замер рабочего пути на выпускном коммите `88a5af1`** ([OCR bench 42177688958](https://github.com/Rimlin-UNC/1c_chek/actions/runs/42177688958)). Код программы скачал
  обе модели Tesseract с api.github.com и модель PP-OCRv6 с huggingface.co, хеши сошлись. Второе прочтение
  рабочим процессом: 54 поля из 60, строки целиком — 9 из 18, пик 492 МБ, документ из одной страницы — 3,7 с вместе с
  загрузкой модели. Связка с Tesseract, как в программе: 57 полей из 60. Пометка латинского номера убрала тихую
  ошибку на фото: «YT-215» теперь с ⚠, а второе прочтение подставляет «УТ-215».
