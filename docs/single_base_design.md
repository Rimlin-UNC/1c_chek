## 2. Как сейчас

**Т1 — база уже одна.** Приложение работает с одной базой `data/ymaster_check.db` через один
движок `DATABASE_URL` ([`app/config.py`](../app/config.py), [`app/database.py`](../app/database.py));
файлы `db-*.db` — резервные копии ([`app/services/backups.py`](../app/services/backups.py)).
Supabase — отдельный демо-контур с синтетикой, не рабочая база ([ADR-10](ARCHITECTURE.md#adr-10)).
«Размножение» есть **внутри** базы: один чек может лежать в трёх таблицах — `receipts` (реестр
компании), `pool_receipts` (Чек-Пул) и `unified_documents` (единая запись с 1.70.82). Реестр и пул
остаются совместимыми проекциями ([ADR-06](ARCHITECTURE.md#adr-06)).

**Т2 — правило уже действует.** Администратор — всё; бухгалтер и руководитель — своя компания;
сотрудник — свои чеки; чек на разборе принадлежности — только администратор
([`app/services/scoping.py`](../app/services/scoping.py),
`can_view_document` в [`app/unified/service.py`](../app/unified/service.py),
[`rbac_matrix.md`](rbac_matrix.md)).

**У чека один владелец.** Уникальность ФН+ФД+ФП глобальная в каждой таблице:
`uq_receipt_fnfd_fp` ([`app/models.py`](../app/models.py)), `uq_pool_fn_fd_fp`
([`app/pool/models.py`](../app/pool/models.py)), `identity_key` в `unified_documents`; владелец —
одна строка `unified_ownership`.

**Чужой дубль не оставляет следа в учёте.** Сканирование чека, который уже есть у другой
компании, отклоняется: «Этот чек уже учтён в другой организации… попросите администратора
переместить его» — `/scan`, `/scan/image`, `/scan/pdf`, `/manual`
([`app/routers/receipts.py`](../app/routers/receipts.py)); перенос из пула в реестр чужой
компании — 409 ([`app/pool/transfer.py`](../app/pool/transfer.py)). В журнал `audit_log`
(с компанией и пользователем) попадает только `/scan` — событие `receipt_duplicate`.
Историческая пара (реестр у одной компании, пул у другой) уходит на разбор (#9).

**Т4/Т5 — счётчика нет.** [`app/services/receipt_merge_audit.py`](../app/services/receipt_merge_audit.py)
даёт только обезличенные итоги из командной строки.

**Т3 — замер 02.11.2026.** Временная база SQLite, 1000 чеков одной компании, штатный
`POST /api/v1/receipts/move` (лимит запроса — 1000 чеков, одна транзакция):

| Перенос | Время | На чек |
|---|---|---|
| Повторный (единые записи уже есть) | 4,9 с | ≈ 4,9 мс |
| Первый (с регистрацией в едином слое) | 9,6 с | ≈ 9,6 мс |

Профиль обработчика: **13 007 SQL-запросов на 1000 чеков** (≈ 13 на чек). Для каждого чека
заново перечитываются администратор и целевая компания (`_recheck_actor`, `_recheck_company`),
ищется единая запись (`document_for_source`), ставится блокировка тройки, пишется событие.

**Наблюдение по анонимности.** Карточка `GET /api/v1/unified/documents/{id}` отдаёт штатным
ролям компании-владельца журнал событий целиком: идентификаторы прежней и новой компании,
идентификатор исполнителя и текст причины решения спора, который пишет администратор
(`document_payload` в [`app/unified/service.py`](../app/unified/service.py)). Это сведения о
других организациях; до появления счётчика их нужно скрыть (фаза 0).

## 3. Варианты и выбор

### 3.1. Как хранить данные компаний

| Вариант | За | Против | Вывод |
|---|---|---|---|
| А. Отдельная база на каждую компанию | Сильная изоляция | Дубли между компаниями не найти без общей базы, счётчик невозможен, перенос — копирование между базами, N резервных копий и миграций | Отклонено: противоречит Т1, Т3, Т4 |
| Б. Схема на каждую компанию (PostgreSQL) | Изоляция средствами СУБД | Те же минусы; в SQLite недоступно | Отклонено |
| **В. Одна база, одна схема, колонка компании и одна точка правил видимости** | Дубль находится по `identity_key`, число — одним `GROUP BY`, перенос — одним `UPDATE`; так уже устроено | Изоляцию держит код — нужны тесты на каждое правило | **Выбрано.** После перехода на PostgreSQL (#11) можно добавить RLS вторым рубежом |

### 3.2. Сколько владельцев у чека

| Вариант | За | Против | Вывод |
|---|---|---|---|
| **1. Один владелец + заявки других компаний** | Чек учитывается в одной компании (1С, лимиты, пул, баллы — без изменений); попытки других компаний не теряются, а становятся заявками; перенос претенденту — одной кнопкой | «Использует» = владелец + претенденты, а не совместный учёт | **Рекомендовано** |
| 2. Совместное использование (каждая компания учитывает чек у себя) | Буквально «чек у нескольких компаний» | Двойной учёт расходов: один чек в 1С двух организаций — налоговый риск для клиентов, обход антифрода и лимитов. Нужно снять глобальную уникальность `receipts` (ломает откат на 1.70.80–1.70.83) или перевести реестр, 1С, отчёты и лимиты на новую таблицу | Не рекомендовано |
| 3. Вариант 1 + «совместный просмотр» по решению администратора (второй компании — только чтение, без выгрузки в 1С) | Покрывает редкие законные случаи | Ещё одна сущность прав | Только если владелец подтвердит потребность; модель варианта 1 это допускает без переделки |

### 3.3. Что считать «компания использует чек»

| Вариант | Вывод |
|---|---|
| Только текущий владелец | Почти всегда 1 — бесполезно |
| **Владелец + претенденты** (кто пытался учесть чек, в том числе отклонённые) | **Рекомендовано**: сигнал антифрода — один чек пытаются провести несколько организаций |
| + прежние владельцы (после переноса) | Переносы-исправления дают шум; администратор всё равно видит прежних владельцев в списке. Включать — по решению владельца (Q-19) |

Администратор может пометить связь «не учитывать» (например, сотрудник ошибся компанией) —
она остаётся в истории, но не входит в число.

### 3.4. Кто и как видит число

- **Режим** — общая настройка: «выключено» (по умолчанию) · «всем компаниям» · «выбранным
  компаниям» (флаг в карточке компании). Рекомендую «выбранным» (Q-20).
- **Роли в разрешённой компании:** бухгалтер и руководитель; сотрудник — по решению владельца
  (Q-21, рекомендую нет); участник-донор, гость и клиент платного API — никогда.
- **Что видно компании:** только число на **своём** чеке («Организаций: 2», включая свою) — без
  названий, ИНН, дат и ролей. Если показ не разрешён, поля в ответе API нет вовсе.
- **При отказе в сканировании** — прежний текст и «администратор увидит вашу заявку» (Q-22), но
  без числа: иначе по фото чужого чека можно было бы узнать число претендентов.
- **Пределы анонимности.** Число 2 неизбежно значит «есть ещё одна организация» — это и
  требовалось. Даты чужих попыток не показываются, чтобы их нельзя было сопоставить; журнал
  карточки для штатных ролей обезличивается (фаза 0).
- **Администратор:** число, а также список компаний с ролью (владелец · претендент · прежний
  владелец), источником (скан QR, фото, PDF, ручной ввод, пул, архив), числом попыток, датами и
  статусом. Действия: «передать претенденту», «отклонить», «не учитывать».

### 3.5. Перенос: проще и быстрее

- **Проще.** Претенденты приходят к администратору сами: на экране «Разбор конфликтов»
  появляется вкладка «Заявки», и чек передаётся претенденту одной кнопкой. Это одна транзакция:
  меняются владелец, проекции реестра и пула, статус заявки, пишется событие. Сотруднику больше
  не нужно искать администратора, а администратору — искать чек.
- **Быстрее.** Перенос идёт пачкой, а не по одному чеку:
  - права и целевая компания проверяются один раз;
  - единые записи выбираются одним запросом;
  - тройки блокируются одним запросом в порядке ключа, без взаимных блокировок;
  - владельцы, реестр и пул обновляются по одному запросу на каждую таблицу;
  - события пишутся одной вставкой.

  Вместо ≈ 13 000 запросов на 1000 чеков получается порядка десятков. Цель приёмки — не больше
  0,5 с на 1000 чеков на SQLite, с замером в тесте. Правила прежние, всё выполняется в одной
  транзакции. Если в пачке есть чек на разборе, отклоняется вся пачка с ответом 409 «Чек
  требует разбора перед перемещением» — так работал и прежний цикл. (В первой редакции здесь
  было «чек пропускается с понятной причиной» — это неточно; пропуск с причиной меняет
  поведение и требует отдельного решения.) Итог — в [разделе 9](#9-фаза-0-сделано-t-32-t-33).

## 4. Модель данных — только добавления ([ADR-03](ARCHITECTURE.md#adr-03))

### 4.1. Таблица `unified_company_links`

Связь «компания ↔ чек», кроме владельца.

| Поле | Назначение |
|---|---|
| `id` | Ключ |
| `document_id` | Единая запись (внешний ключ на `unified_documents`) |
| `company_id` | Компания; без внешнего ключа, как в `unified_ownership` ([ADR-09](ARCHITECTURE.md#adr-09)) |
| `kind` | `claim` (претендент) · `former_owner` (прежний владелец) |
| `status` | `open` · `declined` · `transferred` · `void` (не учитывать) |
| `source` | `scan_qr` · `scan_image` · `scan_pdf` · `manual` · `pool_transfer` · `archive_twin` · `move` |
| `attempts`, `first_at`, `last_at` | Сколько раз и когда пытались учесть |
| `first_user_id`, `last_user_id`, `decided_by`, `decided_at` | Кто пытался и кто решил |

Уникальность — `(document_id, company_id)`; индексы — по `company_id` и `status`. Фискальных
значений и персональных данных в таблице нет ([ADR-12](ARCHITECTURE.md#adr-12)). Повторная
попытка той же компании увеличивает `attempts` — одной операцией вставки или обновления,
одинаково в SQLite и PostgreSQL.

### 4.2. Владелец, настройки, откат и наполнение

- **Владелец** по-прежнему одна строка в `unified_ownership`. Число = 1 за владельца + связи,
  которые учитываются по правилу из п. 3.3.
- **Настройки:** ключи `app_settings` — режим показа и роли; колонка
  `companies.show_companies_count` (логическая, по умолчанию «нет») добавляется через
  `_ensure_schema`.
- **Запись заявки не ломает сканирование.** Она идёт в точке сохранения (SAVEPOINT), как
  синхронизация с ФНС ([ADR-07](ARCHITECTURE.md#adr-07)): при сбое сотрудник получает прежний
  ответ, а причина уходит в журнал. Если чек владельца ещё не в едином слое, он сначала мягко
  регистрируется (тот же механизм, что при первой правке).
- **Откат на 1.70.80–1.70.83 безопасен.** Старый код не читает новую таблицу, а колонка со
  значением по умолчанию ему не мешает. Сверка при старте (`app.unified.reconcile`) закрывает
  связи удалённых компаний. Разбор спора ([#9](https://github.com/Rimlin-UNC/1c_chek/issues/9))
  оставляет проигравшей компании связь `claim/declined`, чтобы число не терялось.
- **Наполнение задним числом.** Без запросов в ФНС:
  - события `receipt_duplicate` из `audit_log` — только сканы QR, остальные пути журнал не
    пишет;
  - исторические пары пул ↔ реестр.

  Компания попытки сравнивается с текущим владельцем — это приближение, оно оговаривается в
  отчёте наполнения.

## 5. API и экраны

- **Администратор:**
  - `GET /api/v1/unified/documents/{id}/companies` — число и список;
  - `POST …/links/{link_id}/transfer`, `/decline`, `/void` — с `expected_version` и
    обязательной причиной, как на экране разбора;
  - `GET /api/v1/unified/claims` — входящие заявки и значок у пункта меню;
  - колонка и фильтр «Организаций» в реестре.
- **Компании:** поле `companies_count` в списке реестра и в карточке чека — только при
  разрешении и подходящей роли. Число считается одним агрегирующим запросом на страницу,
  без N+1.
- **Обезличивание журнала карточки** для штатных ролей: свои компании и сотрудники видны,
  чужие — «другая организация», причина решения скрыта.
- **Платный API (B2B)** — отдельный контур ([`b2b_access.md`](b2b_access.md)): ни числа, ни
  списка не получает.

## 6. Безопасность и 152-ФЗ

- Рабочая база остаётся на сервере владельца. Supabase (eu-west-1) — только синтетический
  демо-контур; рабочие данные и ПДн туда не переносятся ([ADR-10](ARCHITECTURE.md#adr-10),
  [ADR-12](ARCHITECTURE.md#adr-12)). Если база переедет на PostgreSQL (#11), то только с
  размещением в РФ; конкретный хостинг — **требует уточнения** у юриста.
- По умолчанию всё закрыто. Права проверяются по текущему состоянию базы, а не по токену — как
  `can_view_document`.
- Изменения настроек и решения по заявкам пишутся в `audit_log` и `unified_events` без
  фискальных значений.
- **Обязательные тесты:**
  - компания без разрешения не получает поля;
  - компания с разрешением получает только число;
  - сотрудник видит только свои чеки, донор — ничего;
  - число доступно только по своим чекам, перебор чужих невозможен;
  - журнал карточки не содержит чужих идентификаторов и причины решения.

### 9.1. Пакетный перенос (T-33)

`POST /api/v1/receipts/move` вызывает `move_registry_receipts` ([`app/unified/service.py`](../app/unified/service.py)):
- тройки ФН+ФД+ФП блокируются пачкой в порядке ключа (`lock_identities` в
  [`app/services/receipt_identity.py`](../app/services/receipt_identity.py)): встречные пачки
  не ждут друг друга по кругу;
- новые полные тройки регистрируются вставкой пачкой; неполные и уже известные записи (из пула)
  идут прежним `register_source(strict=True)` по одному чеку;
- `move_documents` выбирает записи, владельцев и источники пачками, права и компанию назначения
  проверяет один раз, события пишет одной вставкой;
- политика расходов и правила поставщиков пересчитываются пакетно (`refresh_receipts`,
  `apply_rules_many`): сумма месяца — один запрос на компанию.

**Поведение — как у прежнего цикла.** Тест сравнивает итоговое состояние базы после пакетного
переноса и после копии прежнего цикла из `59fac17` на одинаковой смешанной пачке: новая и уже
зарегистрированная запись, пуловая копия, запись из пула, неполная тройка, висячий источник,
чеки уже в компании назначения (в том числе на разборе), позиции, статус ФНС, лимиты, правило
поставщика. Чек на разборе в пачке — ответ 409, изменения не сохраняются.

**Одно исправление.** Сессия работает без autoflush, и прежний цикл не сохранял нового
подотчётного лица последнего чека до пересчёта политики: месячный лимит видели не все чеки
пачки. Теперь перед пересчётом выполняется `flush`, и пометка у всех чеков совпадает с
`policy.flags_for` (тест `test_bulk_move_assignee_counts_every_moved_receipt`).

**Замеры** (SQLite, 1000 чеков, песочница, 02.11.2026):

| Что | Было | Стало |
|---|---|---|
| Повторный перенос, HTTP | 4,9 с | 0,36–0,48 с |
| Первый перенос с регистрацией, HTTP | 9,6 с | 0,56–0,82 с (0,82 — с 5 позициями на чек) |
| SQL-операций на 1000 чеков | ≈ 13 000 | 24–26 повторный, 36–50 первый |
| Обработчик без HTTP (тест) | — | 0,65 с первый, 0,37 с повторный |

Число SQL-операций не зависит от размера пачки: 28 при первом и 18 при повторном переносе и для
20, и для 200 чеков (`test_bulk_move_statement_count_does_not_grow_with_batch`). Тест времени
держит потолки 3 с и 2 с — с запасом на CI (`-j4`); прежний цикл их не проходит. На PostgreSQL
17 две встречные пачки по 6 чеков проходят без взаимной блокировки (8 прогонов подряд,
`test_postgres_bulk_move_concurrent_batches`).

### 9.2. Журнал карточки без чужих организаций (T-32)

`GET /api/v1/unified/documents/{id}` и список `GET /api/v1/unified/documents` для бухгалтера и
руководителя (`document_payload(..., viewer=...)`):
- своя компания и сотрудники своей компании видны как есть;
- чужая компания, её сотрудник и администратор платформы заменены на `null` с признаком
  `from_company_hidden`, `to_company_hidden`, `actor_hidden`, `created_by_hidden`;
- в `details` событий остаются только ключи без сведений о других организациях:
  `source_kind`, `created`, `resolved_ownership`, `remaining_origins`, `company`, `author`;
- причина сверки остаётся, если это код (`source_deleted`, `projection_changed`); свободный
  текст причины решения спора не отдаётся.

Администратор видит карточку как раньше. Экраны не менялись: единый реестр в интерфейсе есть
только у администратора (`app/static/js/unified_review.js`).
