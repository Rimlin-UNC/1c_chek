# Аудит готовых решений доступа к Telegram Bot API через Cloudflare Workers (v1.70.68)

Дата: 2026-10-30. Отчёт по заданию № 1 технического задания «Внедрение
отказоустойчивого доступа к Telegram API в проект chek ymaster.ru».

Ограничения ТЗ: сервер в Москве (Ubuntu 24.04), прямые запросы к
`api.telegram.org` блокируются или нестабильны; второй зарубежный сервер
категорически запрещён; единственный допустимый внешний посредник —
Cloudflare Workers (бесплатный тариф).

## Поиск

Ключевые слова из ТЗ: `telegram api proxy cloudflare worker`,
`tgwsapiproxy`, `telegram bot api proxy dpi bypass russia`. Обязательные
четыре кандидата проанализированы по коду репозиториев (README и исходники
воркеров получены через `api.github.com`); поиск дополнительно вывел ещё
два примечательных репозитория — они включены в сравнение.

## Кандидаты

### 1. winchanii/TgWsApiProxy (пакет `tgwsapiproxy`)

Схема: бот → локальный прокси (SOCKS5 порт 1080 и HTTP CONNECT порт 8080,
слушает только `127.0.0.1`) → воркер (WebSocket-релей на сырой TCP) →
`api.telegram.org`. Приём из `tg-ws-proxy` (Flowseal), но для обычного
HTTPS Bot API вместо MTProto.

Плюсы:

* белый список в воркере: `ALLOWED_HOSTS` (`api.telegram.org` и
  `149.154.166.110`) плюс `ALLOWED_PORTS` (только 443) — требование ТЗ §6;
* сквозной TLS: рукопожатие с `api.telegram.org` выполняет сервер, воркер
  ретранслирует шифрованные байты и НЕ видит токен бота и содержание;
* DPI на участке сервер → Cloudflare видит только SNI домена
  `workers.dev`;
* нулевые зависимости пакета (только стандартная библиотека) — ставится
  из Git даже когда PyPI заблокирован; нужен Python 3.11+ (в Ubuntu 24.04
  это 3.12);
* диагностика: эндпоинты воркера `/diag` (проверка `connect()` и `fetch()`
  с объяснением, что именно запретил тариф) и `/healthz`;
* CLI: `--listen-host` (по умолчанию только локальный интерфейс),
  `--http-port`, `--allow` (по умолчанию только `api.telegram.org`);
* лицензия MIT — вендоринг `worker.js` в наш репозиторий законен.

Минусы:

* молодой проект: версия 0.1.0, статус бета;
* не опубликован на PyPI — установка только из Git;
* воркер — WebSocket-релей, сложнее простого реверс-прокси (это цена
  белого списка и сквозного TLS).

### 2. 4n0nymou3/Telegram-API-Proxy

Схема: реверс-прокси — в коде бота адрес `api.telegram.org` заменяется на
адрес воркера (наш вариант: поле «Адрес API» в настройках).

Плюсы: простейшая интеграция; подробные инструкции (дашборд и wrangler);
работает с любым HTTP-клиентом.

Минусы: воркер на 1041 строку со встроенной документацией — тяжело
аудировать; белого списка нет; TLS терминируется на воркере — токен бота
виден в контексте воркера; диагностики нет.

### 3. kushagra-goyal-14/telegram-bot-cloudflare-proxy

Схема: лёгкий реверс-прокси (`index.js`, 64 строки), цель захардкожена на
`api.telegram.org`.

Плюсы: минимальный код, легко проверить глазами; благодаря хардкоду не
превращается в открытый прокси.

Минусы: белого списка как механизма нет; токен виден воркеру; нет
аутентификации и ограничения частоты; нет диагностики.

### 4. tuanpb99/cf-worker-telegram

Схема: прозрачный реверс-прокси плюс пересылка вебхук-обновлений на сервер
владельца (константа `BOT_UPDATE_FORWARD_URL`).

Плюсы: все методы Bot API, загрузка файлов (multipart), CORS, встроенная
страница документации; поддержка вебхуков.

Минусы: белого списка нет; токен виден воркеру; вебхуки нам не нужны —
программа работает через long-poll; требует правки константы пересылки.

## Выбор (задание № 2 ТЗ)

Выбран `winchanii/TgWsApiProxy`. Рекомендация ТЗ подтверждена аудитом:

1. единственный кандидат с белым списком на стороне воркера — обязательное
   требование ТЗ §6, иначе открытый прокси и бан аккаунта Cloudflare;
2. единственный, у которого посредник не видит токен бота: TLS сквозной,
   воркер ретранслирует шифрованный TCP;
3. нулевые зависимости — установка возможна даже при заблокированном PyPI;
4. локальный слушатель по умолчанию только на `127.0.0.1` (ТЗ §5.3 —
   порты не открывать наружу);
5. HTTP CONNECT нативно поддерживается `httpx` — клиентский код программы
   менять не нужно: поле прокси существует с v1.29.0 (настройки или
   `TELEGRAM_PROXY` в окружении);
6. встроенная диагностика воркера плюс наш скрипт `check_proxy.sh`
   закрывают мониторинг (ТЗ §6);
7. MIT — `worker.js` вендорится в `deploy/tg-cf-worker/worker.js` без
   изменений кода (добавлена только шапка с источником и предупреждением
   не убирать белый список).

Минусы (молодость проекта, установка из Git) компенсированы: `worker.js`
зафиксирован в нашем репозитории, установка из Git зафиксирована в
`install.sh`, падение локального прокси лечится `Restart=always` в юните
systemd.

## Аудит интеграции (задание № 3.1 ТЗ)

Стек программы: Python 3.11+, FastAPI, `httpx`. Библиотеки aiogram и
python-telegram-bot НЕ используются — примеры из ТЗ неприменимы буквально,
принцип тот же: прокси передаётся в HTTP-клиент.

Единственное место, где программа трогает `api.telegram.org` —
`app/services/telegram_bot.py`:

* `origin = get_api_base(db)` — поле «Адрес API» в настройках или
  `TELEGRAM_API_BASE` в окружении, по умолчанию официальный адрес;
* `proxy = get_proxy(db)` — поле «Прокси» в настройках или `TELEGRAM_PROXY`
  в окружении; передаётся в `httpx.post(..., proxy=...)` во ВСЕХ вызовах:
  отправка сообщений (`api()`), long-poll воркер, диагностический пинг.

Вывод: интеграция сводится к настройке — в поле «Прокси» указывается
`http://127.0.0.1:8080`. Клиентский код не меняется. Патч программы в этом
выпуске: подсказка в настройках Telegram (ведёт к комплекту), сам комплект
`deploy/tg-cf-worker` и этот отчёт.

## Требования ТЗ §6 — как закрыты

* Белый список: `ALLOWED_HOSTS` и `ALLOWED_PORTS` в вендоренном
  `worker.js`; предупреждение «не убирать» — в шапке файла и в README
  комплекта.
* Мониторинг: `check_proxy.sh` — служба активна, слушатели только на
  локальном интерфейсе, `api.telegram.org` отвечает через прокси, воркер
  жив (`/healthz`, `/diag`); плюс диагностика в самой программе (пинг
  измеряется через настроенный прокси — ровно путь бота); журнал службы —
  `journalctl -u tgwsapiproxy`.
* Отказоустойчивость: юнит systemd с `Restart=always` и `RestartSec=3`
  (graceful restart при падении), усиление `NoNewPrivileges`,
  `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`; служебный
  пользователь `tgproxy` без оболочки входа.
