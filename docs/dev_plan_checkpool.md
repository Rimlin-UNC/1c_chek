# План разработки «Чек-Пул» — аккуратное внедрение концепции docs/plan.md

> Разработчик и владелец идеи: ООО «Ямастер» · https://ymaster.ru · info@ymaster.ru
> Статус: утверждаемый план · база: v1.29.0 · концепция: `docs/plan.md` (авторская, 2026-10-06)

---

## 0. Как читать этот документ

`docs/plan.md` — дизайн-документ концепции «Чек-Пул»: открытая краудсорсинговая
база фискальных чеков. «Залётные» пользователи сдают чеки (бот/веб/PWA) за
баллы; компании-клиенты ищут и забирают чеки из пула; оператор видит аналитику
по географии и отраслям; рефералы и 5-слойный антифрод защищают экономику.

Этот документ отвечает на вопрос **«как внедрить это в наш работающий продукт,
не сломав его»**: что берём из концепции, в каком порядке, что переиспользуем,
какие у нас есть отклонения от плана и почему.

---

## 1. Принципы внедрения (не ломаем основную программу)

1. **Отдельный контур.** Пул живёт в своих модулях (`app/pool/…`), своих
   таблицах (префикс `pool_`) и своих роутах (`/api/v1/public/*`,
   `/api/v1/pool/*`). Ни одна существующая таблица, эндпоинт и экран не
   меняются. Ядро (чеки, 1С, АО-1, роли) остаётся как есть.
2. **Флаги на всё.** Каждый этап включается настройкой (`pool_enabled`,
   `pool_public_form`, …). Выключено по умолчанию → деплой безопасен: продакшн
   продолжает работать ровно как раньше, включаем когда проверили.
3. **Переиспользуем готовое** (у нас уже есть ~80% фундамента):
   | Из концепции | Что уже есть у нас |
   |---|---|
   | Приём QR, парсер t=…&s=…&fn=… | `app/routers/receipts.py::scan` + `_parse_qr` |
   | Получение данных из ФНС/источников | движок источников `external.py` (fns_api GetTicket, fns_app, crpt — без квот!) |
   | Дедупликация по ФН+ФД+ФП | уникальность чеков в ядре + проверка `verify` |
   | Классификация по отраслям (словари) | статьи расходов (v1.28.0, `GET /receipts/categories`) как затравка |
   | Telegram-канал | бот v1.16.0/1.29.0 (прокси, привязка, long-poll) |
   | Админ-аналитика | дашборд, CSV-экспорт, живые события |
   | Антифрод-минимум | rate-limit, login_guard, аудит `log_action` |
4. **Миграции только добавляющие.** Новые таблицы создаются `init_db()`
   (SQLite/Postgres совместимо); никаких ALTER существующих таблиц. Привязка
   пула к компании — через `assigned_company_id` в самой таблице пула.
5. **Каждый этап = релиз** с полным прогоном тестов (сейчас 418), харнессом
   (47 PASS), CHANGELOG/WHATS_NEW/инструкцией и возможностью откатиться
   (бэкапы БД уже автоматические, `daily_backup`).
6. **152-ФЗ с первого дня:** в пуле храним только фискальные данные и
   анонимные ID; согласие с офертой — чек-бокс с записью факта; phone/email —
   только по необходимости (вывод баллов).

## 2. Архитектура в нашем коде

```
app/
  pool/
    __init__.py
    models.py          # PoolReceipt, PoolItem, PoolUser, PoolPoints, PoolSignal…
    schemas.py         # Pydantic-контракты публичного API
    ingest.py          # пайплайн: приём → источники → дедуп → гео → отрасль → статус
    enrich_geo.py      # адрес места расчёта → регион/город (справочник РФ, офлайн)
    enrich_industry.py # ОКВЭД/название магазина → отрасль (словари, позже ML)
    antifraud.py       # слои: лимиты, дубликаты, подсети, поведенческие правила
    router_public.py   # /api/v1/public/*  (форма, мои чеки, баллы, лидерборд)
    router_company.py  # /api/v1/pool/*     (подбор, привязка, квота)
    router_admin.py    # /api/v1/pool-admin/* (дашборд, модерация, сигналы)
  static: отдельные страницы SPA: #/public (форма+кабинет), #/pool (у компании)
```

- **Публичная часть — без обязательной регистрации**: анонимный
  `PoolUser` создаётся при первой сдаче чека (tg_user_id / cookie-токен /
  email по желанию). Регистрация с паролем — следующий этап (план.md, раздел 1
  второй части).
- **Данные чека в пул попадают уже обогащённые**: движок источников (v1.27.0)
  отдаёт позиции/ИНН/адрес места расчёта без единой квоты proverkacheka.
- **Гео**: адрес места расчёта из чека (ФФД 1.05+) → справочник регионов/городов
  РФ (офлайн-JSON в `app/pool/geo/`, обновление раз в месяц). Fallback — ИНН →
  Checko (ключ уже есть в настройках) → юр. адрес с флагом `geo_accuracy=low`.
- **Отрасли**: справочник из plan.md (Продукты/Стройка/Авто/Аптека/…),
  сопоставление по ОКВЭД (Checko) и словарю названий сетей; ML (FastText) —
  только на этапе 6, когда наберётся размеченный корпус из статей расходов.

## 3. Дорожная карта (этапы = версии)

### Этап 0 — v1.29.0 (сделано): фундамент надёжности
Прокси и диагностика Telegram (бот — главный канал пула, обязан работать из РФ),
честные полные данные из ФНС/ЧЗ без квот (v1.26–1.27), статьи расходов (v1.28)
как семя классификатора.

### Этап 1 — v1.30.0 «Пул: модель и приём через бота» — ✅ ВЫПОЛНЕН (v1.30.0, 2026-10-06)
> Смогла: таблицы pool_* (UNIQUE fn+fd+fp), пайплайн ingest (дедуп → лимит 50/сут → движок
> источников → статус+баллы), бот: QR строкой → мгновенный ответ, /balance, оферта в /start;
> админка /api/v1/pool-admin/* + карточка «🧩 Чек-Пул» в Настройках; флаг pool_enabled.
> Фото QR и веб-форма — Этап 2. Живой смоук и 17 автотестов пройдены.
- Таблицы `pool_receipts`, `pool_users`, `pool_points` (+ индексы из plan.md);
  UNIQUE (fn, fd, fp).
- Бот: переслал/отправил QR-строку или фото → бот отвечает «чек принят, +1
  балл, у вас N» за ≤5 с (анонимный PoolUser по tg_user_id, согласие офертой
  командой /start).
- Пайплайн `ingest.py`: QR → движок источников → дедуп → статус `verified`
  (без гео/отрасли — на втором проходе). Аномалии → `pending`.
- Настройка `pool_enabled` (выкл. по умолчанию), раздел в админке.
- Критерий приёмки: полный прогон зелёный; чек из Telegram появляется в
  `pool_receipts` с позициями; дубль не создаётся; существующие чеки и 1С не
  затронуты (тесты неизменности: все старые тесты без правок).

### Этап 2 — v1.31.0 «Публичная форма + кабинет /my» (≈1 неделя)
- Страница `#/public` на chek.ymaster.ru: drag&drop фото QR (jsQR уже в
  проекте), вставка ссылки из приложения ФНС, ручной ввод реквизитов.
- Кабинет: баллы, история чеков (PDF/CSV), реферальный код, оферта.
- Анонимная идентификация: подписанная cookie (существующий механизм
  секретов); email опционален.
- Критерий: форма работает с телефона; у бота и формы общий баланс баллов.

### Этап 3 — v1.32.0 «Гео и отрасли» (≈1 неделя)
- Справочники регионов/городов РФ (офлайн), гео-пайплайн с `geo_accuracy`.
- Справочник отраслей + словари сетей; классификация чека по доминирующей
  отрасли позиций; позиции — нормализация имён.
- Админка: счётчики, топ городов/отраслей, чеки без гео/отрасли.
- Критерий: ≥70% новых чеков имеют регион; ≥60% — отрасль.

### Этап 4 — v1.33.0 «Антифрод: слои 1–3, 5» (≈1 неделя)
- Лимиты на пользователя/подсеть/магазин (план.md, раздел 9 «Business rules»),
  дедуп с половинными баллами, «ферма аккаунтов» по device/IP-кластерам,
  honeypot-поля публичной формы, события `pool_signals`.
- `risk_score`/`trust_level` по упрощённой таблице весов; карантин вместо бана.
- Критерий: сценарии «ферма аккаунтов» и «накрутка чеками» из plan.md
  отсекаются автотестами; ложных блокировок на ручных сценариях нет.

### Этап 5 — v1.34.0 «Подбор из пула для компаний» (≈1 неделя)
- Раздел «Подбор из пула» (бухгалтер): фильтры период/регион/отрасль/сумма/ИНН,
  привязка чеков к компании (`assigned_company_id`), выгрузка в CSV.
- Квоты/тариф: счётчик подобранных чеков (подписка/pay-per-receipt — решение
  при запуске), целостность: привязанный чек больше не виден другим.
- Критерий: привязанные чеки попадают в подбор АО-1 без изменения формата
  выгрузки 1С (отдельный путь, ядро не трогаем).

### Этап 6 — v1.35.0+ «Рефералы с порогами, лидерборд, ML» (далее)
- Пороговая рефералка с задержками (0 за регистрацию, бонусы за 1-й/5-й/20-й
  верифицированный чек + lifetime 5% с потолком) — строго по разделу 2 plan.md.
- Лидерборд по городам, ачивки.
- ML-классификатор позиций (FastText) — когда корпус ≥5–10 тыс. позиций из
  статей расходов; до этого словари.
- Граф-аналитика связей (рекурсивные CTE) и `/admin/fraud`-панель.

## 4. Риски и как мы их закрываем

| Риск | Митигация |
|---|---|
| Блокировка Telegram на сервере | решено в v1.29.0 (прокси + диагностика) |
| Квоты/баны источников при потоке пула | цепочка без квот: fns_api(GetTicket) → fns_app → crpt; лимиты и «остывание» движка; поток пула — асинхронно (фоновая очередь) |
| 152-ФЗ | только фискальные данные; оферта+факт согласия; анонимные ID; IP/фingerprint — не дольше 12 мес |
| Накрутка баллов | пороговая рефералка, risk_score, задержки выплат, лимиты |
| Нагрузка на основную БД | таблицы пула отдельно; тяжёлая аналитика — фоновыми задачами; Postgres в бою |
| Регрессия ядра | флаги по умолчанию выкл.; каждый этап не меняет существующие тесты; бэкап перед миграцией |

## 5. Метрики (с первого этапа)

DAU сдающих; % повторных сдач; покрытие регионов/городов; % с отраслью;
% с точным гео; доля чеков, востребованных компаниями; % отклонённых
модерацией. Цели 6 месяцев — по plan.md (50 000 чеков, 40 регионов, 200 городов).

## 6. Что НЕ делаем (осознанно)

- Не встраиваем пул в таблицы ядра (`receipts`) — только ссылка по
  `assigned_company_id` и раздельные отчёты.
- Не делаем многоуровневую рефералку и «бонус за регистрацию».
- Не продаём сами чеки — только доступ к фильтрам/выгрузке (юридически чище).
- Не вводим Celery/Redis на старте — фоновые потоки FastAPI справятся на
  текущих объёмах; ARQ — при росте (отдельное решение).
