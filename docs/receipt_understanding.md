# Понимание чеков: читаемые позиции и категории по отраслям (T-69, v1.70.101)

Запрос владельца 05.11.2026: улучшить читаемость чеков и распределение категорий по отраслям; взять готовые решения
(nlp_in_practice_receipts — FastText; Data-Fusion-Contest-Goodsification — Word2Vec + TF-IDF + CatBoost) и встроить их
с учётом условий: текст позиций приходит из API ФНС (без OCR), сервер — 2 ГБ ОЗУ, внешних сервисов нет (ADR-25).
Задача — [#54](https://github.com/Rimlin-UNC/1c_chek/issues/54); решение — [ADR-31](ARCHITECTURE.md#adr-31).

## Исследование готовых решений (05.11.2026)

- [`xterrafunny/nlp_in_practice_receipts`](https://github.com/xterrafunny/nlp_in_practice_receipts) — соревнование ODS
  «структуризация чеков ОФД»: выделение и нормализация **бренда и товара** из строки позиции; FastText там — векторы
  слов для базового решения.
- [`Irinas5555/Data-Fusion-Contest-Goodsification…`](https://github.com/Irinas5555/Data-Fusion-Contest-Goodsification--18-place-on-public-liderboard-)
  и [`Tytskiy/VTB-Data-Fusion-Goodsification`](https://github.com/Tytskiy/VTB-Data-Fusion-Goodsification) — ВТБ Data Fusion
  2021: категория товара по 800 тыс. размеченных чеков; TF-IDF и Word2Vec + линейная модель, затем «тип чека»
  (преобладающая группа товаров в чеке) и CatBoost; второй репозиторий — псевдоразметка.
- **Лицензий нет** ни у одного репозитория: код не копируем, берём подходы. **Данных в репозиториях нет**: они на
  площадках соревнований с условиями «только для соревнования».
- Законный источник названий — **ОКПД2** (ОК 034-2014, Росстат): документ госоргана не охраняется авторским правом
  (ГК РФ, ст. 1259, п. 6). Машиночитаемая копия — [`prog815/okpd2`](https://github.com/prog815/okpd2) (выгрузка архива
  Росстата от 01.10.2026, 21 081 запись).

**Вывод.** От nlp_in_practice — нормализация названия (товар, марка, фасовка); от FastText — модель на символьных
n-граммах (понимает сокращения и опечатки, весит сотни килобайт); от Data Fusion — признак «тип чека». CatBoost и
Word2Vec не берём: память и процессор сервера, а главное — нет размеченных чеков, ради которых они нужны.

## Как устроено (1.70.101)

**Каскад** (`app/goods/service.py`) — первая уверенная ступень даёт категорию:

1. **Память компании** — бухгалтер уже менял категорию этого товара («как отметил бухгалтер для этого товара»).
   Таблица `goods_memory`: компания, ключ товара, категория (ADR-20 — только в своей компании).
2. **Признак ФНС** — работа или услуга (тег 1212); вид услуги — по словарю услуг, иначе по модели.
3. **Словарь** — 37 категорий внутри прежних 19 групп, 1,4 тыс. признаков с исключениями; услуга в начале названия
   («Аренда бетономешалки», «Ремонт телефона») проверяется первой. Словарь задаёт группу; вид товара внутри группы
   уточняет модель, если уверена на 90 % и больше («ГРУНТОКВА ЦЕРЕЗИТ» — марка дала стройку, модель — грунтовку).
4. **Модель** (`app/goods/model.py`) — слова и символьные n-граммы 3–5 букв, усреднение и softmax (fastText без скрытого
   слоя); принимается с уверенностью от 50 %.
5. **Тип чека и продавец** — для сомнительных позиций: группа, набравшая не меньше половины суммы уверенных позиций, и
   отрасль сети продавца (Чек-Пул) поднимают вероятность своей группы; в кафе «кофе» — блюдо, в магазине — продукты.
6. Иначе — **«не определено»**, честно, без выдумки.

У каждой позиции хранятся категория, источник, уверенность и причина (`receipt_items.goods_category`, `group_source`,
`group_score`, `group_note`); группа и отрасль позиции — производные категории. **Ручная правка главнее всего**:
каскад её не перезаписывает. **Догадка модели или контекста с уверенностью ниже 90 % нарушением политики не считается** —
нарушение только по уверенным признакам.

**Читаемое название** (`app/goods/names.py`) считается на лету, в базе остаётся исходная строка ФНС:

- убираются артикулы и штрихкоды в начале и конце, метки маркировки «[М]», номера строк;
- «капс» → обычный регистр; марки и размеры с цифрами («М500», «4,2х16», «АИ-95»), латиница и известные сокращения
  («ПВХ», «ГКЛ», «ПЦ») не трогаются;
- расшифровываются только сокращения без рода и числа: «д/» → «для», «в/с» → «высший сорт», «б/г» → «без газа»;
- фасовка (вес, объём, штуки) — отдельным полем: «Цемент М500 Д0, 50 кг»;
- ключ товара для памяти — слова без фасовки и размеров: «ЦЕМЕНТ М500 50КГ» и «Цемент М500 25 кг» — один товар.

**Профиль компании** (`app/goods/profiles.py`, настройка политики): «Общий» (как раньше), «Стройка и ремонт»,
«Общепит», «Торговля», «Офис и услуги», «Транспорт и логистика». Профиль даёт запреты по умолчанию (пока у компании нет
своей настройки) и статью расходов по категории: для стройки «Стройматериалы» → «Материалы», «Инструмент» →
«Инструмент и инвентарь», СИЗ — своей статьёй; для общепита продукты — сырьё кухни, а не нарушение. Статья
**предлагается** кнопкой «Подставить», выбор бухгалтера не перезаписывается.

## Обучение и данные

- `qa/goods_okpd2.py` — названия ОКПД2 → категории программы по таблице префиксов кодов (`qa/goods_corpus/okpd2_goods.tsv.gz`,
  10,7 тыс. строк);
- `qa/goods_corpus/goods_examples.tsv` — 650 строк в стиле кассовых чеков, написаны вручную;
- `qa/goods_train.py` — аугментация (сокращения «шпакл.», опечатки, фасовка, обрезка длинных названий, марки), 109 тыс.
  обучающих строк, логистическая регрессия мини-батчами на numpy, отсев слабых признаков, веса int8; детерминировано.
- Проверка — `tests/fixtures/goods_eval.tsv`: 344 строки, модель их не видит; температура 0,5 подобрана на нём (один
  множитель: «уверенность 80 %» ≈ 80 % попаданий).

## Результаты на проверочном наборе

| | чистые названия | с сокращениями и опечатками |
|---|---|---|
| словарь до 1.70.101 | ошибки из таблицы выше | — |
| словарь 1.70.101 (покрытие → точность) | 95,1 % → 100 % | 59,9 % → 92,7 % |
| модель одна (категория / группа) | 93,9 % / 95,1 % | 87,8 % / 90,1 % |
| каскад без контекста чека: отвечает → точность ответа | 99,4 % → 99,4 % | 91,0 % → 91,4 % |

Модель — 475 КБ, +20 МБ памяти процесса, загрузка 56 мс; позиция — 0,12 мс, чек из 40 позиций — 3,7 мс.
