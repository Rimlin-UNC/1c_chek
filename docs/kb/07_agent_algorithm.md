# 7. Алгоритм работы агента

[← База знаний](README.md) · Связанные разделы: [Runbook](04_runbook.md) ·
[Задачи](02_roadmap.md) · [Вопросы](06_open_questions.md) · [Журнал](08_session_journal.md)

Инструкция для каждой новой сессии. Отчёты владельцу — на русском.
Неизвестное — «требует уточнения». Секреты и ПДн никуда не переносить.

## 1. Старт сессии

1. **Прочитать базу знаний** в этом порядке:
   1. [README](README.md) — срез состояния;
   2. этот алгоритм;
   3. [`02_roadmap.csv`](02_roadmap.csv) — `in-progress`, `blocked`, P0–P1;
   4. [`06_open_questions.csv`](06_open_questions.csv) — `open`;
   5. две последние записи [журнала](08_session_journal.csv);
   6. по задаче — нужные ADR и раздел [БД](05_db_and_migrations.md).
2. **Проверить состояние git.** Восстановленное рабочее пространство может
   показывать ветку на старом коммите, а все файлы — изменёнными.
   ```bash
   git status --short | wc -l
   git rev-parse HEAD; git ls-remote origin refs/heads/<ветка сессии>
   # если HEAD ≠ удалённой голове, сравнить дерево через временный индекс:
   GIT_INDEX_FILE=/tmp/v.idx git read-tree <удалённая голова>
   GIT_INDEX_FILE=/tmp/v.idx git add -A
   GIT_INDEX_FILE=/tmp/v.idx git diff --cached --stat <удалённая голова>   # пусто → безопасно
   git reset --mixed <удалённая голова>                                     # указатель и индекс, файлы не трогает
   ```
   Если разница не пустая — **не коммитить**: разобраться и сообщить владельцу.
   Для истории: `git fetch --deepen=300 origin <ветка>`.
3. **Окружение.** `qa/setup_dev.sh --with-postgres`: `.venv` и `node_modules`
   между сессиями не сохраняются.
4. **Сверить базу знаний с фактом** (только чтение):
   - `gh pr list --state all`;
   - `gh issue list --label roadmap --state all`;
   - Supabase: `list_migrations` и запросы из раздела БД;
   - Vercel: последние деплои проекта `1c-chek`.
   
   При расхождении — сначала поправить базу знаний и отметить это в журнале.
5. Если появилась подключённая страница Notion — сверить её с `docs/kb` (T-14).

## 2. Выбор задачи

- Владелец назвал задачу — берём её.
- Иначе — `todo` с наивысшим приоритетом, без блокера, где «Нужно
  подтверждение владельца» ≠ «да».
- Задача с подтверждением: показать план и ждать явного «да».
- Поставить `in-progress` в CSV. Комментировать issues токен не может (403).

## 3. Ветка

- Работать **только в ветке текущей сессии Arena** (`arena/<id>-1c-chek`).
  Другие ветки не создавать, не пушить в них и в `main`.
- Один PR из ветки сессии в `main`. Если он уже открыт — обновлять описание.

## 4. Реализация

Стандарт — [docs/update_playbook.md](https://github.com/Rimlin-UNC/1c_chek/blob/cd769234ebfc4d5c533a1df25fce31e8a9605212/docs/update_playbook.md)
(ADR-02, 03, 05, 12, 15).

- Сначала тест нового поведения (`tests/test_vXYZW.py`), потом код.
- Схема БД — только добавляющие изменения. Старая версия должна работать с
  новой базой (откат кода без отката БД). Внешних ключей из новых таблиц на
  старые не делать (ADR-09).
- Блок «Проверка чеков (ФНС и источники)», паузу антибана и квоту не трогать.
- Новый экран — в обе матрицы ролей: `app/services/rbac.py` и `app/static/js/app.js`.

## 5. Проверки до коммита

1. `./test.sh full -j2` — **0 failed**. Не прерывать: долгий прогон запускать
   фоновым процессом.
2. `.venv/bin/ruff check app tests qa` — «All checks passed»; храповик долга
   (`tests/test_v17038.py`) не вырос.
3. `npm run lint` (0 ошибок), `npm run test:js`; при изменениях UI —
   `npm run test:e2e`.
4. Изменения SQL или БД — тесты PostgreSQL на одноразовой базе (Runbook).
5. Изменения схемы или путей данных — `python -m qa.upgrade_rehearsal --from-ref <коммит на сервере>`.
6. `git diff --check`.

## 6. Выпуск (если меняется версия)

- **Синхронизация:** «7 мест» и дополнительные точки — по [Runbook](04_runbook.md).
- **CHANGELOG:** запись о выпуске помещается в первые 4000 символов файла.
- **Тексты:** WHATS_NEW, `docs/ui_journal.md`, пины изменённых блоков в
  `blocks.py`. Точные пины старых тестов переводить в структурные (`>=`).
- **Коммит:** `vX.Y.Z: суть; NNN passed`.

## 7. Pull request

- `git push origin <ветка сессии>`.
- Обновить описание PR: суть, проверки с числами, риски, `Refs #N` / `Closes #N`.
- **Не сливать** без подтверждения владельца.

## 8. Обновить базу знаний (в том же PR)

- **Задачи:** статус в `02_roadmap.csv` и в issue.
- **Решения:** новые — в `03_adr.csv`.
- **Вопросы:** обновить `06_open_questions.csv`; закрытые получают ответ и
  статус `closed`.
- **БД:** изменения схемы или Supabase — в `05_db_and_migrations.md`.
- **Журнал:** новая запись в `08_session_journal.csv`.
- **README:** срез состояния и дата.

## 9. Деплой

- **Прод:** владелец ставит обновление из программы. В отчёте дать инструкцию:
  ветка, «Проверить», «Обновить», откат.
- **Vercel:** каждый push создаёт превью-сборку. Убедиться, что последний
  деплой ветки в статусе `READY` (`list_deployments` / `get_deployment`). Это
  сигнал сборки, а не прод. Production Vercel собирается из `main`, его роль
  требует уточнения (T-10).
- Изменения Vercel и слияние в `main` — только по подтверждённому плану.

## 10. Отчёт владельцу

- Что сделано.
- Ссылки на PR, коммит, issues.
- Проверки с числами.
- Что ждёт решения владельца.
- Инструкции, если от него нужно действие.

## Подводные камни (проверено на практике)

- **`/tmp` и `.venv` не переживают смену сессии.** Не опираться на временные
  файлы прошлых сессий.
- **Правка удалённого текста** (описание PR, issue): сначала прочитать текущий
  текст через API, изменить его, проверить, что результат не пустой, отправить
  и прочитать обратно. 2026-11-02 описание PR #3 было случайно очищено из-за
  пустого временного файла — восстановлено через минуту, проверено побайтно.
- **`gh pr edit` не работает:** падает на устаревшем поле Projects (classic)
  в GraphQL. Использовать `gh api -X PATCH repos/Rimlin-UNC/1c_chek/pulls/<N> --input <json>`.
- **Issues:** создание работает; комментарии и правка — HTTP 403.
- **Коннекторы** (Notion, Supabase, Vercel) загружаются заново в каждом ответе —
  после паузы на вопрос вызвать `list_connector_tools` снова.
- **Supabase `execute_query`** возвращает только результат последнего оператора.

## Стоп-лист: только после явного «да» владельца

- Слияние в `main`, закрытие или слияние PR, push в чужие ветки.
- Любые DDL, DML или изменения прав в Supabase: удаление `qa_lock`, история
  миграций, настройки Auth, ключи API.
- Настройки, переменные, домены и деплои Vercel; promote или rollback production.
- Перенос архива (backfill) и любые действия на рабочем сервере.
- Изменения блока ФНС, паузы антибана, квоты.
- Удаление или массовая перезапись записей базы знаний (в Notion — тоже) без
  чтения и без причины.

## Можно без подтверждения

- Чтение GitHub, Supabase, Vercel, Notion.
- Коммиты и push в ветку своей сессии, обновление своего PR.
- Issues и записи базы знаний: создание и обновление (не удаление).
- Локальные тесты и одноразовые базы.
