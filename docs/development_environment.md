# Окружение разработки и проверки

Окружение не переключает приложение на новую модель и не изменяет рабочую БД.
Для его восстановления нужны Python 3 с `venv`, Node.js и npm. Из корня проекта:

```sh
qa/setup_dev.sh --with-postgres
qa/setup_dev.sh --check --with-postgres
```

Скрипт создаёт `.venv`, только если она отсутствует; устанавливает
`requirements-dev.txt`, необязательный драйвер psycopg 3 и Node-зависимости из
`package-lock.json`, если `node_modules` ещё не существует. При существующей
папке без Vitest он останавливается, а не перезаписывает её. Режим `--check`
ничего не устанавливает. Это инструменты разработки, не зависимости production.
Папки `.venv` и `node_modules` игнорируются Git и могут исчезнуть при пересоздании
песочницы: запустите скрипт снова. Скрипт не создаёт `.env`, секреты или базы.

Основные проверки:

```sh
.venv/bin/ruff check app
.venv/bin/pytest tests -q -n 2
npm run test:js
npm run test:e2e
```

Тесты Python изолируют свои SQLite-базы. Playwright запускает сервер с новой
временной SQLite-базой и синтетическими чеками; рабочая база не используется.
Требуются совместимые Chromium и системные библиотеки. Можно установить браузер
через `npx playwright install chromium` или указать исполняемый файл переменной
`YM_PLAYWRIGHT_CHROMIUM`. Тесты запускают реальный браузер, но не проверяют
производственную миграцию, PostgreSQL или физическую печать и PDF.

В этой песочнице проверены пять сценариев в Chromium 153, включая подбор и
перенос двух синтетических чеков разных участников и обезличенный фильтр
участника в «Моих чеках компании». Для разового запуска браузер и библиотеки
получены из npm-пакета `@sparticuz/chromium`; недостающие NSS/NSPR взяты из его
архива `al2023.tar.br` и переданы через `LD_LIBRARY_PATH`. В зависимостях
приложения этот пакет не закреплён. Временные файлы и базы не являются бэкапом.

Для конкурентного теста PostgreSQL необходима *отдельная тестовая база*,
доступная по сети напрямую, и переменная окружения `UNIFIED_POSTGRES_TEST_URL`
с SQLAlchemy-адресом `postgresql+psycopg://…`. Не сохраняйте адрес с паролем в
Git или переписке. Затем запустите `.venv/bin/pytest tests/test_postgres_identity_optin.py -q`.
Этот тест создаёт свою случайную схему и удаляет её, но не проверяет всю
миграцию и приложение. Без адреса конкурентные тесты пропускаются. Supabase
коннектор позволяет выполнять SQL, но он не даёт приложению в песочнице прямого
сетевого подключения к PostgreSQL. Не подставляйте рабочую базу.

Текущий проект Supabase содержит оставшуюся после теста схему
`qa_lock_965266689e1c4867b98ef79644d72d2c`: попытку её удаления ранее
заблокировал фильтр провайдера коннектора. Подробнее — `docs/unified_receipts_wip.md`.

## Агрегированная оценка базы перед объединением

`python -m qa.migration_assessment --sqlite /путь/к/копии.db` читает один
согласованный SQLite-снимок, принудительно открыв файл только для чтения.
Для PostgreSQL установите локально в окружении переменную
`YM_ASSESS_DATABASE_URL` (SQLAlchemy URL с драйвером) и запустите
`python -m qa.migration_assessment --postgres`. Адрес с паролем не следует
передавать в чате, сохранять в истории команд или Git. Транзакция PostgreSQL
READ ONLY и REPEATABLE READ; при активной для текущей роли RLS оценка
отказывается работать, чтобы не принять скрытые строки за отсутствующие.

Отчёт содержит только агрегаты: количество чеков, неполных и повторяющихся
реквизитов, совпадения и расхождения, отсутствующие компании, позиции и
участников, счётчики баллов и согласий. Различие суммы считается точно, без
допуска на округление. Различие даты сравнивает хранимые значения: в SQLite
разное текстовое форматирование одного времени тоже считается расхождением.
Несовпадение баланса и суммы событий — сигнал для проверки, а не доказательство
ошибки. Это не проверка всех данных, не бэкап, не миграция и не разрешение на
обновление. Для больших баз сканирование может нагружать сервер, поэтому
предпочтительна отдельная копия. PostgreSQL-путь пока не прогонялся через
Python на реальной базе приложения.
