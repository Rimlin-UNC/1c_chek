# Чек-справка: как вносить обновления, чтобы ничего не сломать

**Ямастер Чек** (ООО «Ямастер») — для проекта, который стал большим и
функциональным. Основано на реальных релизах v1.55.0 → v1.58.0 и ошибках,
которые в них были найдены и исправлены. Документ — рабочий стандарт:
перед каждым изменением открывать разделы 2 и 4.

---

## 1. Карта зависимостей: что от чего зависит

Программа монолитная, но внутри блоки связаны жёстко. Меняя один блок,
вы почти всегда задеваете перечисленное справа.

| Блок (файл) | От него зависит | Что сломается, если забыть |
|---|---|---|
| `app/config.py` → `APP_VERSION` | `index.html` (?v= ×2), `sw.js` (CACHE + ?v= ×2), `manifest.webmanifest`, `blocks.py`, все `TestVersion*` | Браузер отдаст старый кэш; тесты версий упадут |
| `app/services/blocks.py` (реестр блоков) | карточка «Обновления» в UI, `TestBlocksRegistry` | Пин блока не совпадёт с версией |
| `app/routers/receipts.py` (эндпоинты, воркер) | `app/schemas.py`, `app.js` (URL и тела запросов), тесты v2520/v1573/v1574/v1575 | Кнопки в UI зовут старый контракт — «кнопка есть, а не работает» |
| `app/services/external.py` (цепочка источников, форматы запроса) | настройки в БД (`proverkacheka_token`, `fns_master_token`), карточка «Источники» в `app.js`, тесты v1270/v1550/v1570/v1571/v1576–v1580 | Смена порядка форматов/очереди тишино ломает загрузку чеков |
| `app/static/js/app.js` (SPA) | `ui_harness.js` (общий для test_v1130 и v1140), структурные тесты строки списка, карточки, фильтров | Два теста харнесса падают от одной строки |
| `ext_json` (структура данных чека) | `extBlockHTML()` в app.js, разбор `parse_receipt_payload`, `test_v1572` (REAL_PAYLOAD), печать | Данные есть в базе, но не видны в карточке |
| БД-модели (`app/models.py`) | миграции, прямые фикстуры тестов (UNIQUE fn+fd+fp!) | Интегрити-ошибки, падения фикстур |

**Железные правила:**
- Версия поднимается **синхронно в 7 местах**: `config.py`, `index.html` ×2,
  `sw.js` ×3 (имя кэша + два `?v=`), `manifest.webmanifest`, `blocks.py`
  (пин затронутого блока), `CHANGELOG.md`, `WHATS_NEW` в `app.js`.
- Блок «Проверка чеков (ФНС и источники)» (`/settings/fns`, `#fns-token`,
  мастер-токен) — **не трогать** без прямого указания владельца.
- Миграции — **только добавляющие** (новые колонки/таблицы). Строки БД и
  существующие колонки не переименовывать и не удалять.
- Пауза антибана 2–7 с и квота proverkacheka (12–14/сутки) — **критичны**,
  не убирать и не «оптимизировать».
- Без Celery/Redis; 152-ФЗ: персональные данные не покидают базу;
  `chek.ymaster.ru` и деплой-инфраструктуру не трогать.

## 2. Алгоритм внесения изменения (главный чек-лист)

### Шаг 0. План (до любой правки)
1. Сформулировать изменение **одним предложением** — какой блок и что
   меняется. Если предложений больше трёх — это несколько релизов.
2. По карте (раздел 1) выписать: затрагиваемые файлы, связанные тесты,
   связанные тексты UI.
3. Решить тип изменения:
   - **Точечная правка** (текст, мелкий фикс) — править прямо, поднять
     патч-версию (1.58.0 → 1.58.1).
   - **Структурное изменение** (контракт эндпоинта, схема данных,
     порядок источников) — сначала канон-патч + тесты, потом применение
     (см. раздел 3).

### Шаг 1. Чистая среда
```bash
rm -rf /tmp/v15repo && git clone -q --no-hardlinks \
  -b arena/01a0caaa-1c-chek https://github.com/Rimlin-UNC/1c_chek.git /tmp/v15repo
cd /tmp/v15repo && python3 -m pip install -q -r requirements.txt pytest httpx
```
Никогда не править «в живом» репозитории и не проверять на проде.
Прогон тестов — всегда в чистом клоне.

### Шаг 2. Правки с якорями
- Каждый фрагмент правится по **уникальному якорю** (точная строка из
  файла). Перед заменой: `grep -c "якорь" файл` → должно быть ровно 1.
- Отступы в якоре — точно как в файле (проверять `sed -n 'N,Mp' файл`).
- Одно логическое изменение — один шаг патча с понятным именем
  (`worker-log`, `body-error-v1580`), чтобы при падении якоря сразу
  было видно, где.

### Шаг 3. Синтаксис до тестов
```bash
python3 -m py_compile app/**/*.py изменённые.py
cp app/static/js/app.js /tmp/appcheck.mjs && node --check /tmp/appcheck.mjs
```

### Шаг 4. Точечные тесты затронутых блоков
```bash
python3 -m pytest tests/test_<затронутые>.py -q
```
Если упали тесты, «не относящиеся» к правке — **это не мусор, это
зависимость**, которую вы не учли. Разобрать каждый: либо код правится,
либо устаревший тест переводится на новое поведение **осознанно**.

### Шаг 5. Полный прогон (обязателен перед коммитом)
```bash
python3 -m pytest tests/ -q          # ~5 минут, ждать до конца
```
Релиз коммичется только при **0 failed**. Число passed идёт в коммит-
сообщение (трассировка: сколько тестов закрепляли релиз).

### Шаг 6. Версия + тексты (см. «7 мест» выше)
- CHANGELOG: новая запись сверху, стиль `[X.Y.Z] — дата`, секции
  Added/Fixed/Changed.
- WHATS_NEW в `app.js`: новая версия **выше** предыдущей.
- Точные пины старых тестов (`assert ver == "1.57.9"`) переводить в
  **структурные**: `>= (1, 57, 9)` — иначе каждый бамп ломает старые
  тесты (ошибка повторялась 4 раза, пока не стало правилом).

### Шаг 7. Коммит и пуш
```bash
git add -A && git commit -m "vX.Y.Z: суть изменения; NNN passed"
git push origin arena/01a0caaa-1c-chek
```

### Шаг 8. Деплой и боевая проверка
```bash
sudo bash /opt/ymaster-check/deploy.sh --update
curl -s http://127.0.0.1:8000/api/v1/about     # версия = ожидаемой
```
Ctrl+Shift+R в браузере (кэш service worker). Smoke: логин → список
чеков → карточка чека → одна кнопка затронутого блока.

### Шаг 9. Живой журнал (первый час после деплоя)
```bash
sudo journalctl -u ymaster-check --since "30 minutes ago" --no-pager
```
Для загрузки чеков: `grep -E "📩|⚠️|💾"`. Журнал — источник правды:
диагностика должна называть причину словами, а не кодами.

### Шаг 10. Если что-то сломалось — откат
```bash
sudo bash /opt/ymaster-check/rollback.sh          # список версий
sudo bash /opt/ymaster-check/rollback.sh 1.57.9   # откат
```
Откат — легитимный шаг, а не поражение: сначала вернуть сервис,
потом разбираться в чистом клоне.

## 3. Структурные изменения: канон-патч + тесты

Когда изменение затрагивает контракт (эндпоинт, схема данных, цепочка
источников, структура ext_json) — порядок жёсткий:

1. **Сначала тесты нового поведения** (в отдельном файле
   `tests/test_vXYZW.py`), включая негативные кейсы и «боевой» пример
   (для разбора внешних данных — реальный ответ источника, как
   REAL_PAYLOAD в test_v1572).
2. **Канон-патч** (`patch_vXYZW.py`): скрипт, применяющий изменения по
   якорям к чистому клону; в конце — assert-проверки результата.
   Канон **не идемпотентен**: применяется один раз на чистый клон.
3. **Перегон**: чистый клон → тест-файл → канон → синтаксис → точечные
   тесты → полный прогон. Только после этого коммит.
4. Старые тесты, закреплявшие старое поведение, переводятся на новое
   **в том же релизе** (иначе «зелёный» релиз невозможен, а красный
   пушить нельзя).

Правило совместимости контрактов: API расширяется **опциональными**
полями (Query/поле схемы со значением по умолчанию); удалять поля и
менять смысл ответов нельзя — UI предыдущих версий не должен умирать.

| Цепочку источников `provider_chain` | тесты v1550/v1570/v1576/v1270, тексты карточки «Источники данных чека» в `app.js`, журнал 🔑/📋 |

| Строку списка чеков (кнопки 📥/📥✓) | `ui_harness.js` (падают ОБА test_v1130 и v1140), test_v1230, test_v2520 (`test_row_only_edit_when_full`) |

## 5. Грабли, на которые мы уже наступали (не повторять)

1. **Точные пины версий в старых тестах** — только структурные `>=`.
2. **Assert с JS template-литералом** — без внешних бэктиков; в Python-
   строке `${...}` безопасен, `определение` бэктиков ломает якорь.
3. **Комментарий в заменяемой строке теста** — `in   # комментарий`
   закомментирует хвост выражения. Комментарий — на предыдущую строку.
4. **Кортежи-скобки в return**: `return False, ("сообщение" "хвост"), {}` —
   склейка строк без запятой; запятая внутри скобок делает кортеж из 2
   элементов вместо 3 (ловилось тестом `expected 3, got 2`).
5. **Фикстуры чеков**: UNIQUE (fn, fd, fp) — у каждого тестового чека
   своя тройка; счётчик, а не константа.
6. **`_parse_operation` получает ключи в нижнем регистре** ("operationtype").
7. **Харнесс один на два тестовых файла** — правка строки списка чеков
   роняет и v1130, и v1140.
8. **`receipts.full_data` NOT NULL с `qr_data`/`receipt_date`** — прямые
   фикстуры обязаны задавать оба.
9. **Прогон тестов прерывать нельзя** — обрыв pytest оставляет
   непроверенное состояние; ждать полного завершения (~5 мин).
10. **Диагноз должен называть причину** («Токен не принят», «Чека нет в
    базе сервиса (code 5)»), а не «данных нет» — иначе невозможно
    удалённо чинить по журналу.

## 6. Готовность релиза (Definition of Done)

- [ ] Изменение сформулировано одним предложением; блоки по карте найдены
- [ ] Чистый клон, правки по уникальным якорям
- [ ] `py_compile` + `node --check` без ошибок
- [ ] Точечные тесты затронутых блоков — зелёные
- [ ] **Полный прогон: 0 failed**, число в коммит-сообщении
- [ ] Версия в 7 местах, CHANGELOG, WHATS_NEW
- [ ] Блок «Проверка чеков (ФНС)» не тронут; миграции добавляющие;
      квота/паузы не тронуты; 152-ФЗ соблюдён
- [ ] Коммит-пуш; `deploy.sh --update`; `/api/v1/about` = новой версии
- [ ] Живой журнал просмотрен первый час; при сбое — `rollback.sh`

*Документ ведёт ООО «Ямастер». Обновлять при каждом новом типе
зависимости или новой грабле — это живой стандарт проекта.*
