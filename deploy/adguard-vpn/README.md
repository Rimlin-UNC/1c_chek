# Telegram через AdGuard VPN на этом же сервере (v1.70.24)

Когда выбирать этот путь: есть лицензия AdGuard VPN и не хочется
поднимать отдельную машину для моста. Сервер считается одним устройством
лицензии; трафик Telegram-бота крошечный.

**Схема с v1.70.24 — TUN + selective-исключения:** AdGuard поднимает
туннельный интерфейс и пропускает через VPN **только домены Telegram**;
весь прочий трафик сервера (сайт, ФНС, MAX, 1С) идёт напрямую, мимо VPN.
До v1.70.24 использовался режим SOCKS5 с локальным прокси — см. раздел
«Возврат на SOCKS5» в конце.

## Быстрый путь — блок «🛡 AdGuard VPN на сервере» (v1.70.28)

**Настройки → «Устройство и служебное» → «🛡 AdGuard VPN на сервере».**
С выпуска 1.70.28 у VPN собственный блок: из карточки Telegram-бота он удалён —
там ему не место. VPN это служба сервера, а не настройка бота.

В блоке — **трёхпозиционный переключатель**:

| Положение | Смысл | Что делает переключение |
|---|---|---|
| ⬅ **влево** (красный) | VPN **выключен**, трафик сервера идёт напрямую | влево = **отключить**: останавливает туннель и автопилот; вход и лицензия сохраняются |
| ⏺ **середина** (серый) | состояние неизвестно **или** операция идёт | — |
| ➡ **вправо** (зелёный) | VPN **включён**, через туннель идёт только Telegram | вправо = **включить**: запускает мастер — установка CLI, ссылка входа, режим TUN, службы, проверка пути |

Середина — честное положение: до первого ответа сервера переключатель состояние
не угадывает. Раньше кнопка красилась в «выключен» ещё до опроса и врала на
работающем туннеле. Стороны переключателя однозначны, поэтому выбирать действие
по угаданному состоянию больше не нужно: недоступная сторона просто не
нажимается (выключать несуществующий туннель нечего).

Положение берётся из **фактического состояния** юнита `adguard-vpn-telegram`
(`systemctl is-active`), а не из журнала установки: туннель могли остановить
руками, и переключатель не имеет права врать. Если systemd недоступен, он
остаётся в середине вместо ложного «выключен».

**Первое включение** (регистрация сервера в аккаунте AdGuard):

1. поставит CLI официальным установщиком (и создаст ссылку
   `/usr/local/bin`, если установщик её пропустил);
2. покажет **ссылку для подтверждения входа** (это и есть регистрация сервера)
   **прямо в блоке** — откройте её, войдите в аккаунт или создайте его,
   установка продолжится сама;
3. включит режим **TUN** и правило «через VPN только Telegram», пропишет
   службы автоподключения и автопилот (15:10), уберёт прокси из настроек
   программы (в TUN он не нужен) и проверит путь (3 запроса, средний пинг).

Ссылка показывается, как только CLI её выдал, и **не исчезает**, если задание
остановилось: живёт она около 30 минут, и потерять её из-за перезапуска
страницы неправильно. Адрес продублирован текстом под кнопкой — его можно
скопировать.

**Повторное включение** идёт без ссылки: вход хранится в
`/root/.local/share/adguardvpn-cli` и не удаляется при выключении.

**Выключение** гасит сначала автопилот и только потом туннель. Порядок
принципиален: иначе `tg-health.sh` в 15:10 увидел бы мёртвый путь и сам
выполнил `connect -l`, то есть включил бы VPN обратно за спиной владельца.

Процесс виден живым журналом прямо в блоке; в конце — «завершено успешно» либо
понятная ошибка. Ручные шаги ниже — полный контроль, если хочется всё сделать
самому.

### Почему раньше ссылка не приходила (v1.70.28)

По документации AdGuardVPNCLI команда `login` — **интерактивная**: она
показывает меню и ждёт выбора владельца.

    b - Open link in browser
    s - Speed up check
    x - Cancel

Мастер запускал CLI с закрытым входом (`stdin=/dev/null`). Меню получало конец
файла, выбирать было некому, и **ссылка не выдавалась вовсе**: панель честно
писала «идёт установка», но подтверждать было нечего. В SSH-терминале всё
работало именно потому, что `b` нажимали руками — так было в v1.70.13, которую
владелец и вспоминал как рабочую. Никаких прав, сети или лицензий для этой
поломки не требовалось.

Теперь команде даётся **настоящий псевдотерминал** (`pty`, окно 80×24, эхо
ввода погашено), и мастер отвечает на меню сам: `b`, затем `s` («speed up
check») и повторно `b`, если ссылка ещё не пришла. Это в точности воспроизводит
сеанс SSH, в котором вход работал. Вывод очищается от ANSI-эскейпов и `\r` до
того, как попасть в журнал и в разбор ссылки: иначе эскейп прилипал бы к концу
URL и владелец получил бы нерабочий адрес. Домен ссылки по-прежнему проверяется
по списку AdGuard — подменённый домен не показывается
([#188](https://github.com/AdguardTeam/AdGuardVPNCLI/issues/188)).

Если CLI всё же отвечает `Failed to get auth link` — это не наша поломка, а
дефект самого AdGuard VPN CLI:
[#142](https://github.com/AdguardTeam/AdGuardVPNCLI/issues/142) (исправлен в
VPN Client v0.19.35) и открытый
[#169](https://github.com/AdguardTeam/AdGuardVPNCLI/issues/169) на Ubuntu 24.04
с CLI 1.7.12. Причина — недоступные корневые сертификаты. Лечится на сервере:

```
sudo apt install -y ca-certificates
sudo update-ca-certificates
```

Мастер пишет эту команду прямо в тексте ошибки, а отсутствие
`/etc/ssl/certs/ca-certificates.crt` видно **предупреждением на первом шаге** —
до установки CLI и до траты ссылки входа.

Мастер также больше не рапортует «вход уже выполнен» просто потому, что ссылки
не было: признак успеха берётся из документированного текста CLI
(`Successfully logged in`), иначе владелец получает честное сообщение и запасной
путь — ручной вход в SSH.

### Как мастер понимает, что получилось (v1.70.27)

Мастер выполняет **документированную последовательность** команд AdGuard и
верит их кодам возврата — ровно так, как описано в БЗ AdGuard и README CLI:

    adguardvpn-cli login                                   # ссылка подтверждения
    adguardvpn-cli config set-mode TUN                     # режим TUN
    adguardvpn-cli config set-tun-routing-mode AUTO        # маршруты ведёт сам CLI
    adguardvpn-cli site-exclusions mode selective          # только перечисленное — в VPN
    adguardvpn-cli site-exclusions add api.telegram.org    # + остальные домены ниже
    systemctl enable --now adguard-vpn-telegram            # connect --no-fork

Фатальны только отказы **этих** команд, отсутствие `/dev/net/tun` в фазе `tun`
(там TUN действительно невозможен) и реально не поднявшийся туннель.

> **Две ловушки ручного повтора этого списка** (v1.70.29, обе встречены на
> живом сервере):
>
> 1. `site-exclusions add` принимает **конкретные домены**, а не описание
>    «домены Telegram». Полный список — в разделе «Установка на сервере» и в
>    `TG_DOMAINS` помощника. Wildcards обязательны **в кавычках**
>    (`"*.telegram.org"`): без кавычек их раскроет шелл
>    ([#148](https://github.com/AdguardTeam/AdGuardVPNCLI/issues/148)).
>    Пустой список в режиме selective означает, что **через VPN не идёт
>    ничего**, включая Telegram.
> 2. Юнита `adguard-vpn-telegram.service` не существует, пока его не положил
>    мастер (шаг `units` берёт файлы из комплекта
>    `/usr/local/share/ymaster-adguard`, разложенного `install-rule`). Ранняя
>    команда `systemctl enable --now` отвечает «Unit file … does not exist» —
>    это не поломка, а порядок шагов.
>
> Обе ловушки исчезают, если не повторять список руками, а включить VPN
> переключателем в блоке «🛡 AdGuard VPN на сервере»: мастер выполняет эти
> команды сам, в правильном порядке и с настоящими доменами.

Всё остальное — **наблюдения, которые не прерывают установку**. Формат
текстового вывода CLI нам не подконтролен и может отличаться от ожидаемого,
поэтому падать из-за нераспознанной строки нельзя: это мешало бы запуску VPN.
Такие наблюдения пишутся в живой журнал словом «внимание»:

- перечитанный режим исключений (`site-exclusions mode` без аргументов печатает
  текущий). Если CLI ответил `general`, это показано владельцу: в `general` тот
  же список работает наоборот — в VPN уходит всё, КРОМЕ Telegram. Установка
  при этом не прерывается, домены добавляются;
- слушатель на `127.0.0.1:1080` после поднятия туннеля — признак того, что
  сервер остался в SOCKS. Порт может быть занят и посторонним сервисом,
  поэтому это предупреждение, а не отказ;
- отсутствие `/dev/net/tun` на шаге проверки сервера — узел может появиться
  позже (модуль `tun` грузится по требованию), вердикт вынесет сам CLI;
- состояние автопилота при выключении — выключение не блокируется, а от
  воскрешения VPN защищает сам `tg-health.sh` (см. ниже).

**Настоящая проверка пути — шаг `verify` в программе**: он меряет фактический
маршрут до `api.telegram.org` (3 запроса, средний пинг) тем же способом,
которым ходит бот. Если selective-режим не применился, Telegram пойдёт
напрямую и шаг честно упадёт — это надёжнее разбора текстового вывода CLI.

Автопилот `tg-health.sh` **не поднимает VPN, который владелец выключил**:
скрипт выходит, если юнит туннеля снят с автозапуска (`disabled`/`masked`).
Проверяется текст ответа `systemctl is-enabled`, а не код возврата — при
недоступном systemd прежнее поведение сохраняется.

`deploy.sh --update` помимо помощника и sudoers-правила освежает уже
разложенные по системе юниты и `/usr/local/sbin/tg-health.sh` — через
`try-restart`, а не `restart`, поэтому выключенный владельцем VPN обратно
не включается. Ни одна команда освежения не может уронить `install-rule`.

### Пароль сервера не нужен (v1.70.16)

Мастер **не спрашивает пароль sudo** — ни в браузере, ни где-либо ещё.
Привилегированные шаги выполняет один помощник
`ymaster-adguard-setup.sh` из этого каталога, установленный в
`/usr/local/sbin/ymaster-adguard-setup` (root:root, 0755) и разрешённый
узким правилом `/etc/sudoers.d/ymaster-adguard` на фиксированные фазы:

    sudo -n /usr/local/sbin/ymaster-adguard-setup preflight|install|login|tun|off|units|autopilot|version|status|rights

`deploy.sh` ставит помощник и правило сам — при установке и при каждом
`--update`. Если сервер развёрнут раньше (или правило сняли), панель
мастера покажет **одну** команду: выполните её в SSH один раз и нажмите
«Проверить снова»:

    sudo bash /opt/ymaster-check/deploy/adguard-vpn/ymaster-adguard-setup.sh install-rule /opt/ymaster-check

Что делает команда: раскладывает комплект юнитов в root-каталог
`/usr/local/share/ymaster-adguard`, ставит помощника в `/usr/local/sbin`,
пишет правило NOPASSWD на перечисленные фазы для служебного пользователя
программы (берётся из `User=` юнита `ymaster-check`, иначе — владелец
каталога программы) и проверяет его через `visudo -c`. Служебный
пользователь может помощник **запустить**, но не может изменить — поэтому
правило не даёт ему произвольного root.

Откат (убрать правило, помощника и root-копию комплекта):

    sudo /usr/local/sbin/ymaster-adguard-setup remove-rule

Проверка, что правило работает (от имени служебного пользователя):

    sudo -u ymaster sudo -n /usr/local/sbin/ymaster-adguard-setup rights   # → ok

## Как это работает

    Ямастер Чек ──обычный HTTPS-запрос──▶ api.telegram.org
                     │ (selective-исключение AdGuard)
                     ▼
                 tun-интерфейс ──шифрованный туннель──▶ сеть AdGuard

Режим **TUN** поднимает виртуальный сетевой интерфейс, а
**selective-исключения** (`site-exclusions mode selective`) говорят
AdGuard: в туннель отправлять **только** перечисленные домены. Маршрути-
зация — `AUTO`: AdGuard сам держит маршруты при реконнектах и смене
локации. Всё, что не в списке (сайт, ФНС, MAX, 1С), идёт напрямую и VPN
не затрагивает.

Почему не SOCKS5, как было до v1.70.24: программа ходит в Telegram через
`httpx`, а его SOCKS-транспорт не поддерживает `socks5h` — удалённое
разрешение имён. Значит адрес `api.telegram.org` определялся **обычным
DNS сервера**, и при отравлении DNS бот получал подменённый адрес и
молчал, хотя прокси был жив. В TUN-режиме DNS уходит в туннель, поэтому
такой отказ невозможен, а поле «Прокси» в программе остаётся пустым.

Почему не самодельные маршруты по CIDR Telegram (режим `SCRIPT`):
[AdguardTeam/AdGuardVPNCLI#69](https://github.com/AdguardTeam/AdGuardVPNCLI/issues/69)
и [#190](https://github.com/AdguardTeam/AdGuardVPNCLI/issues/190) —
«Routing mode SCRIPT cause "Unknown error" and won't connect». Плюс
список подсетей AS62041 пришлось бы поддерживать вручную, а доменные
исключения AdGuard обновляет сам.

> **Известное ограничение selective-режима.**
> [AdguardTeam/AdGuardVPNCLI#166](https://github.com/AdguardTeam/AdGuardVPNCLI/issues/166)
> (открыт, отложен до VPN CLI v2.0): при нестабильном основном туннеле
> bypass-соединения тоже разрываются на реконнектах. Ответ разработчика
> AdGuard от 19.08.2026: «В теории это можно улучшить, и не рвать их».
> Для сервера это означает, что в момент переподключения VPN могут коротко
> рваться и прямые соединения. Если такое заметите — см. «Возврат на
> SOCKS5» в конце файла.

## Установка на сервере (Ubuntu)

> **Главное правило ручной установки: всё — от одного пользователя.**
> Вход и настройки CLI хранятся в `$HOME/.local/share/adguardvpn-cli`,
> а юнит туннеля запускает CLI от root (`User=root`, `HOME=/root`).
> Если сделать `login` под обычным пользователем, а службу запустить от
> root — туннель поднимется без лицензии и сразу отвалится. Поэтому все
> команды ниже выполняются через `sudo`.

1. **Установите CLI** (официальный установщик). Флаг **`-a y`** отвечает
   «да» на единственный вопрос установщика — «create a link in
   /usr/local/bin? [y/N]». Ссылка обязательна: на неё жёстко прописаны
   `ExecStart=` юнита туннеля и `CLI=` в автопилоте.
   ```
   curl -fsSL https://raw.githubusercontent.com/AdguardTeam/AdGuardVPNCLI/HEAD/scripts/release/install.sh \
       -o /tmp/adguard-install.sh
   sudo sh /tmp/adguard-install.sh -a y
   ```
   Двумя командами, а не через `| sh`: в пайплайне код возврата
   принадлежит последней команде, и отказ `curl` (нет сети, DNS,
   GitHub недоступен) выглядел бы как успешная установка.

   > `-v` — это **verbose**, а не «без вопросов» (и он уже включён по
   > умолчанию). Без `-a y` установщик читает ответ с терминала; если
   > терминала нет, ответ считается пустым, создаётся файл
   > `.nosymlink` — и ссылка не появляется вовсе.

   Проверка:
   ```
   adguardvpn-cli --version
   ```
   Если пишет `command not found` — установщик не стал делать ссылку
   (так бывает, когда `/usr/local/bin` не входит в `PATH`): создайте её
   вручную.
   ```
   sudo ln -sf /opt/adguardvpn_cli/adguardvpn-cli /usr/local/bin/adguardvpn-cli
   ```
2. **Войдите в аккаунт с лицензией** (один раз, обязательно через `sudo`):
   ```
   sudo adguardvpn-cli login
   ```
   CLI покажет ссылку — откройте её на любом удобном устройстве
   (компьютер/телефон) и войдите. Сервер запомнит вход.
3. **Включите режим TUN и правило «через VPN только Telegram»**:
   ```
   sudo adguardvpn-cli config set-mode TUN
   sudo adguardvpn-cli config set-tun-routing-mode AUTO
   sudo adguardvpn-cli site-exclusions mode selective
   sudo adguardvpn-cli site-exclusions add api.telegram.org
   sudo adguardvpn-cli site-exclusions add "*.telegram.org" t.me "*.t.me" \
        telegram.me telegram.dog core.telegram.org
   ```
   `api.telegram.org` — обязательный: это Bot API, через него работает
   бот. Поддомены AdGuard сам не наследует
   ([#148](https://github.com/AdguardTeam/AdGuardVPNCLI/issues/148)),
   поэтому `"*.telegram.org"` добавлен отдельно **и в кавычках** — без
   кавычек wildcard раскроет шелл.

   Проверка, что правило записалось:
   ```
   sudo adguardvpn-cli site-exclusions show
   sudo adguardvpn-cli site-exclusions mode      # → selective
   ```
4. **Выберите локацию**, где Telegram доступен:
   ```
   sudo adguardvpn-cli list-locations
   ```
5. **Подключитесь и проверьте путь** (в TUN прокси не нужен — запрос
   идёт обычным образом, а в туннель его уводит selective-правило):
   ```
   sudo adguardvpn-cli connect -l "<локация из списка>"
   sudo adguardvpn-cli status
   curl https://api.telegram.org/ -m 10
   ```
   Любой ответ HTTP (200/302/404) — путь жив; «таймаут» — попробуйте
   другую локацию (шаги 4–5).

   Заодно убедитесь, что остальной трафик в VPN **не** ушёл — публичный
   IP должен остаться адресом сервера:
   ```
   curl -s https://ifconfig.me
   ```

   Перед включением службы из шага 6 остановите это ручное подключение
   (`sudo adguardvpn-cli disconnect`), иначе служба и ваш сеанс будут
   мешать друг другу.
6. **Автозапуск туннеля** (юнит `adguard-vpn-telegram.service` —
   переподключает VPN после перезагрузки сервера). Файл уже лежит на
   сервере вместе с программой — берите из комплекта, это не зависит от
   доступности GitHub и от ветки:
   ```
   K=/opt/ymaster-check/deploy/adguard-vpn
   sudo install -m 0644 -o root -g root $K/adguard-vpn-telegram.service /etc/systemd/system/
   sudo systemctl daemon-reload
   sudo systemctl enable --now adguard-vpn-telegram
   systemctl is-active adguard-vpn-telegram
   ```
   То же с GitHub (ветка `main` — канал обновлений с v1.70.18), если
   комплекта на сервере нет:
   ```
   B=https://raw.githubusercontent.com/Rimlin-UNC/1c_chek/main
   curl -fsSL -o /tmp/adguard-vpn-telegram.service \
       $B/deploy/adguard-vpn/adguard-vpn-telegram.service
   sudo install -m 0644 -o root -g root /tmp/adguard-vpn-telegram.service /etc/systemd/system/
   sudo systemctl daemon-reload
   sudo systemctl enable --now adguard-vpn-telegram
   ```
   Юнит запускает CLI от root (`User=root`, `HOME=/root`) — поэтому
   `login` из шага 2 обязательно должен быть выполнен через `sudo`.
   Если вход делали под другим пользователем, повторите
   `sudo adguardvpn-cli login` (либо поправьте `User=`/`HOME=` в юните).

   Проверка, что туннель действительно поднялся:
   ```
   systemctl status adguard-vpn-telegram --no-pager
   curl https://api.telegram.org/ -m 10
   ```
7. **В программе**: «Настройки → Telegram» → кнопка «🛡 AdGuard VPN».
   В TUN-режиме поле «Прокси для Telegram» должно быть **пустым** —
   мастер очищает его сам. Если там осталось `socks5://127.0.0.1:1080`
   от прежней схемы, уберите его (символ `-` в поле → «Сохранить»):
   локального прокси больше нет, и бот стучался бы в мёртвый порт.
   Затем «🔍 Диагностика» → «💾 Сохранить и запустить».

## Отладка

- статус и подключение: `sudo adguardvpn-cli status`;
- текущий режим и список исключений:
  `sudo adguardvpn-cli config show`,
  `sudo adguardvpn-cli site-exclusions show`;
- логи автозапуска: `journalctl -u adguard-vpn-telegram -f`;
- бот молчит: проверьте, что поле «Прокси» в программе **пустое** (в TUN
  прокси не нужен, а старое значение `socks5://127.0.0.1:1080` уводит бота
  в мёртвый порт) и что воркер запущен (строка статуса в карточке);
- путь не работает: `curl https://api.telegram.org/ -m 10` — таймаут
  означает, что либо туннель не поднят, либо `api.telegram.org` не попал
  в selective-исключения;
- в VPN уходит не только Telegram: `sudo adguardvpn-cli site-exclusions
  mode` должен отвечать `selective`; в режиме `general` через туннель идёт
  всё, кроме исключений, — это противоположный смысл списка;
- нет `/dev/net/tun` — TUN-режим невозможен (контейнер без `NET_ADMIN`).

## Безопасность

- В туннель попадают **только** домены из selective-списка; прочий трафик
  сервера (сайт, ФНС, MAX, 1С) идёт напрямую и не покидает свой маршрут.
- Локального слушающего порта схема больше не поднимает: SOCKS-прокси
  127.0.0.1:1080 в TUN-режиме отсутствует, наружу не отдаётся ничего.
- DNS-запросы к доменам из списка уходят в туннель — подмена адреса
  `api.telegram.org` локальным DNS больше не возможна.
- Токен бота остаётся зашифрованным в базе программы; VPN-сервис его не
  видит — он лишь транспорт.
- Привилегированные шаги по-прежнему выполняет только помощник
  `ymaster-adguard-setup` через узкое sudoers-правило на фиксированные
  фазы; произвольных команд от root программа не запускает.

## Возврат на SOCKS5 (если selective-режим подвёл)

Selective-режим AdGuard не идеален:
[#166](https://github.com/AdguardTeam/AdGuardVPNCLI/issues/166) — при
нестабильном туннеле на реконнектах рвутся и прямые соединения. Если это
мешает, прежняя схема возвращается четырьмя командами:

```
sudo adguardvpn-cli config set-mode SOCKS
sudo adguardvpn-cli config set-socks-port 1080
sudo systemctl restart adguard-vpn-telegram
curl -x socks5h://127.0.0.1:1080 https://api.telegram.org/ -m 10
```

И в программе: «Настройки → Telegram» → поле «Прокси для Telegram» →
`socks5://127.0.0.1:1080` → «💾 Сохранить и запустить».

> **Важно.** Прокси в этом поле нужен **только** в SOCKS-режиме. В рабочем
> режиме TUN его задавать нельзя: локального слушателя `127.0.0.1:1080` там
> нет, и бот ушёл бы в несуществующий прокси и замолчал. Мастер потому и
> очищает это поле при установке. Возврат на SOCKS5 — крайняя мера, а не
> настройка по умолчанию: в SOCKS-режиме `set-dns` и `set-change-system-dns`
> не работают, а маршруты и DNS остаются прямыми.

Автопилот `tg-health.sh` определяет режим сам: если порт 1080 слушается —
замеряет через прокси, иначе напрямую. Менять скрипт при переключении
режимов не нужно.

## Автопилот: суточная проверка и смена локации (v1.70.14)

Локацию не нужно подбирать руками. Раз в сутки — проверка и, если надо,
автосмена.

**Как работает:**
1. **15:00 МСК** — программа замеряет пинг пути (3 коротких запроса) и
   показывает среднее в карточке Telegram рядом с кнопкой «📏 Пинг».
2. **15:10 МСК** — сценарий-автопилот `tg-health.sh` (systemd-таймер):
   - пинг в норме (≤ 30 мс) → ничего не делает (экономия: в обычный день
     всего 3 коротких запроса);
   - пинг выше 30 мс или путь мёртв → подключает **Германию**; если и
     она медленнее порога — локацию с **минимальным пингом**; после
     смены — контрольный замер. Список локаций с пингами запрашивается
     только в этот момент (не тратим трафик в здоровые дни).

**Установка (один раз).** Нужен root: файлы пишутся в `/usr/local/sbin`
и `/etc/systemd/system`. Проще всего взять их из комплекта, который уже
лежит на сервере вместе с программой (`/opt/ymaster-check/deploy/adguard-vpn/`)
— тогда не зависит от доступности GitHub и от ветки:
```
K=/opt/ymaster-check/deploy/adguard-vpn
sudo install -m 0755 -o root -g root $K/tg-health.sh /usr/local/sbin/tg-health.sh
sudo install -m 0644 -o root -g root $K/tg-health.service /etc/systemd/system/
sudo install -m 0644 -o root -g root $K/tg-health.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now tg-health.timer
systemctl list-timers tg-health.timer --no-pager
```
То же самое с GitHub (ветка `main` — канал обновлений с v1.70.18), если
комплекта на сервере нет:
```
B=https://raw.githubusercontent.com/Rimlin-UNC/1c_chek/main
curl -fsSL -o /tmp/tg-health.sh $B/deploy/adguard-vpn/tg-health.sh
sudo install -m 0755 -o root -g root /tmp/tg-health.sh /usr/local/sbin/tg-health.sh
curl -fsSL -o /tmp/tg-health.service $B/deploy/adguard-vpn/tg-health.service
curl -fsSL -o /tmp/tg-health.timer $B/deploy/adguard-vpn/tg-health.timer
sudo install -m 0644 -o root -g root /tmp/tg-health.service /tmp/tg-health.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now tg-health.timer
```
Автопилот управляет подключением через тот же `sudo`-доступ к CLI, что и
служба туннеля, поэтому `login` из шага 2 тоже обязан быть root'овым.

**Проверка вручную** (сразу видно результат, не дожидаясь 15:10):
`systemctl start tg-health.service` и `journalctl -u tg-health.service
-n 30 --no-pager`. Порог и прокси меняются в шапке скрипта
(`TARGET_MS`, `PROXY`).

Таймер живёт по серверному времени — сервер по инструкции стоит в МСК
(проверка: `timedatectl`; если нет — `timedatectl set-timezone Europe/Moscow`).
Точные пороги подберёте сами: 30 мс — хороший уровень для уведомлений бота
(трафик крошечный, даже 60 мс не заметят сотрудники).
